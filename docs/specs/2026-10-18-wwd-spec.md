# wwd: one fact per host, declared jobs, pooled workers (spec)

Status: draft for WWD-0 (lead 1f, 2026-10-18). Plan: `docs/plans/2026-10-18-wwd-plan.md`. Discussion page (decisions,
inventory, removal list, App migration, roadmap): `docs/pages/wwd-plan.html`. Research: `reports/測試工作 runner 與資源池.md`.

## 0. Why

The week of 10-11 grew load control one layer at a time — leases, the gate, the watcher, the App's load views, assist,
the dispatcher — each patched onto the last. 40 releases and 424 PRs later mlab was still "full" 76–78% of the time,
something waited for a slot 15–20 hours a day, and the watcher spent 1.38 G cache-read tokens in 2.2 days. The host
state is read in 13 places with 6 definitions of "full"; the gate guesses from command text what a command is and keeps
needing new rules. This spec replaces the guessing with declaration and the scattered readings with one fact per host.

## 1. User decisions (2026-10-18, do not reopen)

- **D1** Three layers: measurement, control, demand. Presentation is out of scope until WWD-7.
- **D2** One fact, many readers: each host has exactly one sampler; derived judgements (zone, headroom) are computed by one
  piece of code that every reader uses.
- **D3** Name: **wwd** (watcher worker daemon), installed on all four hosts (mlab, air26, mserv, air19). Roles:
  **watcher** (measurement), **queue** (stores the jobs submitted on its host; always on), **worker** (claims jobs from any
  host's queue and runs them; can be switched off). The queue is not part of the worker. "runner" is not a role name.
  air19 runs no worker by default.
- **D4** The Hosts page section 「觀察主機」 becomes 「資源池主機」 and lists all four hosts.
- **D5** Control by declaration: heavy work goes through declared tasks (a per-repo manifest) and `pdx test`; a job has
  an id, a stored result and a completion notice, and outlives its caller.
- **D6** No live output streaming: the caller gets the result after the job ends (agents only read output at the end).
- **D7** Decentralised queue with work stealing: a job lives in the queue of the host it was submitted on; every worker
  reads all queues and claims from the origin. A busier origin is more attractive to steal from.
- **D8** Agents decide by one rule — tests, builds, lint and type checks go through the entry. A hook may rewrite or
  block. Whatever is not declared is observed and the rules are patched later.
- **D9** Isolation: process level on macOS (clean env, private HOME/TMPDIR, `tmux -L`, process groups); systemd limits
  and sandboxing on mserv. No VMs (VirtualBuddy) and no OrbStack in the worker.
- **D10** Runnability is earned: a host may advertise a task label only after a qualification run matches a reference
  host; toolchain drift revokes it; disagreement quarantines it.
- **D11** Exceptions (the App's dev-page auto packaging, dev servers, watch mode) are not queued; wwd sees them and the
  local worker yields while they run.
- **D12** (recommendations accepted with 「可以開工」, 10-18) The App keeps talking only to Purdex daemons, which expose
  the pool; the manifest lives at `.wwd/tasks.toml`; single-file tests stay on the local fast lane and never leave the
  host; the assist allow list is dropped (host owners control their worker switch); the watcher becomes an advisor woken
  only for exceptions (WWD-8); #3189 closed; phases gated by real-host acceptance and metrics.
- **D13** Team size up to 6 members; members are woken staggered, each after checking memory pressure (user, 10-18).

## 2. Processes and hosts

| Host | Purdex daemon | wwd | worker (default) |
|---|---|---|---|
| mlab (macOS arm64, M4, 16 GB) | yes | yes | on: heavy 1, light 2; interactive sessions first |
| air26 (macOS arm64, M5, 24 GB) | yes | yes | on; yields while the owner is active |
| mserv (Linux amd64, N150, 16 GB) | no | yes | on; 2 cores / 4 GB sandbox beside production services |
| air19 (macOS 14 amd64, Intel) | no | yes | **off** |

- **Binary**: `cmd/wwd`, built for darwin/arm64, darwin/amd64 and linux/amd64. It depends only on packages that build on
  Linux (`internal/hostmem`, `internal/gate`, `internal/resources`, `internal/fleet` already do; `cmd/pdx` does not, #3076).
  New code lives under `internal/wwd/...`.
- **Separate process** from the Purdex daemon, restarted independently: deploying Purdex never stops a running job.
- **Install**: `pdx setup` installs or upgrades wwd on mlab and air26 (launchd LaunchAgent, KeepAlive). mserv and air19
  get the binary and a unit by a small install script (systemd service on mserv, LaunchAgent on air19).
- **Paths**: config `~/.config/wwd/config.toml`; pool token `~/.config/wwd/pool.token` (0600); data
  `~/.local/share/wwd/` (SQLite `wwd.db`, logs, job logs); local socket `~/.local/share/wwd/wwd.sock`; work root per
  host config (default `~/.local/share/wwd/work`; air26 and mserv keep `~/Assist` so prepared clones and dependency
  caches are reused).
- **Network**: HTTP on port **7871** (7870 is taken on mlab), bound to the host's tailnet address and 127.0.0.1.

## 3. Facts (watcher)

### 3.1 The record

One record every 5 s, kept in memory for an hour; a per-minute rollup is written to `wwd.db` (the successor of
`resources.db`'s `host_minutes`). Wire form (JSON, `v` = 1):

```json
{
  "v": 1, "host_id": "…", "alias": "mlab", "at": "2026-10-18T05:00:00+08:00",
  "platform": "darwin", "arch": "arm64", "os_version": "26.6.2",
  "cpu":  { "ncpu": 10, "load1": 4.7, "load5": 5.1, "idle_pct": 62.0 },
  "mem":  { "total_mb": 16384, "available_mb": 843, "pressure": 1, "page_out_rate": 0, "swap_out_rate": 0,
            "swap_used_mb": 2100, "compressor_mb": 2300, "psi": null },
  "disk": [ { "mount": "/", "free_gb": 17.2, "used_pct": 92.4 } ],
  "procs": [ { "pid": 123, "name": "node", "cpu_pct": 88, "mem_mb": 910, "mem_kind": "footprint",
               "owner": { "kind": "job", "id": "j_…", "session": "…" } } ],
  "residents": [ { "session": "…", "kind": "codex-broker", "count": 3, "mem_mb": 640 } ],
  "tools": { "go": "1.26.0", "node": "24.14.0", "pnpm": "10.23.0", "php": ["7.4.33", "8.4.21"], "xcode": "…" },
  "owner": { "active": true, "idle_s": 42, "reason": "hid" },
  "exceptions": [ { "name": "app-dev-package", "since": "…", "until": "…" } ],
  "derived": { "zone": "normal", "headroom": { "heavy": 1, "light": 2 }, "sessions_room": 2 },
  "worker": { "enabled": true, "slots": { "heavy": 1, "light": 2 }, "running": { "heavy": 0, "light": 1 } }
}
```

- `procs`: the top 12 by memory and the top 12 by CPU (union). `owner.kind` is one of `job` (a wwd job's tree), `session`
  (a Claude Code or codex session's own tree), `codex` (a codex run dispatched by a session, attributed to that session),
  `resident` (a long-lived helper owned by a session: codex broker, vite, playwright, MCP servers), `system`.
  Attribution is best effort (process ancestry first, then environment; macOS `procargs2` limits apply).
- `residents`: per session, the non-job long-lived helpers (the watcher's 10-18 investigation: idle codex brokers, vite
  for screenshots, playwright, 13 workspace-mcp copies). Shown, never killed.
- `mem.psi` (Linux only): `{ "some10": …, "full10": …, "some60": … }`. On Linux `pressure` is derived from PSI and
  `available_mb` by the mapping measured in **M-L** (WWD-0); until then `pressure` = 0 (unknown).
- `owner` (air26 only; `null` elsewhere): rule from **M-S2** (HID idle time, xcodebuild / swift-frontend running).
- `sessions_room`: advisory "how many more agent sessions this host can take", for a lead deciding whether to wake a
  member (watcher 10-18: average live sessions rose 3.6 → 8.6; each woken session adds about 0.5 GB). Never enforced.
- Every field above is part of the contract and has a fixture in `internal/wwd/wire` (WWD-0c), including `disk`,
  `residents`, `exceptions` and `worker`; a field a platform cannot read is `null`, never omitted.
- Sampling must not become load: no fork per sample on macOS where a syscall exists (sysctl, Mach, libproc); budget
  idle CPU < 1% and RSS < 50 MB, measured at WWD-1 acceptance.
- Known false readings are fixed at the source (#3134 simulator memory counted twice, #2965 desktop apps), not hidden
  by an ack table.

### 3.2 Derived judgements (the only definitions)

- `zone` (`normal` | `warning` | `danger` | `unknown`): macOS keeps today's `PressureZoneLatch`
  (`internal/resources/pressurezone.go`): danger at pressure 4, warning at pressure ≥ 2 or page-out rate ≥ the limit,
  leaving warning only below `ExitMargin` (0.9) × the limit. Linux uses the M-L mapping. CPU load is shown, not zoned.
- `headroom.heavy` = free heavy slots when zone is `normal`, no exception is active and the owner is not active; else 0.
  `headroom.light` = free light slots unless zone is `danger`, an exception holds light too, or the owner is active.
- These replace `FullLatch`, `ZoneLatch`, the mod's available-MB parallelism, the watcher thresholds (`x_cores`, `y_mb`)
  and the assist probe's load / idle rules.

### 3.3 API (facts)

- `GET /v1/info` → `{host_id, alias, version, proto: 1, platform, arch, worker: {enabled}, labels: [...]}`
- `GET /v1/facts` → the current record.
- `GET /v1/facts/history?since=<RFC3339>&step=1m|5s` → records (5 s within the last hour, 1 m rollups beyond).
- `GET /v1/pool` → this wwd's cached view of every peer (`info` + latest facts + reachability), the single place the
  Purdex daemon reads the pool from.
- `GET /v1/events` (Server-Sent Events) → `facts` (≤ 1 per 5 s), `job` (state changes), `labels`, `exception`.

## 4. Jobs and the queue

### 4.1 The job

```json
{
  "id": "j_01JC…", "origin": "mlab",
  "repo": { "name": "purdex", "root": "<sha of the repo's first commit>", "remote": "git@github.com:wake/purdex.git" },
  "snapshot": { "commit": "<sha>", "tree": "<tree sha>", "base": "<merge-base with the default branch>", "rel_cwd": "spa" },
  "task": "spa-related", "args": ["src/a.ts"], "class": "merge",
  "labels": ["os:darwin", "repo:purdex"], "locks": [], "cacheable": true, "timeout_s": 1800,
  "supersede_key": "<hash of the worktree path>:spa-related",
  "submitter": { "session": "…", "ref": "_abc123", "team": "…", "host": "mlab" },
  "created_at": "…", "state": "queued",
  "claim": { "worker": "air26", "attempt": 1, "since": "…" },
  "result": { "exit": 0, "summary": { }, "log": "j_…/log", "host": "air26",
              "started_at": "…", "finished_at": "…", "cache_hit": false, "reason": "" }
}
```

- `class`: `release` > `merge` > `dev` (priority). Default from the manifest; `pdx test --class` may lower, never raise
  above the manifest's maximum (a lead's release scripts may set `release`).
- The snapshot is the X2a temporary-index commit (`internal/gate/assist_snapshot.go` `SnapshotTree`): the working tree
  as it is, untracked files included, the caller's index untouched.

### 4.2 States and transitions

`queued → claimed → running → succeeded | failed | cancelled | superseded | expired`, plus `running → queued` (release).

| Transition | Who | Wire |
|---|---|---|
| queued → claimed | a worker | `claim` (one SQLite transaction on the origin; first wins) |
| claimed → running | the worker, once the workspace is ready and right before the command starts | `start` |
| claimed/running → queued | the worker: owner reclaim (attempt not counted) or infrastructure failure (attempt counted, host held 5 min for the repo) | `release` |
| claimed/running → queued or failed | the origin: lease lapsed (attempt + 1; after 2 attempts `failed`, reason `lost`) | — |
| running → succeeded / failed / cancelled / superseded | the worker | `result` |
| queued → superseded / cancelled / expired | the origin | — |

- **Claim token**: a successful claim returns a fresh random `claim_id` (128 bit). `start`, `heartbeat`, `release`,
  `result`, `log` and `snapshot` must present it; the origin compares it in the same transaction that changes the job.
  A request with a stale or unknown `claim_id` gets `409` and changes nothing — an old execution can never heartbeat,
  upload a log or post a result after its lease was given to someone else. The `claim_id` is never listed in
  `GET /v1/jobs`.
- **Leases are relative**: the claim and each heartbeat answer `{lease_s, renew_s}` (initially 60 s and 15 s). The
  origin keeps the deadline on its own clock; the worker keeps its own deadline on its monotonic clock from the moment
  it received the answer. No absolute time is compared across hosts.
- **Worker that cannot renew**: when its monotonic deadline passes without a successful renewal, the worker ends the
  command (TERM, KILL 10 s later), discards the outcome and cleans up — the origin will have requeued the job.
- **Origin restart**: on start the origin gives every `claimed` / `running` job a fresh full lease before it expires
  anything, so workers that kept running while it was down can renew.
- **Result delivery**: if the origin is unreachable when the job ends, the worker keeps the result and log and retries
  with backoff for up to 10 minutes while still renewing; `result` is idempotent per `claim_id` (a repeat returns the
  first answer). If the lease is lost meanwhile, the result is discarded.
- **Cancel and supersede**: the origin marks a running job `cancel_requested`; the next heartbeat answers
  `cancel: true`; the worker ends the command and posts `result` with `cancelled` (or `superseded`). A newer job with
  the same `supersede_key` supersedes a queued older one at once, and a running one only if the task is
  `interruptible`; a non-interruptible older job runs to its end and its result is kept with `superseded_by` set.
- `expired`: queued longer than the task's `queue_timeout` (default 2 h); the submitter is told, nothing ran.
- Jobs and results are kept 7 days; logs 3 days (the host that ran the job uploads the log with the result).

### 4.3 Cross-host calls (all with the pool token over TCP)

- `POST /v1/jobs/{id}/claim` `{worker, labels, fingerprint}` → `200 {job, claim_id, lease_s, renew_s}` or `409 {state}`.
- `POST /v1/jobs/{id}/start` `{claim_id}` → `200 {lease_s, renew_s}` / `409`.
- `POST /v1/jobs/{id}/heartbeat` `{claim_id}` → `200 {lease_s, renew_s, cancel}` / `409` (stop).
- `POST /v1/jobs/{id}/release` `{claim_id, reason: "reclaim" | "infra", detail}` → `200` / `409`.
- `POST /v1/jobs/{id}/result` `{claim_id, state, exit, summary, started_at, finished_at}` → `200` (idempotent) / `409`;
  `PUT /v1/jobs/{id}/log?claim_id=…` (the log body).
- `GET /v1/jobs/{id}/snapshot?claim_id=…&format=bundle&have=<sha>` → a git bundle of `have..commit`; `format=tar` →
  `git archive` of the commit. Served only for a live `claim_id`. Which format the worker asks for follows **M-S1**.
- `started_at` / `finished_at` in a result are informational (the worker's clock); the origin records its own receive
  times for ordering and metrics.

### 4.4 Submission and reads

- `POST /v1/jobs` — **only on the local socket** (a job is always submitted on its own host); returns `{id}`, or
  `{id, result}` at once on a cache hit.
- `GET /v1/jobs?state=queued` (peers, with the token) → the queued jobs with what a worker needs to choose (no args of
  ad-hoc jobs, see §8.3). `GET /v1/jobs/{id}`, `GET /v1/jobs/{id}/log`, `POST /v1/jobs/{id}/cancel`,
  `GET /v1/jobs?submitter.session=…` (the App and `pdx jobs`).

### 4.5 Result reuse

- Key: snapshot tree + task + args + the task definition hash (its `run`, `cwd`, `env`, `args` kind, `summary` after
  parsing the manifest) + `os` + `arch` + the full toolchain fingerprint of the host that ran it (OS version and every
  tool version the task's labels name) + that host's qualification fingerprint for the task.
- Only `succeeded` results of tasks marked `cacheable` are reused; failed, cancelled, superseded, expired and
  infrastructure outcomes never are. A drift that revokes a label invalidates the reuse entries made with it. A hit returns the stored result with `cache_hit: true`. This removes the
  member-then-lead re-verification by hand, and codex re-running what Claude just ran (watcher 10-18: 72% identical).

### 4.6 Ordering and fairness (our product rule; no CI system defines one)

A worker scores every claimable job it can see:

`score = 1000·class + wait_minutes + origin_bonus + warm_bonus − size_penalty − same_session_penalty`

- `origin_bonus`: +200 when the origin's zone is `warning`, +400 at `danger` (offload where it hurts).
- `warm_bonus`: +50 when the repo clone and the dependency cache for the job's lockfile are already on this host.
- `size_penalty`: this host's speed factor × the task's estimated minutes (mserv is slow: it prefers small jobs).
- `same_session_penalty`: −30 per earlier queued job of the same submitter session.
- Ties by `created_at`. The weights are initial values, tuned from job records after WWD-4.

## 5. Worker

- **Loop**: every 2 s, or on a peer's `job` event: if `headroom` allows, read all peers' queued jobs, keep those whose
  labels ⊆ this host's labels and whose locks are free, score, claim the best; on `409` try the next. After the workspace is ready the worker calls `start`; it renews per
  `renew_s` until it posts the result or releases.
- **Capacity**: config slots (heavy / light) × headroom (§3.2). The local fast lane (§5.2) uses the same slots.
- **Workspace**: a fresh directory per job under the work root, from the snapshot (`git worktree add --detach` on a
  local clone when present, else the tar); dependencies from a cache keyed by the lockfile hash (APFS clone on macOS);
  per-job tsc build info; removed after the result is sent; a sweep removes leftovers older than 1 h.
- **Environment**: starts empty; only the manifest's `env` allow list and fixed values; `HOME`, `TMPDIR` and
  `XDG_*` point into the workspace; `PDX_*` state directories point into the workspace; tests use `tmux -L`.
- **Platform limits**: macOS — a process group, `dev` jobs on mlab under background QoS so interactive sessions keep the
  P cores. Linux — `systemd-run --wait --pipe` transient service with `CPUQuota`, `MemoryMax`, `PrivateTmp`,
  `ProtectHome`, `ReadWritePaths=<workspace>`, `NoNewPrivileges` (parameters confirmed by **M-L2**); a per-job MySQL
  database on mserv for tasks with `db = "per-job"`.
- **Timeout and cancel**: TERM to the group, KILL 10 s later. **Owner reclaim** (air26): stop claiming, end running jobs,
  `release` them with `reason: "reclaim"` (back to `queued`, no attempt counted).
- **Summary**: parsed from the task's report (`go-json`: `go test -json`; `vitest-json`: the JSON reporter; `junit`:
  phpunit / jest junit; `plain`: the last 40 lines). Shape: `{passed, failed, skipped, failures: [{name, file, message}],
  tail: [lines]}`. The agent reads the summary, the full log only when needed.

### 5.1 Infrastructure failures

Snapshot fetch, workspace or dependency setup failing is not the command's result: the worker calls `release` with
`reason: "infra"` (the job returns to `queued`, attempt counted), this host is held off for that repo for 5 min, the
reason is recorded. If the origin cannot be reached for `release`, the lease simply lapses. A red test is red: the result is never re-run
elsewhere to get another answer.

### 5.2 Local fast lane

When the task allows it (`local`), the submitter is on this host and `headroom` allows, `pdx test` runs the command in
the caller's own working tree at once (no snapshot), holding a local slot (today's gate light-slot code), and records a
job with the result. Single-file tests always take this lane and never leave the host (D12).

## 6. Task manifest — `.wwd/tasks.toml`

```toml
[entry]
mode = "rewrite"            # advise | rewrite | deny — what the hook does with an undeclared test/build command

[tasks.spa-file]
run     = "pnpm vitest run --reporter=json --outputFile={report} {files}"
cwd     = "spa"
args    = "files"           # files | packages | none | pass (pass: local-only tasks)
local   = true              # true | false | "files<=N" | "packages<=N"
summary = "vitest-json"

[tasks.spa-related]
run       = "pnpm vitest related --run --reporter=json --outputFile={report} {files}"
cwd       = "spa"
args      = "files"
class     = "merge"
labels    = ["os:darwin", "repo:purdex"]
deps      = ["pnpm-lock.yaml"]
cacheable = true
timeout   = "30m"
summary   = "vitest-json"
qualify   = { args = ["src/lib/fleet/parse.test.ts"], reference = "air26" }
```

- Placeholders: `{files}` (paths relative to `cwd`, validated to exist in the snapshot, no `..`), `{packages}` (Go
  package patterns), `{report}` / `{junit}` (output files inside the workspace).
- Fields: `run`, `cwd`, `args`, `local`, `class` (default `dev`, the maximum a caller may ask), `labels`, `locks`,
  `deps` (lockfiles for the dependency cache key), `cacheable`, `interruptible`, `timeout`, `queue_timeout`, `env`
  (allow list and fixed values), `db` (`per-job`), `summary`, `qualify`.
- The test tiers become tasks: development (`spa-file`, `go-pkg`), merge (`spa-related`, the changed packages, `lint`,
  `execstat-guard` run on its own without `-run`), release (`go-all`, `spa-full`, `tsc-force`, `mod-all`).
- Manifests for purdex, aigora-v2 and at-inwin-plugin are written in WWD-3 / WWD-6.

## 7. Labels and qualification

- **Automatic labels** from facts: `os:darwin|linux`, `arch:arm64|amd64`, `tool:node24`, `tool:go1.26`, `tool:php80`,
  `tool:xcode16`, …; `repo:<name>` once the host has a prepared clone of that repo.
- **Earned labels** `task:<repo>/<task>`: granted after a qualification job — the task's `qualify` args run on this host
  and on the reference host at the same snapshot, with the same pass/fail sets. The fingerprint (tool versions, OS
  version) is stored with the label.
- **Drift**: a fingerprint change revokes the host's earned labels for the affected tools and queues a `dev`-class
  re-qualification.
- **Disagreement**: the same snapshot + task with different outcomes on two hosts quarantines the label on the
  non-reference host until re-qualified. The original result stands.
- A job's `labels` may name earned labels; a host without them never claims it.

## 8. Entry, enforcement and observation

### 8.1 CLI

- `pdx test <task> [args…] [--class dev|merge|release] [--detach] [--json]` — submit and wait; prints the summary; exit
  code = the job's exit code; `124` timeout, `130` cancelled, `3` wwd unreachable, `4` manifest or argument error, `5`
  no host can ever take it (labels), `6` expired in the queue. Waiting long is fine: the mod moves a waiting foreground
  call to the background, and Claude Code notifies on completion.
- `pdx test --list` · `pdx jobs [ls|show|log|cancel] …` · `pdx wwd [status|pool|worker on|off|exception start|stop]`.

### 8.2 Hook (successor of `hooks/gate.js`)

- Recognises a test or build tool call (go test/build/vet, vitest, jest, tsc, phpunit, pest, swift build/test,
  xcodebuild, pnpm build/test/check, make lint/test, composer test).
- Matches the repo manifest's tasks by command shape → rewrites to `pdx test <task> …`.
- No match → by `[entry].mode`: `advise` (let it run, say which task to use), `rewrite` (run it as an ad-hoc job),
  `deny` (refuse with the task to use). It no longer decides heavy versus light.

### 8.3 Ad-hoc jobs

An undeclared command run through the entry. Conservative: heavy class, local host only (an arbitrary command is never
executed on another host), recorded as `undeclared`.

### 8.4 Observation

Process trees that belong to no job but use more than a threshold (CPU × duration or memory) are recorded with their
session, command and peak — codex trees included. A periodic list feeds manifest and hook rules. Nothing is blocked or
killed.

## 9. Exceptions and worker settings

- wwd routes (local socket, or TCP with the pool token for the Purdex daemon of another host acting for the App):
  `GET /v1/worker`, `PUT /v1/worker` `{enabled, slots: {heavy, light}, owner_rule}` (persisted in `wwd.db`, emits a
  `worker` event); `POST /v1/exceptions` `{name, until | pid, holds: ["heavy", "light"]}`, `DELETE /v1/exceptions/{name}`
  (emit `exception` events).

- `pdx wwd exception start <name> [--until <time>|--pid <pid>]` / `stop`; the Purdex daemon calls it for the App's
  dev-page auto packaging; known packagers (electron-builder) are recognised by their process too.
- While one is active the local worker takes no new heavy job (light too if declared); other hosts are unaffected.
- Dev servers and watch mode are never jobs; they count in facts and therefore in `headroom`.

## 10. Purdex daemon integration

- The Purdex daemon reads only its local wwd (socket): `GET /v1/pool`, `GET /v1/events`, job queries.
- **For the App**: `GET /api/pool/hosts` (the four hosts: info, latest facts, worker state, labels), `GET /api/pool/facts/
  history?host=…`, `GET /api/pool/jobs?…`, `GET /api/pool/jobs/{id}` (+ log), host events `pool.changed` and
  `jobs.changed`; capabilities `pool.v1`, `jobs.v1`. During migration `/api/fleet` and `fleet.changed` are produced from
  the pool (same `FleetHost` / `FleetFast` / `FleetQueue` shapes) so the App changes nothing until WWD-7.
- Mutations for the App, admin token only (device tokens 403): `PUT /api/pool/hosts/{alias}/worker`,
  `POST /api/pool/hosts/{alias}/exceptions`, `DELETE /api/pool/hosts/{alias}/exceptions/{name}`; the daemon forwards to
  the named host's wwd.
- `monitor` host readings, RT-5a `spawn_resources` and the watcher detector read `derived` / facts from wwd.
- Completion notice: when the submitter's session lives on this host, the Purdex daemon tells it (the same per-session
  notify path assist X1b uses), in addition to the waiting `pdx test` process — once per job (deduplicated by job id)
  for every terminal state: succeeded, failed, cancelled, superseded, expired, lost, and a cache hit.

## 11. Security

- TCP requires the pool token; the local socket is trusted (same user). Submissions only on the socket.
- A worker runs only manifest tasks for remote jobs; arguments are validated against the task's `args` kind.
- Snapshots, heartbeats, releases, results and logs need the job's live `claim_id` (a per-claim capability); the
  shared pool token alone is not enough, so one peer cannot act for another's claim.
- A worker rejects a remote job whose task is not in the repo's manifest at the snapshot, or whose arguments fail the
  task's `args` validation; the origin never lists ad-hoc jobs to peers.
- Tailnet-only bind; no route is exposed through `mcp.mlab.host` or Cloudflare.

## 12. Migration and compatibility

- `pdx lease run` stays as an alias (WWD-0a kept it) until its callers move to `pdx test`: lead deploy scripts
  (`~/.local/share/purdex-lead/deploy/*.sh`, 20 scripts), aigora-v2 `scripts/lib/check.ts:500` and

  tables (with a migration).
- The watcher keeps running as today until WWD-8.

## 13. Advisor (the watcher's successor, WWD-8)

Woken only when rules cannot resolve: an unknown heavy process tree persisting; pressure ≥ 2 for long while the queue
is empty (residents, not jobs); a qualification disagreement; disk below 20 GB; a worker crash loop. One session per
incident, Sonnet by default, given a facts snapshot; it ends when done. A daily digest is generated from records.
The name (「顧問」, code `advisor`) is to be confirmed by the user.
