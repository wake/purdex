架構拆分 · 開源選型 · 決策文件

Nexen · Type 2 執行平面

把「常駐 agent」與「單次執行 agent」拆成兩型，釐清 Purdex 該留什麼、該卸什麼， 並盤點 2026-07 的開源選項判斷 build-vs-buy。 新服務定名 Nexen，指令 nex——與 Purdex(pdx) / Ploom(plm) 同一系列。

一句話
Type 2 的空隙是真的（跨主機執行全場只有四家做到），自建有正當性；但不該從零開始——Purdex 的 dispatch/execution 有八成可以直接搬。 真正待拍板的只有一題：Aigora 遷不遷。
§1

兩型 agent，兩種本質

先把環境與需求拆開。這條軸能一次解釋掉後面所有的設計差異。

TYPE 1

常駐 agent

Purdex · 現在的主力開發工具
  • 在 terminal 中持續存活，有工作目錄
  • 長時間作業與互動，人在現場
  • tmux 是基質，不是實作細節
  • 需要跨主機 UI：host picker、composite key、WS ticket、nested store
  • 逃生艙價值高：背景 job、watch、半跑的 pipeline 都活在 pane 裡
TYPE 2

單次執行 agent

Ploom 與 Aigora 的共同底層需求
  • 以服務形式存在：claude -p stream / codex app-server
  • 一次執行一個工作單元，人多半不在現場
  • 沒有 tmux 可管——沒有終端機語意可用
  • 需要的是：行程生命週期、事件串流、崩潰後可回復、對外可稽核
  • 跨主機靠 pull 模型自然成立，不需要 UI 層的多主機機制
現況的問題
Type 2 的需求正被分兩邊各自處理，而且 Purdex 那一份是歷史偶然。 Ploom 的派工需求疊到 Purdex 上，起因只是「這邊已經有 daemon」——那是機緣，不是設計理由。 Aigora 則自己的伺服器解決掉。於是同一種能力有兩份實作，而承載其中一份的 Purdex 本質是 type 1。

而 Purdex 是現在的開發主力，即使 Aigora 進入狀況也還是會兩邊作業。 所以「把 Purdex 改造成 type 2 平台」這個選項直接出局——不該把每天在用的工具改成別的東西。
§2

耦合實測：能搬多少

這是整份決策最關鍵的事實。直覺會以為「對外可稽核骨架」跟 Purdex 綁死，實測不是。

模組非測試碼碰 Purdex 內部的檔案判讀
executioninternal/module/execution 2,758 行
36 檔		 launcher.go 一個（tmux） 狀態機／outbox／原子交易／admission／canonical／reconcile／sandbox clamp／artifact／read 全部只 import config + core
dispatchinternal/module/dispatch 1,518 行
8 檔		 module.go 一個（wiring：relay／stream／session） client／worker／consumer／report 都是純的

可以直接搬（約八成）

execution 狀態機、launch fence、outbox + 單調 seq + ack cursor、四個複合原子交易、admission（canonical + allowlist + per-repo lock + head/dirty 快照）、reconcile 矩陣、manual reclaim、sandbox clamp、pointer-first artifact、dispatch client/worker/consumer/report。

而且會變簡單

新 repo 的 launcher 不用 tmux、不用 relay——就是 exec.CommandContext + pipe。wiring 也少掉三個依賴。

要重建的

daemon 外殼：HTTP server + bearer auth + config + module registry。Purdex 有，新 repo 要自己的——但 type 2 版本更小：不託管 SPA、不做終端機 WS 多工。

還有

事件串流給即時 client 的介面（Aigora 那條路若要接就需要）。

意外便宜的：跨主機

pull 模型下幾乎免費。每台機器起一個 daemon，各自帶自己的 allowed_repo_roots，各自輪詢 Ploom、claim 服務得了的工單。沒有中央排程器要寫，沒有 host 路由要設計。

對照

Purdex 那套昂貴的跨主機機制（SPA nested store、composite key hostId:sessionCode、host picker、WS ticket auth）全部是 type 1 的需求——人要在 UI 上選連哪台。

沒有白工，也沒有拆除風險

PR-Ploom-M0 還沒開工，契約可以從第一天就指向新服務。而且整套 Ploom+Purdex 派工從未端到端跑過、零使用者——Purdex 那份是 shipped 但未啟用的死碼，遷完直接拆，沒有 gating。

測試就是搬遷的驗證

execution + dispatch 共 10,192 行，其中測試約 5,900 行——比實作還多，且編碼的正是 F1-F5 那些 crash-consistency 情境（兩獨立 DB 原子性／缺依賴 claim-and-drop／rejection 無 backing row／seq gap／allowlist fail-closed）。新 repo 測試全綠＝搬遷忠實，綠了原始碼就沒有保留價值。

⚠️ 「八成可搬」的適用範圍
這個數字量的是 Ploom 那條路的耦合度。一旦 Aigora 也要接（見 §6），Nexen 的範圍就變大，而新增的那塊 Purdex 沒有：

搬得動（Purdex M0，Go）：dispatch consumer · outbox + seq + ack + 原子交易 · admission · execution 狀態機 + launch fence
要用 Go 重寫（Aigora 現有 TS 設計可照抄，程式碼不能）：provider adapter 抽象 · 事件正規化（claude.ts 412 行 + codex.ts 641 行）· resume/interrupt/compact 語意 · 額度讀取與多帳號解析
全新：live 串流給即時 client 的出口

結論不變（還是該建 Nexen），但工時估算要往上調。
§3

開源選型：2026-07-28 盤點

兩支 subagent 分頭查證（OSS runtime 現況 / 協定與 SDK 層），星數與日期取自 GitHub API，抓取日 2026-07-28。 結論：沒有能直接買來用的完整解，但有兩個可以「買一半」。

Paseo — 唯一「產品形態已完成」的

AGPL-3.0 · 11.5k★ · v0.2.3 (07-27)

架構跟要蓋的東西幾乎同構：daemon 跑在任意機器上管 agent 行程、輸出即時串成 WebSocket，各種 client 平等。已經有中性契約——各 provider 正規化成 AgentStreamEvent。生命週期成熟：durable session 恢復不重放歷史、閒置 30 分鐘回收、中斷必須等 provider 確認才改狀態（明確為了避免 split-brain）。額度感知內建。

落差

沒有 issue 輪詢也沒有聊天室入口——兩個前端都要自己接。897 open issues。

AGPL 沒想像中可怕

義務是「網路提供服務時要給使用者源碼」，使用者是自己和幾個朋友就給 repo 連結。只要是「用它的 API」而非「fork 它」，Ploom 和 Aigora 就不是衍生作品。真代價不是授權，是把執行層的演進速度交給別人。

選它之前必做

讀原始碼確認 Claude provider 到底是 spawn binary 還是用 Agent SDK——文件自相矛盾，而這決定了合規（見 §5）。

Symphony — issue 端該抄的規格

Apache-2.0 · 26.3k★ · Elixir 只是參考實作

它不是 runtime，是 SPEC.md。解的正是「issue 被動輪詢 + 排程派工」那一半：輪詢 tracker → per-issue 隔離 workspace → 跑 agent → 產 PR。有個漂亮的設計決策：回寫看板由 agent 自己用 provider-native tool 做，不是 orchestrator 代勞。state machine 值得抄：Unclaimed / Claimed / Running / RetryQueued / Released + run attempt 的 PreparingWorkspace / StreamingTurn / Succeeded / TimedOut。

落差

Codex-only（整棵樹零個 claude）。而且排程狀態純記憶體——重啟後清殘留、重新輪詢、從頭派工，重試計時器與執行中 session 都不持久化。它說的 crash recovery 指 agent 掛掉，不是 orchestrator 掛掉。

反過來的意義

Purdex M0 的 outbox + 原子交易 + reconcile 在這點上比 OpenAI 的參考實作完整。那四輪 codex review 不是過度工程。

Goose — 唯一治理中立的長期押注

Apache-2.0 · 51.8k★ · Linux Foundation AAIF

已捐給 Agentic AI Foundation（與 MCP、AGENTS.md 並列創始，Anthropic 與 OpenAI 都是 Platinum 會員）——全場唯一不綁單一廠商的 durability 訊號。

技術上最該注意的

claude_code.rs 用了完整的 --input-format stream-json 雙向控制協定，實作 ControlResponse / PermissionResponse，能程式化仲裁 Claude Code 的權限詢問，且 CLI 跨 turn 保持存活。這是無人值守派工的關鍵能力，Purdex M0 完全沒有（只有 --permission-mode 一刀切）。

落差

Codex 那側只走 codex exec --json 一次性路徑，弱一截。整體是通用 agent 平台，issue/chat 前端與跨機編排都不在裡面。

§4

協定層：契約不用自己發明

中性事件契約已經有事實標準可以站；但 orchestration 那一半（觸發來源、佇列、workspace、任務生命週期）沒有標準，還是得自己寫。

層現況對本場景的適配
ACPAgent Client Protocol v1 穩定（v2 draft 2026-07-20，勿用 production）· Apache-2.0 · 中立 org + JetBrains · Registry 25+ agents · Go SDK = coder/acp-go-sdk 詞彙可抄，transport 別跑。事件模型涵蓋 content/thinking chunk、tool_call（status/kind/locations/diff）、plan、request_permission、cancel、session/load。但 v1 是 1:1 point-to-point，多 client 看同一 session 沒有語意。
Claude Agent SDK 就是 claude -p 的 typed wrapper（官方 hosting 文件明說 SDK spawn claude CLI 走 stdio）。只有 TS/Python，無官方 Go。 官方文件明確指路：非 TS/Python 語言就用 -p。所以 Go daemon + claude -p 是官方指的路，不是繞路。
codex app-server 官方文件化規格 · Thread→Turn→Item 三層 · thread/resume（server-side 從 rollout JSONL 還原）、turn/interrupt、delta opt-out 全在協定內非 capability 選配 四塊裡最貼場景。它本來就是設計給「你自己的產品」用的 server 端協定。generate-json-schema 可產 Go 型別（不只 generate-ts），schema 隨 CLI 版本走要 pin。
AHPmicrosoft/agent-host-protocol 自稱「ACP 之上的 mutex」：N clients 對 shared session、pure reducer + write-ahead reconciliation。有 Go client。152★，無 production 宣告。 正是 interactive lease 問題的成熟解法（多來源看同一 session 誰有寫入權）。抄它的 state model，別依賴它的實作。
MCP 2026-07-28 spec 改版：core 改 stateless、Tasks 降為 extension、Sampling / Roots / Logging 標記 deprecated 不是 agent lifecycle 層。位置是「agent 用它接外部工具」，不是「daemon 用它管 agent」。Sampling 曾是最接近反向驅動的機制，正要被拿掉。
A2A Linux Foundation · 150+ 組織 · production 使用 粒度太粗——處理「把任務丟給遠端 agent」，不處理逐 token 串流 + 工具呼叫 + 權限請求。
建議的組合
詞彙抄 ACP（Go 型別參考 coder/acp-go-sdk）→ Claude 直接 claude -p --output-format stream-json --include-partial-messages（不經 ACP adapter，見 §5）→ Codex 直接講 app-server（不經 codex-acp，用 generate-json-schema 產 Go 型別並 pin 版本）→ orchestration 抄 Symphony 的 state machine + Sortie 的 workspace 隔離／stall 偵測／SQLite 跨重啟 resume。
⚠️ 無文件保證的介面
--input-format stream-json 官方零文件（anthropics/claude-code issue #24594 明確指出「除了 CLI flag 表格外完全沒有文件」），而這是 print mode 唯一的雙向程式化通道。 自建就是在無文件保證的介面上蓋房子。緩解：用 system/init 事件的 capabilities 陣列做 feature detection（如 interrupt_receipt_v1），不要比版本號。
§5

合規紅線

兩家強度不對稱，這會直接影響架構——不是法務問題，是設計約束。

AnthropicOpenAI
非互動自動化的官方立場 只有「沒被禁的縫」。條款明文禁第三方 offer claude.ai login、禁代使用者路由訂閱請求，且保留無預警執法權。 有官方祝福的路徑。Codex access tokens 定位就是「trusted scripts, schedulers, private CI runners」+ app-server automation。
時間線 2026-01-09 server 端限制 → 02-19 條款明文 → 04-04 全面執行 CI/CD 指南允許搬 auth.json，但要求私有基礎設施 / 單機或序列化 / 非公開 repo
mlab daemon 的處境 灰區——spawn 官方 CLI 而非拿 token 自己打 API，官方也指引用 -p，但沒有任何文件正面說「wrap 官方 CLI 的自建服務可以」 符合官方指南的全部條件
分水嶺 「自己用」vs「服務他人」。條款針對的是 offer login 與代使用者路由。自建自用屬 ordinary use 的合理解釋；一旦讓別人透過你的服務吃你的額度就明確踩線——Aigora「5 人共用房主訂閱」要特別注意這條。

⚠️ --bare 將成為 -p 的預設

官方文件：bare mode「skips OAuth and keychain reads」，認證必須來自 ANTHROPIC_API_KEY 或 apiKeyHelper，且「will become the default for -p in a future release」。

影響

這打在「走訂閱＝零 API token 成本」這個護城河上。不論最後選哪條路，auth 必須從第一天就是可切換的一等設計（訂閱 OAuth ↔ API key ↔ Bedrock/Vertex），不能像現在隱含綁死在 spawn env 裡。

信心

單一來源，未交叉驗證（另一支 agent 沒查這條）。但方向與 Anthropic 持續收緊一致，當成要防的風險而非既成事實。

Claude 走 ACP adapter 是合規死路

官方 agentclientprotocol/claude-agent-acp 包的是 Agent SDK 不是 CLI，實測撞牆——2026-04 有 issue 回報 Pro 訂閱失效，錯誤訊息「does not support using claude.ai subscriptions」，至今無 maintainer 回應。而且會多一層 Node 進程（Go daemon → Node adapter → 實際 agent）。

所以

抄 ACP 的詞彙，但 Claude 這條直連 claude -p。

計價現況

Agent SDK 獨立 credit pool 宣布後已取消／暫停，目前 claude -p、Agent SDK 仍走一般訂閱額度。官方說會重做方案並提前通知。

一處未解的矛盾

一支 agent 引 Help Center 說「ACP 用量照舊走訂閱」；另一支引 GitHub issue 說「ACP adapter 撞訂閱牆」。判讀是「計費歸屬」vs「auth 被擋」兩件事，但無權威來源調和。實測最快——跑一次 ACP adapter 就知道。

§6.5

Workspace 模型

目錄分兩種型態，而非兩種 workspace「模式」。 Nexen 只持有 allowlist 母路徑（policy）；具體用哪些目錄由 consumer 送入（intent）。 這是 M0 已定原則的推廣——sandbox profile 是 request、host policy 是權威、不合就拒；現在同一個模式套到路徑上。

服務層開發層
是什麼Aigora room、Ploom project日後會擴充repo——agent 開發的地方兩個 consumer 都會用到
誰造的服務使用者（自己 clone 的）
服務的自動版本安全網
init + 機械 auto-commit		 ✅ 套用 ❌ 不套用——改用 admission 單一 live + head_at_start/dirty_at_start 快照（＋M3 worktree）
admission 生效不用（每實體獨立，天然無衝突）要（同 repo 併發寫是資料事故）
交付物通常落在這裡diff 本身就是交付物
生命週期跟服務實體綁（房刪了目錄刪）跟使用者的 checkout 綁
釘死：型態由「路徑落在哪組 root」決定，不由 consumer 宣告
nexen config
  service_roots: [ …/aigora/data/rooms, …/ploom/data/projects ]
  repo_roots:    [ /Users/wake/Workspace ]
只有一組 roots、靠 consumer 送進來時標型態的話，consumer 搞錯或說謊，Nexen 就會往使用者的 repo 塞 commit。 由落點決定，consumer 就無法把 /Users/wake/Workspace/foo 標成服務層來繞過保護。 跟 M0 的 unknown profile → reject 同一個 fail-closed 精神。

再加一道目錄層偵測：動任何 git 寫入前先 git rev-parse --git-dir——服務層 root 底下也可能有人放了 repo，或 consumer 把服務層目錄覆寫到 repo 裡（Aigora 的 files_dir 可覆寫）。 已在某個 repo 裡就退回「不 init、不 commit、不顯示版本」。roots 分類決定意圖，目錄偵測是最後保險。
⚠️ 別誤讀：被禁的只有「服務偷偷幫使用者的 repo 存快照」
agent 自己在使用者 repo 裡 git add / commit / 開分支 —— 完全正常，那就是委派的目的，不受任何限制。 兩者是不同的行為者：

agent 的 commit＝有意圖的交付（「我完成了 X」），訊息有意義，時點由 agent 判斷。
服務的 auto-commit＝機械快照（「時間點 T 的檔案狀態」），本質是用 git 實作的 undo buffer，agent 根本不知道發生了。

auto-commit 套在使用者 repo 上最致命的是：它會把使用者自己未提交的 WIP 一起 commit 掉——它只看「git status 有變動」，分不出哪些是 agent 動的。其餘問題：turn 結束 ≠ 工作完成（三輪才做完會產出三個半成品 commit）／歷史被兩種語意交錯污染／可能撞到使用者正在進行的 rebase/stash/detached HEAD。

M0 現在做得是對的：daemon 對使用者的 repo 只讀（rev-parse HEAD、status --porcelain、diff --numstat），零寫入。 dirty_at_start 這個欄位的存在本身就是證據——知道使用者可能有未提交的東西，所以不動它，只記錄它存在過，好讓最後的 diff 能被正確解讀。

worktree 是開發層安全網的升級（從「限制併發」變成「真隔離所以不必限制併發」），不是這條規則的前提。git worktree add 本身是服務對使用者 repo 的寫入，但那是明示的產品功能，不是偷偷做的安全網。
§6.6

收斂後的介面形狀

// consumer → Nexen
session.create {
  mounts: [
    { path: "/…/aigora/data/rooms/<id>/files", role: "artifact", writable: true  },
    { path: "/Users/wake/Workspace/foo",        role: "cwd",      writable: true  },
    { path: "/Users/wake/Workspace/bar",        role: "aux",      writable: false }  // claude 會降級
  ],
  sandbox_profile: "…",        // request，Nexen clamp（只能降）
  provider: "claude" | "codex"
}

Nexen 收到後：canonicalize 每個 path → 依落點判型態 → 開發層那些取有序多鎖 + 快照 → clamp profile → 組 --add-dir / writableRoots → launch。 Nexen 完全不需要知道什麼是「房間」或「project」；日後服務層擴充只是多一組 root，零設計改動。

M0 要改的那一小部分：admission 從單 repo 變多 repo

M0 簽名是 WithRepoLock(ctx, repoLocation string, fn)，Admission{CanonicalPath, HeadAtStart, DirtyAtStart}——單一 repo 的假設寫死在裡面。但 Aigora 的 MAX_WORK_DIRS = 8 說明「一個執行掛多個工作目錄」已是既有能力。

要動的

有序多鎖（canonical path 排序後依序取得，避免死鎖）· Admission 變 slice，每 repo 各自快照 · 衝突判定＝開發層 mount 集合有交集就擋（A 掛 repo1+repo2、B 掛 repo2 也要擋）· terminal diff 每 repo 各做一份。

cwd 由 consumer 送，但 Nexen 要驗

cwd 是產品邏輯（有無工作目錄時該用哪個，是 consumer 的事）。Nexen 驗兩件事：cwd 必須是 mounts 之一；codex resume 時若送來不同 cwd 要明確報錯——codex 的 cwd 在 thread 建立時固定改不了，靜默忽略會讓 consumer 以為改成功了。

服務層的 git 由 consumer 做，不是 Nexen

commit 時機、作者名、要不要 commit 全是產品語意（Aigora 掛 agent 名字、Ploom 可能根本不 commit）。Nexen 回報 terminal + artifact 清單，consumer 自己決定。這也對齊「git 失敗不影響主流程」——那是產品層容錯決策。

Nexen 只做一件

偵測並拒絕在開發層 mount 上做任何 git 寫入，含拒絕 consumer 要求。

有了 artifact sink，就不用掃了

M0 的 artifact ＝ 對 head_at_start 的 diff，隱含假設交付物在 repo 裡——對「改 code 產 PR」成立，但 agent 產的報告／SVG／試算表不屬於任何 repo。

所以

Aigora 現在靠掃 workDir 比對 mtime 猜哪些是產出（scanProducedImages）。有了明確的 role: "artifact" mount 之後根本不用掃——落在 sink 裡的就是。

權限不對稱要在契約層明示

codex 能「掛上但唯讀」（不列進 writableRoots）；claude 沒有 per-path 規則，writable: false 會靜默降級成可寫。

所以

契約要明講，不能讓 Ploom 以為它請求的唯讀真的生效。這跟 Aigora 在 UI 誠實寫「claude 的 workspace 是軟限制」是同一件事，只是搬到契約層。

憑證歸 Nexen 持有

Aigora 現在每輪解析帳號、把 OAuth token 塞進 spawn env。搬到 Nexen 後憑證應歸 Nexen（它才是 spawn 的人），consumer 只送「用哪個帳號」的意向。

連帶

這剛好是 §5 那個「auth 可切換」設計的落點。

§7

委派模型

最後一輪收斂出的形狀：Aigora 保有自己的 agent system，但可以向 Nexen 派送任務。 這讓 Aigora 與 Ploom 變成同一份資訊框架，差別只在主動／被動。

關鍵區分：輔助對話 ≠ 執行任務
房間裡的 claude/codex 存在的目的是輔助對話，它的 conversation 就該活在房間裡——那正是它的價值。 長效開發任務則該委派出去成為獨立執行體。兩者不是同一種東西。
常駐對話 agent委派執行體
是誰房間的 claude / codexNexen 的 execution body（例：Adam）
目的輔助對話執行任務（尤其長效開發）
conversation活在房間、長命、跨話題自己的、任務範圍、獨立
workDir房間檔案目錄（服務層）委派時指定的 repo mount（開發層）
runtime 控制權Aigora 持有Nexen 持有
生命週期跟房間綁跟任務綁，可跨房存在

這剛好補完了原本「常駐角色 vs 任務執行」那條軸——codex 當初指出它不完整、缺的是「誰有 runtime 控制權」。 兩條軸都到齊而且正交，模型才站得住。 

我:      cc 請你用 nn 進行這項開發任務
claude:  好的，任務派送中....
         [Agent Adam 加入]
claude:  任務派送完成，目前由 Adam 進行執行中

「Adam 加入」的三個設計含意

① 執行體是房間的一等參與者，不是一則狀態訊息——有席位、名字、狀態徽章（⏳ 執行中／✅ 完成／❌ 失敗／👀 等你回答）。Aigora 現成的 presence 三態 + hover 選單可直接擴充。

② @ Adam ＝ attach with control lease。房裡的人跟它講話就是取得寫入權，lease 因此有了自然的 UI 語意。

③ Adam 的 transcript 不進 claude 的 conversation。這是最大收益——輔助對話的 context 保持乾淨，不會被任務細節灌爆（也就不用一直 /clear 付那 20k tokens）。

推論

房間 agent 不該等待。說完「派送完成」這一輪就結束，任務獨立跑、之後 Adam 自己回報。fire-and-forget + 事後通知，是「不污染 conversation」能成立的前提。

「類似 subagent 但不是」

真 subagentNexen 執行體
住在哪父 agent 行程內獨立行程
身分無execution_id
可 attach不行可以
壽命隨父 turn 死獨立、可續
誰看得到只有父任何有權的 consumer

UX 隱喻是 subagent，架構上是生一個對等體。

派送有兩種模式，但不是二選一

照 Ploom 已定的 API-first 原則：核心先有 API，CLI 與 MCP 都是它的外皮。

Nexen core API   ← 唯一真相
   ├─ nex CLI    ← 人 · 腳本 · CI · 有 Bash 的 session
   └─ MCP server ← 同一組操作的 tool 化外皮

🔑 但有個實際差異

MCP 可以在不給 Bash 的情況下開放派送。Aigora 的 accessLevel 預設是 off（只有 Write），這種房間沒有 Bash，nex delegate 走不通；但 MCP tool 能單獨加進允許清單（--tools Write,mcp__nexen__delegate）——房間 agent 拿得到派送能力，但拿不到 shell。

分工

MCP：房間 agent 派送（尤其 off 級）· 要 schema 驗證與稽核的動作 · 讓模型知道能力存在而不必寫進 prompt。
CLI：人 · 腳本 · CI · 已有 Bash 的高權限 session · 執行體自己要再派子任務。

Aigora ↔ Nexen 的重疊度

Aigora 房間 agent 需要：spawn · 事件解析 · delta 串流 · resume · interrupt · compact · 額度+多帳號 · 多目錄掛載 · model 切換 · accessLevel · steps · 產圖回收

Nexen 需要：↑ 全部，再加 admission · durable outbox · reconcile · attach+lease · pull adapter · 跨主機

所以

adapter 層近乎 100% 重疊；orchestration 層近乎 0% 重疊。
→ 兩套 orchestration 天經地義（服務不同產品語意）；兩套 adapter 才是痛點——那恰好是最麻煩的部分（--input-format stream-json 官方零文件、codex schema pin 在 CLI 版本），而且要在兩個語言各修一次、各踩一次才發現。

不急著合併，但盯兩個訊號

訊號一：同一個 provider 漂移造成的 bug，你修了第二次（在另一個語言裡）。發生兩三次，重複維護成本就超過遷移成本。

訊號二：Aigora 想讓房間 agent 跑在別台機器上。跨主機是 Nexen 結構上有、Aigora 結構上沒有的東西——這是唯一「不遷就做不到」的需求。

路徑

b → a 可行：先兩套並行（Aigora 保有自己的，只有委派走 Nexen），有證據再決定要不要收斂。

跨 consumer attach 的授權

在 Aigora 房裡接上正在跑的 Ploom execution，在這個模型下自然成立（執行體不屬於 Ploom）。作法：Ploom 依專案產出授權金鑰 → Aigora room 設定填入。

三個要補的細節

① 金鑰帶 scope，預設只給觀察——attach:observe 與 attach:control 分開。
② 每把綁一個 room，不是一個 project 共用一把，才能單獨撤銷。
③ 歸因誠實——Aigora 暱稱即身分，Ploom 只能記「經由 room X（暱稱：…）」，不能假裝是具名帳號。

反方向另計

房裡長出的任務要掛回 Ploom issue，是 Aigora→Ploom 的寫入，另一組憑證、另一套授權。

⚠️ 這個模型帶來的四個待辦
① interactive lease 從逃生艙變核心。M0 是用「deeplink observe-only」迴避 SubscriberToRelay 多 writer race 的；attach-and-converse 成為核心功能後這招不能用。需要：一 execution 一 controller、lease 有期限可 detach、訊息帶 execution_id + lease_id + seq 做冪等、狀態機 detached/attaching/attached/stale/terminated。抄 AHP 的 state model（實作太早期不能依賴）。

② subagent 要誠實分兩件事。觀察 ✅ 可行（parent_tool_use_id 樹狀歸屬）；對話 ❌ 現有 CLI 介面做不到——subagent 沒有獨立 stdin，是父 agent 一個 tool call 內部的東西。能做的最接近版本是「跟父 agent 說話請它轉達」。這限制要早點寫進設計，否則會畫出做不到的 UI。

③ execution body 的生命週期動詞。run terminal ≠ body 終結。需要 active → idle → sleep → archived → terminated，而且有實際成本（一條 claude 磁碟 session／一條 codex thread）。Aigora 的 codex adapter 已有 idle 15 分鐘 unsubscribe + 退避重試可搬。

④ 契約要改：execution_id 會分裂成兩個概念。M0 的 execution_id 同時是「可回報的工作單元」與「deeplink handle」。新模型下 body ＝ attach handle（長命）、run ＝ 可回報單元（一次性）。M0 契約在 Ploom 側還沒實作，現在改零成本。
Core 動詞（修正版）
我先前說「統一之後 Nexen 反而變小、core 只有三個動詞」——這個框架下不成立，範圍是變大的。run 降級成內部階段，對外是執行體： 
execution.delegate(context, mounts, profile, provider) → execution_id
execution.attach(execution_id, mode: observe | control)  → 事件流 [+ lease]
execution.send(execution_id, lease_id, message)          ← 需 lease
execution.interrupt(execution_id, lease_id)
execution.lifecycle(execution_id, sleep | archive | terminate)
第一版切線：單一 controller + observer 唯讀 · 不做 subagent 寫入 · 不做跨 consumer attach（介面留好、預設關閉）。模型不用重畫，第一版不會失控。
§8

順序

為什麼 Aigora 排在 Ploom 前面
dogfood 的路徑是 Aigora，不是 Ploom。Aigora 是活的、天天在用；Ploom 的端點還不存在。 用一個沒人用的 consumer 去定義 API 是經典錯誤——先做 Ploom、之後才補串流，會得到一個對即時場景很難用的介面。 Ploom 那條契約已經寫死在 m0-contract.md，之後對齊就好。
1

Nexen 立起來

搬 execution + dispatch 核心 → 用 Go 重寫 adapter 層（照抄 Aigora 的 TS 設計）→ headless launcher（exec + pipe，比 tmux 版簡單）→ 薄 daemon 外殼。auth 一開始就做可切換。

2

Aigora 先接 —— 第一個 consumer

活的使用者、最快回饋，API 立刻被真實使用打磨。先決定直接接 vs proxy（見 §6）與三個設計張力（§6.5）。

3

Ploom 對接

docs/specs/m0-ploom-handoff.md 改指向 Nexen。契約已有，對齊即可。

4

Purdex 卸下 dispatch/execution

隨時可做，無 gating——整套從未端到端跑過、零使用者。實務上等 Nexen 測試全綠（＝搬遷忠實的證據）就可以拆。

§9

給新 repo 的設計清單

從這輪研究直接導出的具體項目，不是通則。

  • auth 可切換是一等設計（訂閱 OAuth ↔ API key ↔ Bedrock/Vertex）——--bare 風險與 Anthropic 的無預警執法權都指向這裡。
  • feature detection 用 system/init 的 capabilities 陣列，不要比版本號。
  • 權限仲裁：Goose 的 ControlResponse/PermissionResponse 雙向控制協定＝無人值守派工的關鍵，M0 的 --permission-mode 一刀切不夠。
  • 中斷要 bounded：Aigora 的三層（整輪 timeout → interrupt → 寬限後 forceStop 讓事件迴圈脫身）＋ Paseo 的「中斷必須等 provider 確認才改狀態」防 split-brain。
  • resume 前先驗屍：Sculptor 會先檢查 ~/.claude/*.jsonl 還有效才 --resume。
  • 對話續接要有自己的一格：claude -p 自產 UUID → --resume；別跟 runtime session 混名（見委派架構合成檢討 §五-Q3）。
  • 額度歸帳：每輪解析帳號並落在執行紀錄上（Aigora 已有）；Claudexor 是多 profile 輪替的專門解。
  • multi-client 寫入權：抄 AHP 的 immutable state + pure reducer + write-ahead reconciliation，別自創。
  • codex schema pin 版本：generate-json-schema 產出隨 CLI 版本走，升級要 regenerate + 回歸測試。
