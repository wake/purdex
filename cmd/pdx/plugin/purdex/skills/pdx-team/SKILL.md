# pdx-team — lead / member / team and context relay

Vocabulary (spec §4): a **lead** runs a **team** of **members**. A member is never called a worker (that word is Nexen's headless execution). **接力** (relay) is a new conversation taking over when context is full; **切換** (handoff) is terminal ↔ worker.

## When to ask for lead mode, and how to wait

- Ask only when the work is **large and parallel**: several independent pieces that would each take a session a long time. One sequential task is not a reason.
- When the user runs `/team` (or the older `/lead`) or plainly asks you to become a lead, request it at once: the "large and parallel" test above does not apply.
- Run `pdx lead request --reason "<why>" --name "<team name>" --label "<短名>" [--max-members N] [--root <dir>]` **in the foreground**, with Bash `timeout: 600000`. **Never in the background**: the approval is a hard lock on this session and a background run defeats it.
- Always give `--name`: a name for the team's work (at most 64 bytes); it is shown in the team panel, and the user may change it when approving.
- Always give `--label`: a short, meaningful name of your own for the tab group label, about five Chinese characters (10 display columns), e.g. `A 線`, `資源線`, `資源派工` — a summary, never the name cut short.
- The answer is a person's click in Purdex.app. **Never approve yourself**: there is no `pdx` command that approves, and you must not look for another way. While unattended mode is on (which you never turn on and never ask for) your own `pdx lead request` and `pdx adopt` are **refused** (exit 13, `unattended_refused`, "無人值守模式不開放申請，請等待模式解除後，依情況重新申請"): wait until it is off and ask again only if it is still needed.
- **Never turn on 無人值守模式 (unattended mode).** It is the user's switch in Purdex.app: there is no `pdx` command for it, and you must not call the daemon's route or edit host config to get around that.
- Exit 0 means approved. **Treat a timeout (exit 11) as no**, like a denial (exit 10). Exit 13 means the rules refused (you are already a lead, or a member cannot lead).

## Commands the person types: `/team …` and `/relay`

- `/team`, `/team <note>`, `/team spawn <task> [--model m] [--effort e]`, `/team adopt <ref>`, `/team release <ref>`, `/team kill <ref>` and `/relay` are **the person's own commands** and they act at once: no card, no click, no quota, whatever the unattended switch. A person's `/relay` in a member relays that member at once.
- When the mod's prompt gives you `--person <token>` (after `/team` or `/team spawn`), put that exact token on the command it names (`pdx lead request --person <token> …`, `pdx spawn --person <token> …`). **Never invent, guess, store or reuse a token**; it is good for one command, for a few minutes. If the answer is `person_token_invalid`, tell the user to type the command again.
- **Never type into your own terminal to run a slash command** (no `tmux send-keys`, no send-keys route) and never call Purdex.app's routes to approve something or to switch a mode. The daemon cannot stop you yet; the rule is yours to keep.

## As a lead

- `pdx spawn [--cwd <dir>] [--title <t>] [--model <m>] [--effort <e>] [--brief-file <f> | --brief <text>] [--task-subject <s> [--done-when <line>]…]` opens a member on this host in `--cwd` (default: your working directory; it must be under the roots you were granted) and prints one JSON line with its address and ref. The brief reaches the member from you, after a first line saying it is your member, so its replies come back to you. `pdx kill <ref>` closes one of your members; `pdx team` lists them. Address members by **ref** (`<host>/_xxxxxx`): names change, refs are redirected across relays.
- `pdx adopt <ref>` takes a **running session on this host** in as your member (`<ref>` is `_xxxxxx`, its session id, or `<host>/_xxxxxx`; a name alone is not enough). Run it **in the foreground with Bash `timeout: 600000`**: it waits for a click in Purdex.app and prints one JSON line (in unattended mode it is refused, exit 13 `unattended_refused`). Exit 13 means a rule refused it (`adopt_self`, `adopt_target_is_lead`, `adopt_already_member`, `adopt_target_not_found`, `remote_unsupported`, `request_open`, `team_full`; `adopt_target_ambiguous` means two sessions share that ref, so use the session id; the code is the last word on stderr). An adopted member keeps its own model and effort, its self relay is off, and it is told it is your member.
- `pdx release <ref>` lets a member go: it keeps running as an ordinary session. `pdx kill <ref>` closes one: a spawned member's tmux session ends, an adopted member's Claude Code process is stopped and its tmux session stays.
- When you yourself judge that a member is no longer needed, first ask the user with AskUserQuestion. Name the member (its address and title) in the question, and give exactly three options: 釋出 / 關閉 / 保留. Then do what the answer says: 釋出 → `pdx release <ref>`, 關閉 → `pdx kill <ref>`, 保留 → nothing. When the user asked you directly to release or close a member, do it without asking.
- `pdx kill <ref> --handoff` is **hand over, then close**: the member writes its handoff file (or reuses the fresh one it already wrote), then the daemon closes it, and you are told `[pdx team] member … 已交接：<path>，已關閉`. Use it when the member holds work or knowledge worth keeping; it waits for the member, so run it in the foreground. Exit 0 the member is closed; 14 it did not respond (nothing was closed: kill it again or without `--handoff`); 13 refused (`relay_unsupported`: a remote member or an older mod, use plain `pdx kill`). If you are told the file is written but the member was **not closed** (`關閉沒完成`), run `pdx kill <ref> --handoff` again (it reuses the file) or plain `pdx kill <ref>`. What goes into memory and docs is yours to decide.
- **Choose each member's model and effort for its task**: `--model sonnet` for mechanical work, `--model opus` for design; `--effort low|medium|high|xhigh|max`. The host's default model is not fixed, so a spawn without `--model` runs whatever it happens to be today. Check `pdx team`: its MODEL and EFFORT columns show what each member actually runs, from its first turn on.
- Exit 13 means the team rules refused (`not_lead`, `team_full`, `cwd_outside_grant`, `not_your_member`, `relay_open`; the code is the last word on stderr). Exit 14 (`member_start_timeout`) means the daemon gave up on the member after 20 s and freed its place; for a spawn on this host stderr says why (a busy host, retry later, or a host that never saw the Purdex hooks); a spawn --host prints no reason. Exit 1 with the member's JSON on stdout means the member was opened but the brief could not be confirmed: first look with `pdx msg log --tail 10` (or ask the member); only if the log shows it was not sent, send it yourself with `pdx msg send <address>`.
- A brief, task or report message that **may not have arrived** is not an error: the command exits as usual and says on stderr `delivery_uncertain` (or that the daemon's answer could not be read). Treat that message as possibly undelivered, **never send it again** (it would arrive twice), and look with `pdx msg log --tail 10` or ask the receiver. An exit 1 from these commands means the send could not be confirmed (it may also have gone out and only its answer been lost): check with `pdx msg log --tail 10` before sending by hand.
- If `pdx spawn` ends with `spawn_wait_timeout` (exit 1, after 9 minutes of waiting), the member may still be starting: check `pdx team` first and do not spawn again.
- Hand each piece of work to a member as a task: `pdx task add --to <ref> --subject … --brief-file …` (or `pdx spawn … --task-subject …`, whose brief becomes the member's first task); `pdx task ls` and `pdx team` show what each member is on.
- **Recommend a worktree** to each member — have it `EnterWorktree`, or prepare one for it. Where the member works is your call (U10).
- When a member's context runs high (`pdx team` shows CTX, or the daemon's notice arrives: `[pdx team] member <address> [<ref>]「<title>」已用 <N>%，目前閒置。要接力請執行：pdx relay _<ref>`; after a member was auto-compacted you hear `[pdx team] <ref> 已自動壓縮（lead 未在 70% 時接力）`), **you decide** whether and when to relay that member: `pdx relay <ref> --wait 9m`, **in the foreground with Bash `timeout: 600000`** (or with `run_in_background` if you would rather not hold your terminal: the finished background task hands you the same exit code and op JSON, and you must read them; the `[pdx team] member … 接力完成` notice is only a second signal, it is best effort and a failed or cancelled relay sends a different one). While it waits it prints one line on stderr at every state change (`接力 claimed → writing（…，12s）`) and a `接力仍在進行` line each minute, so a quiet terminal is not a hung one: do not interrupt it, the relay finishes when the member's new session ends its first turn (this can take many minutes after `cleared`). The daemon only detects and reports (U9). Exit 0 is done, or the op is still `seen` / `requested` when `--wait` ran out: that means **it will happen when the member's current turn ends** (the daemon waits out a long turn for up to 60 minutes and tells you once at 15), so look at `pdx team` later; 10 denied, 11 timed out or still waiting for the user's approval (member quota used up in unattended mode), 12 cancelled, **or your wait was interrupted (Ctrl-C, a Bash timeout): the relay keeps going, so check `pdx team` before deciding it did not happen**; 13 refused (`not_lead`, `not_your_member`, `relay_unsupported`: that member has no Purdex mod, relay it by hand or restart it; `relay_open`: one is already running); 14 the member did not respond or is gone (`member_unseen`: its mod never acknowledged within 60 s, so its terminal may be stuck on a dialog such as "Mods: Enable hot reloading?" or Claude Code is not running: look at its tab; `member_blocked`: it is waiting on a prompt; `member_busy_timeout`: one turn ran past 60 minutes). A relay waiting for approval is the user's to answer: you never approve it.
- **When `[pdx team] member … 申請接力` arrives you have 5 minutes, and you must answer it.** The member's own mod asks you once its context passes 70% (it keeps working meanwhile). To approve, run `pdx relay _<ref> --wait 9m` **in the foreground with Bash `timeout: 600000`**; the member relays at its next turn boundary. To decline, run `pdx relay _<ref> --deny` (exit 0 once the ask is closed; exit 13 `no_open_ask` if there is none): the member goes on and may ask again later. **Never let it lapse**: the request that says 「這是最後一次申請」 (90% or more) pauses the member until you answer, and you are told 「接力申請 5 分鐘沒有回應，已暫停作業」 with both commands; `pdx relay _<ref>` relays it and resumes it, `--deny` resumes it without a relay. In unattended mode the daemon accepts the ask itself against your member pool (or pauses the member when the pool is empty) and tells you 「無人值守：member … 已自動接力」; you answer nothing. The exit codes are those of `pdx relay` above.
- Write the team roster (each member's ref, address, task and worktree) into §8 「協作關係」 of your own handoff, so the conversation that takes over from you still knows its team.

## As a member

- Report with `pdx report <kind>` (`ack` when you start, `ready` before any merge and wait for the lead's go-ahead, `merged`, `done`; `question` / `blocked` with `--needs`), not free text; `pdx task mine` lists your tasks, and after a relay the notice lists them too.
- **Never relay yourself.** Your relay is the lead's to start — or the person's, by typing /relay.
- Your Purdex mod asks your lead for a relay by itself at 70% of context, at a turn boundary, and you keep working while it waits: **you do nothing**. If the lead approves, the mod takes the relay as below.
- When the lead relays you, the Purdex mod does it all: it takes the lead's control message itself (you never see it) and waits for your running turn to finish. When its **接力 prompt** arrives, write the handoff file it names with **one `Write`** and answer `HANDOFF-WRITTEN`, nothing else (§8 of the file: the prompt lists your lead and team). Then the mod clears you and the new conversation reads the file; your old ref still reaches you.
- Report to the lead's address (`pdx msg send <lead address> "..."`), not to the user.
- A session the lead adopted reads `[pdx team] 你已成為 …` and from then on follows these member rules; if it later reads that its lead let it go, it is an ordinary session again.

## Self relay

- The **Purdex mod asks the user on its own** when this session's context passes the threshold. **You never ask for a relay and never approve one.** When the mod's prompt arrives, write the handoff file it names with **one `Write`** (the mod has already put the git state in the prompt; run no other tool, the relay lock refuses them) and answer `HANDOFF-WRITTEN`, nothing else.
- `/relay off` / `/relay on` / `/relay status` is **the user's switch, not yours**. Do not run it.
- `/relay` (or `/relay now`) is the user's way to relay early: **you never run it**. A session paused with `/relay off` is not relayed by it; the user runs `/relay on` first.
- **Never turn on 無人值守模式 (unattended mode).** It is the user's switch in Purdex.app: there is no `pdx` command for it, and you must not call the daemon's route or edit host config to get around that.
- **The relay quota is the user's.** How many automatic relays a session chain may have while unattended mode is on, and the switch that turns that rule on, are set by the user in Purdex.app's unattended panel (a lead sees its own in the header of `pdx team`, read-only; anyone else looks in the App): there is no `pdx` command for either, you must not call the daemon's routes or edit host config for them, and you never ask for more quota. A relay waiting because the quota is used up waits for the user.
- **The team's member limit is the user's.** How many members a team may have is set by the user in Purdex.app; you never change it and you never ask for a larger team (`team_full` means the team is full: finish or release a member, or tell the user). A lead sees the count as `members M/N` in the header of `pdx team`, read-only.
