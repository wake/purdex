# wwd: one fact per host, declared jobs, pooled workers (spec)

Status: rev 3 — WWD-0 measurements M-L and M-S folded in, WWD-0c contract notes (lead 1f, 2026-10-18). Reports:
`~/.local/share/purdex-lead/briefs/2026-10-18-wwd0-measure-{mserv,snapshot}-result.md`. Plan: `docs/plans/2026-10-18-wwd-plan.md`. Discussion page (decisions,
inventory, removal list, App migration, roadmap): `docs/pages/wwd-plan.html`. Research: `reports/測試工作 runner 與資源池.md`.

## 0. Why

The week of 10-11 grew load control one layer at a time — leases, the gate, the watcher, the App's load views, assist,
the dispatcher — each patched onto the last. 40 releases and 424 PRs later mlab was still "full" 76–78% of the time,
something waited for a slot 15–20 hours a day, and the watcher spent 1.38 G cache-read tokens in 2.2 days. The host
state is read in 13 places with 6 definitions of "full"; the gate guesses from command text what a command is and keeps
needing new rules. This spec replaces the guessing with declaration and the scattered readings with one fact per host.

## 1. User decisions (2026-10-18, do not reopen)

- **D1** Three layers: measurement, control, demand. Presentation is out of scope until WWD-7.
- **D2** One fact, many readers: each host has exactly one sampler; derived judgements (zone, headroom) are computed by one
  piece of code that every reader uses.
- **D3** Name: **wwd** (watcher worker daemon), installed on all four hosts (mlab, air26, mserv, air19). Roles:
  **watcher** (measurement), **queue** (stores the jobs submitted on its host; always on), **worker** (claims jobs from any
  host's queue and runs them; can be switched off). The queue is not part of the worker. "runner" is not a role name.
  air19 runs no worker by default.
- **D4** The Hosts page section 「觀察主機」 becomes 「資源池主機」 and lists all four hosts.
- **D5** Control by declaration: heavy work goes through declared tasks (a per-repo manifest) and `pdx test`; a job has
  an id, a stored result and a completion notice, and outlives its caller.
- **D6** No live output streaming: the caller gets the result after the job ends (agents only read output at the end).
- **D7** Decentralised queue with work stealing: a job lives in the queue of the host it was submitted on; every worker
  reads all queues and claims from the origin. A busier origin is more attractive to steal from.
- **D8** Agents decide by one rule — tests, builds, lint and type checks go through the entry. A hook may rewrite or
  block. Whatever is not declared is observed and the rules are patched later.
- **D9** Isolation: process level on macOS (clean env, private HOME/TMPDIR, `tmux -L`, process groups); systemd limits
  and sandboxing on mserv. No VMs (VirtualBuddy) and no OrbStack in the worker.
- **D10** Runnability is earned: a host may advertise a task label only after a qualification run matches a reference
  host; toolchain drift revokes it; disagreement quarantines it.
- **D11** Exceptions (the App's dev-page auto packaging, dev servers, watch mode) are not queued; wwd sees them and the
  local worker yields while they run.
- **D12** (recommendations accepted with 「可以開工」, 10-18) The App keeps talking only to Purdex daemons, which expose
  the pool; the manifest lives at `.wwd/tasks.toml`; single-file tests stay on the local fast lane and never leave the
  host; the assist allow list is dropped (host owners control their worker switch); the watcher becomes an advisor woken
  only for exceptions (WWD-8); #3189 closed; phases gated by real-host acceptance and metrics.
- **D13** Team size up to 6 members; members are woken staggered, each after checking memory pressure (user, 10-18).

| Host | Purdex daemon | wwd | worker (default) |
|---|---|---|---|
| mlab (macOS arm64, M4, 16 GB) | yes | yes | on: heavy 1, light 2; interactive sessions first |
| air26 (macOS arm64, M5, 24 GB) | yes | yes | on; yields while the owner is active |
| mserv (Linux amd64, N150, 16 GB) | no | yes | on; 2 cores / 4 GB sandbox beside production services |
| air19 (macOS 14 amd64, Intel) | no | yes | **off** |

- **Binary**: `cmd/wwd`, built for darwin/arm64, darwin/amd64 and linux/amd64. It depends only on packages that build on
  Linux (`internal/hostmem`, `internal/gate`, `internal/resources`, `internal/fleet` already do; `cmd/pdx` does not, #3076).
  New code lives under `internal/wwd/...`.
- **Separate process** from the Purdex daemon, restarted independently: deploying Purdex never stops a running job.
- **Install**: `pdx setup` installs or upgrades wwd on mlab and air26 (launchd LaunchAgent, KeepAlive). mserv and air19
  get the binary and a unit by a small install script (systemd service on mserv, LaunchAgent on air19).
- **Paths**: config `~/.config/wwd/config.toml` (this host's alias and slots, the peers: alias + tailnet address, and the `[repos]` clones of §7); pool token `~/.config/wwd/pool.token` (0600); data
  `~/.local/share/wwd/` (SQLite `wwd.db`, logs, job logs); local socket `~/.local/share/wwd/wwd.sock`; work root per
  host config (default `~/.local/share/wwd/work`; air26 and mserv keep `~/Assist` so prepared clones and dependency
  caches are reused).
- **Network**: HTTP on port **7871** (7870 is taken on mlab), bound to the host's tailnet address and 127.0.0.1.

## 3. Facts (watcher)

### 3.1 The record

One record every 5 s, kept in memory for an hour; a per-minute rollup is written to `wwd.db` (the successor of
`resources.db`'s `host_minutes`). Wire form (JSON, `v` = 1):

```json
{
  "v": 1, "host_id": "…", "alias": "mlab", "at": "2026-10-18T05:00:00+08:00",
  "platform": "darwin", "arch": "arm64", "os_version": "26.6.2",
  "cpu":  { "ncpu": 10, "load1": 4.7, "load5": 5.1, "idle_pct": 62.0 },
  "mem":  { "total_mb": 16384, "available_mb": 843, "pressure": 1, "page_out_rate": 0, "swap_out_rate": 0,
            "swap_used_mb": 2100, "compressor_mb": 2300, "psi": null },
  "disk": [ { "mount": "/", "free_gb": 17.2, "used_pct": 92.4, "total_bytes": 245107195904, "avail_bytes": 18467692544 } ],
  "procs": [ { "pid": 123, "name": "node", "cpu_pct": 88, "mem_mb": 910, "mem_kind": "footprint",
               "owner": { "kind": "job", "id": "j_…", "session": "…" } } ],
  "residents": [ { "session": "…", "kind": "codex-broker", "count": 3, "mem_mb": 640 } ],
  "tools": { "go": "1.26.0", "node": "24.14.0", "pnpm": "10.23.0", "php": ["7.4.33", "8.4.21"], "xcode": "…" },
  "owner": { "active": true, "idle_s": 42, "reason": "hid" },
  "exceptions": [ { "name": "app-dev-package", "since": "…", "until": "…" } ],
  "derived": { "zone": "normal", "headroom": { "heavy": 1, "light": 2 }, "sessions_room": 2 },
  "worker": { "enabled": true, "slots": { "heavy": 1, "light": 2 }, "running": { "heavy": 0, "light": 1 },
              "owner_rule": "" }
}
```

- `procs`: the top 12 by memory and the top 12 by CPU (union). `owner.kind` is one of `job` (a wwd job's tree), `session`
  (a Claude Code or codex session's own tree), `codex` (a codex run dispatched by a session, attributed to that session),
  `resident` (a long-lived helper owned by a session: codex broker, vite, playwright, MCP servers), `system`.
  Attribution is best effort (process ancestry first, then environment; macOS `procargs2` limits apply).
- `stats` (**per-minute rollups only**; absent from 5 s records, and from minutes stored before it existed — a reader
  that finds none approximates): what the minute's 5 s samples add up to, worked out per sample in wwd:
  `{sampled_s, full_ticks, full_starts, full_longest_s, normal_s, warning_s, danger_s, heavy_running_max,
  light_running_max, gate_waiting_max}`. `sampled_s` is 5 per good sample (a sample that failed adds nothing; a minute
  wwd started inside has fewer than 60). *Full* is the "host is full" flag with its 0.9 hysteresis (`derived.FullLatch`,
  the same definition as the Purdex `resources.FullLatch`, kept equal by a test until WWD-9 removes that one): entering
  at load1 ≥ ncpu, memory in use ≥ 90 %, or pressure ≥ 2; leaving only below 0.9 × each; `full_starts` counts off→on
  transitions in the minute, `full_longest_s` the longest run running in the minute (one that began earlier counts, and
  may exceed 60). Memory in use is (total − available) / total of the record's own `mem` figures, which on macOS is the same quantity the Purdex sampler computes (Mach's free pages already hold the speculative ones). `*_s` zone seconds are the seconds sampled in each zone (unknown is in `sampled_s` only). The running
  maxima are the worker's. `gate_waiting_max` is null until the gate is folded into wwd (WWD-8/9). The rollup's own
  `worker.running` is the minute's peak too.
- `residents`: per session, the non-job long-lived helpers (the watcher's 10-18 investigation: idle codex brokers, vite
  for screenshots, playwright, 13 workspace-mcp copies). Shown, never killed.
- `mem.psi` (Linux only): `{ "some10": …, "full10": …, "some60": … }` of the **production slices** — the larger of
  `system.slice` and `user.slice` `memory.pressure` — never the host-wide `/proc/pressure/memory`. **M-L** measured why:
  a job throttled inside its own memory limit drives host-wide PSI to some10 92 / full10 90 while `system.slice` and
  `user.slice` stay at 0.00, MemAvailable moves by 170 MB and swap and paging stay at 0. Workers therefore run in
  `wwd.slice` (assist runs in `assist.slice` since 10-18); a slice's PSI is that slice's own state (a job stalled in its
  limit is reported on the job, §5), never host pressure. On Linux `pressure` maps as below; the thresholds are
  **starting values** (M-L could not create a real host-wide shortage beside production services, and the daytime
  baseline was not measured), validated at the first real pressure:

  | `pressure` | Any of (rises after ≥ 10 s, falls after ≥ 30 s) |
  |---|---|
  | 1 | otherwise (measured: idle, and a 2-core PHP suite, both keep memory PSI at 0) |
  | 2 | production `some10` ≥ 10, or `full10` ≥ 1, or `available_mb` < 20% of total, or swap used > 512 MB |
  | 4 | production `full10` ≥ 10, or `some60` ≥ 25, or `available_mb` < 1536, or swap grew > 1 GB within a minute |

  `page_out_rate` / `swap_out_rate` are reported on Linux but never used for the zone (always ≈ 0 under every M-L
  case; `pgpgout` is file write-back). CPU pressure is shown, not zoned. `pressure` = 0 means unknown on any platform
  (the field is never null).
- `owner` (every macOS host; `null` on Linux, and when the owner frameworks cannot be loaded), from **M-S2** (62 samples over 30 minutes,
  every reading from one ssh; wwd reads the same sources locally). It is read whether or not the owner rule is in force: `[owner]
  enabled = false` (or no `owner_rule` in the worker settings) only means the reading is never counted (§3.2) and the worker does not
  yield to it — it does not stop the sampling, so the monitoring page can show whether the owner is using the machine (#3682). A host
  that reads its owner accepts an `owner_rule` (`PUT /v1/worker`) whatever `[owner] enabled` says: the config only gives the rule its
  starting value, and the App's owner-rule editor is shown exactly where `owner` is not null. A job's usage record (§8.6) keeps the owner
  only where a rule is in force. `active` is true when any of:
  1. HID idle (`IOHIDSystem` `HIDIdleTime`) is below N minutes — default 5, set in the worker settings. In use the
     idle time never exceeded 4 s; away, it grew linearly without noise. `reason: "hid"`. Read from `IOHIDSystem`
     itself (10-18, #3280): on air26 the combined-session `CGEventSourceSecondsSinceLastEventType` read 1575 s while
     `HIDIdleTime` read 24871 s, every time (which events shortened the CG reading was not identified), so the CG
     reading is not used; read this way, wwd's idle equals `ioreg`'s.
  2. The screen is unlocked (`IOConsoleLocked` false) and a build of the owner's is running — `xcodebuild`,
     `XCBBuildService` / `SWBBuildService`, `swift-frontend` — or a simulator device is booted (`SimLaunchHost`; the
     `Simulator` app itself is often not running). `reason: "build"` / `"simulator"`. Processes of wwd's own jobs are
     excluded by one shared check (the job marker of §5), used by both the facts and the worker.
  - Not usable: the front app (it stayed `Purdex` through 22 minutes away), load average, and `pmset` `UserIsActive`
    (held for hours by `rcd`, always 1).
  - Known misses, accepted: watching a video or a meeting without input reads as away (a non-`caffeinate`
    `PreventUserIdleDisplaySleep` assertion as a third rule is to be validated, §16); working on air26 over ssh reads
    as away; screen sharing reads as in use.
- `sessions_room`: advisory "how many more agent sessions this host can take", for a lead deciding whether to wake a
  member (watcher 10-18: average live sessions rose 3.6 → 8.6; each woken session adds about 0.5 GB). Never enforced.
  Initial formula (WWD-1d, tuned by observation): when `zone` is `normal`,
  `(available_mb − 1024 − compressor_mb / 4) / 512`, at least 0 and at most 8; any other zone gives 0. On macOS
  `available_mb` is free + inactive pages.
- `worker` in the record carries `owner_rule` beside `enabled`, `slots` and `running`, so every reader — the local
  Purdex daemon and a peer's alike — sees a host's worker state from one place; `GET /api/pool/hosts` fills each host's
  `worker` from its facts.
- Every field above is part of the contract and has a fixture in `internal/wwd/wire` (WWD-0c), including `disk`,
  `residents`, `exceptions` and `worker`; a field a platform cannot read is `null`, never omitted.
- Sampling must not become load: no fork per sample on macOS where a syscall exists (sysctl, Mach, libproc); budget
  idle CPU < 1% and RSS < 50 MB, measured at WWD-1 acceptance.
- Known false readings are fixed at the source (#3134 simulator memory counted twice, #2965 desktop apps), not hidden
  by an ack table.

### 3.2 Derived judgements (the only definitions)

- `zone` (`normal` | `warning` | `danger` | `unknown`): macOS keeps today's `PressureZoneLatch`
  (`internal/resources/pressurezone.go`): danger at pressure 4, warning at pressure ≥ 2 or page-out rate ≥ the limit,
  leaving warning only below `ExitMargin` (0.9) × the limit. Linux uses the §3.1 mapping on the production slices
  (pressure 2 → warning, 4 → danger). CPU load is shown, not zoned.
- `headroom.heavy` = free heavy slots when zone is `normal`, no exception is active and the owner is not active; else 0.
  `headroom.light` = free light slots unless zone is `danger`, an exception holds light too, or the owner is active.
  **The work the worker can take may be wider than this headroom, and only because of a hold with `allow` (§13.4):** the facts keep
  saying 0 with `exception:<name>` for every outside reader, so a reader that knows nothing of `allow` still waits; the worker sets the
  selective holds aside (`derived.HeavyRoomForAllowed`: every other heavy reason must be absent) and takes only a job each of them lists
  (`derived.AdmitsJob`: its class or its repo, every hold must admit it; both lists empty admit none). An exception without `allow`
  holds as before.
  "The owner is active" means this host has an owner rule in force (the one `PUT /v1/worker` last set, not only the config's
  `[owner]`) and its reading says the owner is in use; with an empty rule the reading is still reported in `owner` but is never
  counted here, and the worker does not yield to it either. (`[owner] enabled = false` only leaves the rule empty; it does not turn
  the sampling off — the reading is taken on every macOS host, #3682.)
- **Why a side is 0** (`internal/wwd/derived`, next to `Compute`, which decides headroom from the same list, so a side has room
  exactly when it has no reason): `worker_off`, `zone_warning` | `zone_danger` | `zone_unknown`, `exception:<name>`,
  `owner_active`, `disk_low`, `slots_full`, `gate_full`, in that order; heavy is held by every zone but `normal`, light only by `danger`.
  **`disk_low`** (10-20, ed3920-61): the work root's volume (read with a statfs of the work root itself at every sample, so a volume of
  its own that the facts' disk list does not hold is measured too; unreadable is not a reason) has less free space than the worker's
  `disk_min_gb` (`[worker]`, default 10 like the pdx gate's; 0 is none; `PUT /v1/worker` changes it at run time and `wwd.db` keeps it).
  It holds **heavy only** — a queue job is not claimed and an adhoc fast-lane command is refused (429) — and the facts say so with
  `derived.disk_low` (present only while true), so that the remainder is not read as `gate_full`. Exactly the floor is enough; there
  is no hysteresis. Only that one volume is looked at: a fast-lane directory on another volume is not.
  `GET /api/pool/hosts` gives each host with facts `headroom_reasons {heavy: [...], light: [...]}` (capability `pool.assess.v1`;
  an empty list means there is room). A facts record does not carry the pdx gate (#3450) or which exception also holds light
  work, so the daemon reads those as the remainder: **`gate_full` is the residual condition** — heavy at 0 with none of the
  other reasons (and slots free) — and light at 0 with slots free, no zone or owner reason and some exceptions names all of
  them. A side at 0 that nothing in the record explains (a faulty or skewed peer) is `unknown`, so an empty list always means
  room. `worker_off` is the worker's own flag; it does not change the headroom the record states.
- These replace `FullLatch`, `ZoneLatch`, the mod's available-MB parallelism, the watcher thresholds (`x_cores`, `y_mb`)
  and the assist probe's load / idle rules.

### 3.3 API (facts)

- `GET /v1/info` → `{host_id, alias, version, proto: 1, platform, arch, worker: {enabled}, labels: [...], fingerprint: {os_version, <tool>: <full version>, ...}}`
- `GET /v1/facts` → the current record.
- `GET /v1/facts/history?since=<RFC3339>&step=1m|5s` → records (5 s within the last hour, 1 m rollups beyond).
- `GET /v1/facts/series?since=<RFC3339>&step=1m|5s&limit=<n>` → `{step, points: [...], truncated}`: the same history cut down to
  the points a chart draws (the fields of `GET /api/pool/facts/series`, §10), oldest first. The host that has the data does the
  cutting, so a day of 1 m points is about 300 KB on the tailnet instead of 10 MB of records. **At most `limit` points**
  (default and ceiling 21600: 14 days of 1 m rollups is 20160); more and the latest are kept and `truncated` is true. Served
  and forwarded like the history (socket `?host=`; TCP for a peer's forward). A new route, not a change of the facts record.
- `GET /v1/pool` → this wwd's cached view of every peer (`info` + latest facts + reachability), the single place the
  Purdex daemon reads the pool from.
- `GET /v1/events` (Server-Sent Events) → `facts` (≤ 1 per 5 s), `job` (state changes), `labels`, `exception`.

## 4. Jobs and the queue

### 4.1 The job

```json
{
  "id": "j_01JC…", "origin": "mlab",
  "repo": { "name": "purdex", "root": "<sha of the repo's first commit>", "remote": "git@github.com:wake/purdex.git" },
  "snapshot": { "commit": "<sha>", "tree": "<tree sha>", "base": "<merge-base with the default branch>", "rel_cwd": "spa" },
  "task": "spa-related", "args": ["src/a.ts"], "class": "merge",
  "labels": ["os:darwin", "repo:purdex"], "locks": [], "cacheable": true, "timeout_s": 1800,
  "supersede_key": "<hash of the worktree path>:spa-related",
  "submitter": { "session": "…", "ref": "_abc123", "team": "…", "host": "mlab" },
  "created_at": "…", "state": "queued",
  "claim": { "worker": "air26", "attempt": 1, "since": "…" },
  "started_at": "…",
  "result": { "exit": 0, "summary": { }, "log": "j_…/log", "host": "air26",
              "started_at": "…", "finished_at": "…", "cache_hit": false, "reason": "" }
}
```

- `class`: `release` > `merge` > `dev` (priority). Default from the manifest; `pdx test --class` may lower, never raise
  above the manifest's maximum (a lead's release scripts may set `release`).
- The snapshot is the X2a temporary-index commit (`internal/gate/assist_snapshot.go` `SnapshotTree`): the working tree
  as it is, untracked files included, the caller's index untouched. **M-S1** found X2a's empty temporary index drops
  tracked files that match `.gitignore` (at-inwin-plugin lost three under `tests/log/`); the temporary index starts as
  a copy of the real one (`git rev-parse --git-path index`), with skip-worktree / assume-unchanged entries refreshed
  and split indexes handled. Snapshot time then follows the tracked file count, not the change size: purdex 1.5 s →
  0.25 s, aigora-v2 0.9 s → 0.2 s.
- `started_at` (queue schema 9, MD-5; optional, left out while null): when `start` moved the job to `running`, on the origin's clock.
  `claim.since` to `started_at` is the time the worker spent preparing (workspace, dependencies), `started_at` to the end is the time the
  command ran (both are differences of the origin's clock: `start` never writes a time before `claim.since`, so the first is never negative
  even if the clock stepped back, but a step back between `start` and the end can still make the second one negative, and a reader shows
  such a difference as 0); before it a queued or claimed job shows none. Every way back to `queued` (a release, a lapsed lease) clears it, and the next
  `start` writes a new one, so it is the start of the run that is going on or was the last; an ended job keeps the last. A repeated `start`
  with the same claim is a renewal and leaves it. A fast-lane run, recorded as `running` at once, started when it was recorded. It is the
  origin's `start` that writes it, not the worker's clock, and it is not `result.started_at` (the worker's own, which only exists once the
  job has ended).
- `interruptible` and `queue_timeout_s` are the task's manifest values copied in at submission; `adhoc` marks an
  undeclared command (§8.3). The origin never re-reads the manifest.
- `git_dir` (submission only, WWD-3b-1b): the repo's common git directory as an absolute path
  (`git rev-parse --path-format=absolute --git-common-dir`), not the working tree — a member's worktree may be removed
  before the job runs, the common directory holds the snapshot's objects. At submit the origin checks that it is a git
  directory holding `snapshot.commit` (else the submission is refused, `pdx test` exit 4). It is queue-private: never
  in a job, a listing, an event or any answer to a peer. Ad-hoc jobs carry it too.
- **Pin**: on submit the origin first records the pin in its own `git_pins` table (job id, git directory, time), then
  pins the snapshot with `refs/wwd/<job id>` in that git directory, so `gc` cannot drop it; the ref is removed when the
  job reaches a terminal state. The retention sweep only releases pins this queue recorded (job gone or terminal, after
  a 10-minute grace; a git directory that no longer exists just drops the record). It never lists `refs/wwd/` and
  deletes what it does not know: two wwd databases (two dev instances, a rebuilt database) may share one repo
  (WWD-3b-2b, schema v2). Pins left behind when `wwd.db` itself is lost are accepted; they cost only object space.
  Every git call runs through the exec helper with the clean environment of `internal/gitenv` (every inherited `GIT_*`
  removed except the three that name configuration files).
- `locks` are mutual-exclusion keys **on the host that runs the job**: one host never runs two jobs, from any origin
  or the local fast lane, that share a key; jobs on different hosts never conflict. The worker enforces them (§5); the
  origin stores and lists them and does not check them at claim.
- `result.reason` (free text, empty on success) uses these words when they apply: `lost` (two lapsed leases),
  `oom`, `timeout`, `infra` (§5.1), `superseded_by:<id>`.

### 4.2 States and transitions

`queued → claimed → running → succeeded | failed | cancelled | superseded | expired`, plus `running → queued` (release).

| Transition | Who | Wire |
|---|---|---|
| queued → claimed | a worker | `claim` (one SQLite transaction on the origin; first wins) |
| claimed → running | the worker, once the workspace is ready and right before the command starts (the origin writes `started_at`) | `start` |
| claimed/running → queued | the worker: owner reclaim (attempt not counted) or infrastructure failure (attempt counted, host held 5 min for the repo); `started_at` is cleared | `release` |
| claimed/running → queued or failed | the origin: lease lapsed (attempt + 1; after 2 lapses `failed`, reason `lost`); `started_at` is cleared when it goes back to `queued` | — |
| running → succeeded / failed / cancelled / superseded | the worker | `result` |
| queued → superseded / cancelled / expired | the origin | — |

- **Counting** (10-18, 3b-3a): `attempts` counts every release for infrastructure and every lapse; the `lost` limit
  counts lapses only. Infrastructure releases have no limit of their own: the job ends by `queue_timeout` expiry, and
  each one holds that host off the repo for 5 min.
- **Lease end** (10-18, 3b-3a): a lease ends when the origin's sweep lapses it, not at the deadline itself. Between the
  deadline and the sweep the holder's `heartbeat` or `result` is still taken; one `BEGIN IMMEDIATE` serialises them with
  the sweep, and after the sweep the old `claim_id` no longer passes, so two executions never overlap. The worker stops
  by its own monotonic deadline (WWD-4a). A job with `cancel_requested`, or one superseded, ends as `cancelled` /
  `superseded` on release or lapse and is never requeued. A wwd process opens one queue; opening it grants the restart
  grace.
- **Claim token**: a successful claim returns a fresh random `claim_id` (128 bit). `start`, `heartbeat`, `release`,
  `result`, `log` and `snapshot` must present it; the origin compares it in the same transaction that changes the job.
  A request with a stale or unknown `claim_id` gets `409` and changes nothing — an old execution can never heartbeat,
  upload a log or post a result after its lease was given to someone else. The `claim_id` is never listed in
  `GET /v1/jobs`.
- **Leases are relative**: the claim and each heartbeat answer `{lease_s, renew_s}` (initially 60 s and 15 s). The
  origin keeps the deadline on its own clock; the worker keeps its own deadline on its monotonic clock from the moment
  it received the answer. No absolute time is compared across hosts.
- **Change order** (10-18, #3293): every change of a job's state, result, cancel request, `superseded_by`, log or claim
  advances the origin's own counter (`rev`, one per committed change; a heartbeat that only moves the deadline does not).
  Readers order and resume by that counter, never by time fields, which are information only.
- **Worker that cannot renew**: when its monotonic deadline passes without a successful renewal, the worker ends the
  command (TERM, KILL 10 s later), discards the outcome and cleans up — the origin will have requeued the job.
- **Origin restart**: on start the origin gives every `claimed` / `running` job a fresh full lease before it expires
  anything, so workers that kept running while it was down can renew.
- **Result delivery**: if the origin is unreachable when the job ends, the worker keeps the result and log and retries
  with backoff for up to 10 minutes while still renewing; `result` is idempotent per `claim_id` (a repeat returns the
  first answer). If the lease is lost meanwhile, the result is discarded.
- **Cancel and supersede**: the origin marks a running job `cancel_requested`; the next heartbeat answers
  `cancel: true`; the worker ends the command and posts `result` with `cancelled` (or `superseded`). A newer job with
  the same `supersede_key` supersedes a queued older one at once, and a running one only if the task is
  `interruptible`; a non-interruptible older job runs to its end and its result is kept with `superseded_by` set.
  **As built** (C2 pre-check, 10-19): a running interruptible job that is superseded ends `cancelled` — the worker only ever
  posts `cancelled` for a cancel request — with `result.reason` `superseded_by:<id>` and `result.superseded_by` set by the
  origin. `superseded` is the state of a job that was still queued (or was let go by a lapse or a release) when the newer one
  came.
- `expired`: queued longer than the task's `queue_timeout` (default 2 h); the submitter is told, nothing ran.
- Jobs and results are kept 7 days; logs 3 days (the host that ran the job uploads the log with the result).

### 4.3 Cross-host calls (all with the pool token over TCP)

- `POST /v1/jobs/{id}/claim` `{worker, labels, fingerprint}` → `200 {job, claim_id, lease_s, renew_s}` or `409 {state}`.
- `POST /v1/jobs/{id}/start` `{claim_id}` → `200 {lease_s, renew_s}` / `409`.
- `POST /v1/jobs/{id}/heartbeat` `{claim_id}` → `200 {lease_s, renew_s, cancel}` / `409` (stop).
- `POST /v1/jobs/{id}/release` `{claim_id, reason: "reclaim" | "infra", detail}` → `200` / `409`.
- `POST /v1/jobs/{id}/result` `{claim_id, state, exit, summary, started_at, finished_at}` → `200` (idempotent) / `409`;
  `PUT /v1/jobs/{id}/log?claim_id=…` (the log body).
- `GET /v1/jobs/{id}/snapshot?claim_id=…&format=bundle&have=<sha>` → a git bundle of `have..commit`; `format=tar` →
  `git archive` of the commit. Served only for a live `claim_id`. **M-S1**: a worker with a clone of the repo asks for
  `bundle` with `have` = the newest commit it holds of the job's `snapshot.base` line (a bundle is 3–190 KB and fetches
  in about 0.3 s; a stale base costs about 2.3 KB per commit, so the clone needs only an occasional `git fetch`, no
  sync scheme). **A base the clone does not have yet** (pushed after the clone's last fetch: `manifest_ref` fetches every 10 minutes, a
  release gate runs seconds after its push) is not a reason for the tar (#3730): the worker first fetches the clone once
  (`fetch --quiet --no-tags -- origin`, once, at most 30 s) and looks again; only a clone that still lacks the base (never pushed, or a
  remote that does not answer) falls back to the tar. What counts is the base being in the clone, not the fetch's own answer: git stores
  the objects before it updates the refs, so a fetch that fails at a ref (another fetch holds a ref lock, or a branch name clashes with
  a directory of branches) has still brought the commits in, and the job neither waits for the lock nor retries. So the same task has a workspace of the same
  shape — a worktree, with a `.git` — whatever minute it started in (#3729: a tar has no `.git`, and a test that asked git for the
  commit failed in that window); a host without a clone (mserv, a cold host) asks for `tar` (purdex 70 MB, 25 MB gzip −1, about 1 s on
  the tailnet links measured at 60–80 MB/s). Workers keep HTTP connections to peers alive (a new connection cost
  0.2 s per call in X2a's ssh path).
- `started_at` / `finished_at` in a result are informational (the worker's clock); the origin records its own receive
  times for ordering and metrics.

### 4.4 Submission and reads

- `POST /v1/jobs` — **only on the local socket** (a job is always submitted on its own host); returns `{id}`, or
  `{id, result}` at once on a cache hit.
- `POST /v1/jobs/{id}/position` `{position: front|back|hold|normal}` — **only on the local socket**, no `?host=`
  forwarding (§4.6 "Manual order"; `pdx jobs move <id> front|back|hold|normal`): the manual place of a *queued* job,
  returned as the job (`409 {state}` for any other state). A job carries `manual` (`""`, `front`, `back`, `hold`) and
  `manual_seq` (smallest first within a kind: a later `front` gets a smaller one than the fronts before it, a later `back`
  a larger one). `hold` is not handed out (a claim of it gets `409 {state: "queued"}`); `front` goes before every scored
  job, `back` after every scored job; a change moves `rev` and is announced like any change to a job. Peers read both
  fields with the job.
- `GET /v1/jobs?state=queued` (peers, with the token) → the queued jobs with what a worker needs to choose. Ad-hoc jobs
  are never listed to peers and a peer's claim of one gets `409` (§8.3, §11). `GET /v1/jobs/{id}`, `GET /v1/jobs/{id}/log`, `POST /v1/jobs/{id}/cancel`,
  `GET /v1/jobs?submitter.session=…` (the App and `pdx jobs`).
- **Resuming** (10-18, #3251 / #3293): `GET /v1/jobs?after=<cursor>` (with the same filters, and `limit`) answers
  `{jobs, cursor}`: each job changed after that point once, in its latest state, in change order; `cursor` is where to
  ask from next. Without `after` it reads from the start (`0`). An empty `cursor` in an answer is not a checkpoint: keep
  the previous one. A log uploaded after a job ended makes it come back once more, so a reader that notifies
  deduplicates by job id and terminal state (WWD-3f: one notice per job).
- **Database epoch** (10-18, #3309): every list answer carries `epoch`, a random id made with the queue's tables and
  never changed after; a reader keeps it with its cursor. A cursor past this database's last change gets `409
  {reason: "cursor_ahead", head, epoch}` (the `wwd.db` was made again): start again from `0` under the new epoch.
- **The route surface** (10-18, #3301): submission `POST /v1/jobs` exists only on the local socket (the TCP surface has
  no such route; a socket with no queue wired answers `501`). Reads and `POST /v1/jobs/{id}/cancel` are on both; a
  peer's view leaves ad-hoc and fast-lane jobs out (`404`). Cancel ends a queued job at once and asks a held one to
  stop at its next heartbeat; the answer is the job as it is then, and a job that has already ended is `409 {state}`.
  `GET /v1/jobs/{id}/log` answers `text/plain; charset=utf-8` with `X-Content-Type-Options: nosniff`; forwarded through
  `?host=` it streams (up to 64 MiB, a total limit of 2 min, `Content-Length` required, a short read aborts the
  connection).

### 4.5 Result reuse

- Key: snapshot tree + task + args + the task definition hash (its `run`, `cwd`, `env`, `args` kind, `summary` after
  parsing the manifest) + `os` + `arch` + the full toolchain fingerprint of the host that ran it (OS version and every
  tool version the task's labels name) + that host's qualification fingerprint for the task.
- Lookup (WWD-5d): a submission is answered from an entry when (1) snapshot tree, task, args and definition hash are
  equal; (2) the labels of the host that produced it (`result.host`) include the job's `labels`, so a job that names
  `os:linux` never takes a darwin result; (3) that host is still valid for the task — it holds the earned label with
  the fingerprint the entry was made with, or it is the task's reference host with an unchanged fingerprint; (4) an
  entry whose host meets neither is answered only to a submission from that same host. A member's result on a
  qualified mserv therefore answers the lead's re-verification on mlab.
- Entries are kept 3 days (the log retention, §4.2) and at most 10,000 (oldest first out); an entry never outlives
  the job and log it points at.
- Only `succeeded` results of tasks marked `cacheable` are reused; failed, cancelled, superseded, expired and
  infrastructure outcomes never are. A drift that revokes a label invalidates the reuse entries made with it. A hit returns the stored result with `cache_hit: true`. This removes the
  member-then-lead re-verification by hand, and codex re-running what Claude just ran (watcher 10-18: 72% identical).

### 4.6 Ordering and fairness (our product rule; no CI system defines one)

A worker scores every claimable job it can see:

`score = 1000·class + wait_minutes + origin_bonus + warm_bonus − size_penalty − same_session_penalty`

- `origin_bonus`: +200 when the origin's zone is `warning`, +400 at `danger` (offload where it hurts).
- `warm_bonus`: +50 when the repo clone and the dependency cache for the job's lockfile are already on this host.
- `size_penalty`: this host's speed factor × the task's estimated minutes (mserv is slow: it prefers small jobs).
- `same_session_penalty`: −30 per earlier queued job of the same submitter session.
- Ties by `created_at`. The weights are initial values, tuned from job records after WWD-4.
- **Manual order** (user, 10-18): a person or the watcher can move a queued job to the front or the back, hold it and
  let it go again, as `pdx gate queue front|back|hold|normal` does today; a manual position overrides the score. wwd
  keeps this; the App's controls are designed in WWD-7b.

## 5. Worker

- **Loop**: every 2 s, or on a peer's `job` event: if `headroom` allows, read all peers' queued jobs, keep those whose
  labels ⊆ this host's labels and whose locks are free, score, claim the best; on `409` try the next. After the workspace is ready the worker calls `start`; it renews per
  `renew_s` until it posts the result or releases.
- **Locks** (§4.1): "free" means no job claimed or running on this host (from any origin) and no local fast-lane run
  holds any of the job's keys. Check, claim and record happen under one local mutex, so two claims on one host never
  pass each other.
- **Job marker**: every process a job starts carries `WWD_JOB=<job id>` and `WWD_ORIGIN=<origin tag>` in its environment and runs
  under the work root; facts (`procs[].owner`, the air26 owner rule) and the worker use one shared check for "this is a wwd job"
  (`facts.MarkFromEnv`). A job id is only unique within the origin that made it, so the mark of a job is **both**: the tag is
  `OriginTag(source)`, the first 16 hex characters of sha256 of the worker's own name for the connection the job came in on
  (`cand.Source`, never the job's `Origin` field, which a peer fills in; worker/ident). `WWD_JOB` keeps its value (the id), so
  readers that look at it alone (Purdex's attribution, the matrix probes) are unchanged, and `facts` still shows `{kind: job, id}`:
  the tag lives in the process environment and in the worker, not on the wire. **Pairing rule** (the sweep, the usage sampler): a
  process belongs to the job (tag, id) when its `WWD_JOB` is the id and its `WWD_ORIGIN` is the tag; a process with **no valid**
  `WWD_ORIGIN` (a command an older wwd started and that outlived the upgrade) is paired with any tag **during the transition only**
  (#3465: removed in the release after, once no such process can exist).
- **Capacity**: config slots (heavy / light) × headroom (§3.2). The local fast lane (§5.2) uses the same slots.
- **Workspace**: a fresh directory per job under the work root, from the snapshot (`git worktree add --detach` on a
  local clone when present, else the tar); dependencies from a cache keyed by the lockfile hash (APFS clone on macOS);
  per-job tsc build info; removed after the result is sent; a sweep removes leftovers older than 1 h.
  **Dependency cache (#3620; `docs/wwd-deploy.md` §10)**: a task that declares `deps` gets `node_modules` / `vendor` before its command; a
  key with no entry is installed once, in that job's workspace, under the job's own sandbox, QoS and environment (the install needs the
  network), and filed; a pnpm workspace's members' `node_modules` are kept with the root's. The key is the lockfile's content, the install
  command, the tool versions, the platform and the task's fixed `env`, **and an enumerated list of the files an install reads**: next to each
  lockfile `package.json`, `.npmrc`, `.pnpmfile.cjs`, `.yarnrc(.yml)`, `pnpm-workspace.yaml`, `composer.json`, and each pnpm member's
  `package.json`. **Limit (lead, 10-20)**: that is a list, not a derivation. A file those name and the workspace holds (a `yarnPath` or a
  plugin, a script of `composer.json` that runs a file of the workspace) is not followed, so two snapshots that differ only there share an
  installed set. It is accepted because the repos are the user's own (§11), the tasks in use are pnpm, and the result cache's key holds the
  whole snapshot tree, so a stale installed set can change the environment a command runs in but cannot make another tree's result be
  reused. An install may write only its package manager's own download cache (bounded, `worker.deps_store_max_mb`), never the installed
  sets; the same key failing twice in a row on a host ends the next job of it (`deps_install_failed`, no exit, counted by no outcome and no
  qualification).
- **Environment**: starts empty; only the manifest's `env` allow list and fixed values; `HOME`, `TMPDIR` and
  `XDG_*` point into the workspace; `PDX_*` state directories point into the workspace; tests use `tmux -L`.
  `[tools] extra_path` (absolute or `~/` directories; a missing one is skipped and logged) goes in front of the default tool directories. The facts' tool probe and a job's PATH come from the same list, so a tool the facts report is a tool a job finds; a change takes effect when wwd restarts. This is the PATH of a worker job: a fast-lane run (§5.2) keeps its caller's environment and PATH, and the PHP probe also looks in Herd's directory, which is not on a job's PATH.
- **Platform limits**: macOS — a process group, `dev` jobs on mlab under background QoS so interactive sessions keep the
  P cores. Linux (**M-L2**, all measured on mserv) — a transient **service**, never `--scope` (a scope rejects the
  sandbox properties):

  ```
  sudo systemd-run --wait --pipe --uid=wake --unit=wwd-<origin tag>-<job id> --slice=wwd.slice \
    -p CPUQuota=200% -p MemoryMax=4G -p MemorySwapMax=0 -p RuntimeMaxSec=<timeout + 60> -p TimeoutStopSec=10 \
    -p PrivateTmp=yes -p ProtectHome=read-only -p ProtectSystem=strict -p ReadWritePaths=<workspace> -p WorkingDirectory=<workspace> \
    -p NoNewPrivileges=yes -p InaccessiblePaths=-/run/docker.sock \
    env -i <the job's environment: HOME, TMPDIR, XDG_* in the workspace, WWD_JOB=<job id>, as in Environment above> \
      nice -n 10 ionice -c3 sh -c '<wrapper>' <status file> <command>
  ```

  - Always `--unit=`: an unnamed unit that fails stays as `run-p….service`, and mserv's booter checker alerts the user
    on failed units. No `--quiet` and no `--collect`, so the unit's `Result` can be read; after reading it the worker
    runs `systemctl reset-failed wwd-<origin tag>-<job id>`. The unit is named for the origin because a job id is only unique within
    the origin that made it (#3373): `<origin tag>` is the first 16 hex characters of the SHA-256 of the connection's name (the local
    alias, or a peer's), safe in a unit name where an alias is not. A quarantine marker written before the tag existed names `wwd-<job
    id>` and keeps working: it is asked about by the name it stores, and the quarantine accepts both forms.
  - Slice names contain no `-` (a `-` makes a hierarchy: `wwd-x.slice` lives under `wwd.slice`).
  - wwd itself (10-18, #3275) runs in `wwdd.slice` (`CPUQuota=100%`, `MemoryMax=512M`, `TasksMax=256`), apart from both
    `system.slice` (the production services) and its jobs' `wwd.slice`. The service sets no `NoNewPrivileges`: its jobs
    start through `sudo systemd-run`, which that flag would refuse; the privilege boundary is sudoers (§12). wwd's own process is a
    slice of its own, `wwdd.slice` (its unit: `Slice=wwdd.slice`, `CPUQuota=100%`, `MemoryMax=512M`, `TasksMax=256`),
    apart from the jobs' `wwd.slice` and out of `system.slice`, where the production services live.
  - `MemoryMax` without `MemoryHigh`: with Max alone an over-limit job is OOM-killed in 0.1 s; `MemoryHigh` only
    throttles, and a throttled job stalls until its fuse (measured 30 s). `RuntimeMaxSec` is the reliable fuse.
  - `ProtectSystem=strict` (added after WWD-4d-3 measured it on mserv, 2026-10-18): the whole file system is read-only but the
    workspace and the private `/tmp` and `/var/tmp` (`PrivateTmp` covers both). Without it `wake` could write to `/srv/backups` (real
    backup data), `/srv/stacks`, `/var/crash` and `/var/log/installer`; with it those writes are refused, and composer and phpunit
    ran the same (`docs/wwd-4d3-mserv.md`).
  - In the sandbox `HOME` is inside the workspace (Environment above), only the workspace is writable, `/tmp` is private, `sudo` is blocked, stdout and
    stderr arrive separately, exit codes pass through, and at-inwin's PHP suite gives the same result as outside
    (69 s, tests 6324 F27 E94). A task that runs composer needs its cache in `ReadWritePaths`.
  - A per-job MySQL database on mserv for tasks with `db = "per-job"`: `internal/wwd/jobdb` makes a database `wwd_<hash of the job id>` and a user `wwdu_<hash>` that holds
    privileges on that database alone (random password, given to the job as `DB_*` entries), drops both after the result is sent,
    and a sweep at start drops those no live job owns. The administrator is the mysql client's defaults file named in the worker's
    config (no password on a command line).
- **Timeout and cancel**: macOS — TERM to the group, KILL 10 s later. Linux — `systemctl stop wwd-<job id>`: killing the
  `systemd-run` client (INT, TERM or HUP) leaves the service running. **Outcome on Linux** comes from
  `systemctl show wwd-<origin tag>-<job id> -p Result,ExecMainStatus,ExecMainCode`, not from `systemd-run`'s exit code (OOM and
  timeout both exit 1; a stop exits 0 and looks like success): `exit-code` → the command's code; `oom-kill` → failed,
  reason `oom`; `timeout` → failed, reason `timeout`; stopped by the worker → `cancelled` / `superseded` (the worker
  records that it stopped it). **The status file** (measured on mserv, WWD-4d-3): a unit that ended well is unloaded by systemd
  at once, so its Result is gone and `systemd-run`'s exit 0 cannot stand for it (a unit stopped from outside also leaves 0). The
  command therefore runs under a one-line `sh` wrapper that writes its exit status to a per-run file in the workspace
  (`.wwd-exit.<random>`, removed after the run) and exits 125 if it cannot write it. Unit gone, `systemd-run` exit 0 and the file
  says N → the command exited N; unit gone and no file → stopped from outside (`cancelled` with an error: an infrastructure
  failure for the caller); `systemd-run` non-zero and no unit → nothing was started. A failed unit stays loaded and its Result is
  read as above, with one rule: `exit-code` **125 or 200..243 with no status file** is an infrastructure failure (systemd's own
  set-up failures are 200..243, e.g. 226 for a `ReadWritePaths` entry that does not exist, 203 for a missing program; 125 is the
  wrapper's), released with `infra` like §5.1 and not counted as a red test; with the file the same numbers are the command's.
  A `ReadWritePaths` entry that does not exist is refused before anything starts. The file separates a finished job from a stopped
  unit; it is not a boundary against the task itself (§11). **Owner reclaim** (air26): stop claiming, end running jobs, `release` them with
  `reason: "reclaim"` (back to `queued`, no attempt counted).
- **Marker sweep** (macOS, WWD-3d-2b): after the group is gone — on success, failure, cancel or timeout alike — the
  worker reads the process table (the facts reader, no fork) and ends every process whose environment carries
  `WWD_JOB=<this job>` and the job's `WWD_ORIGIN` (the pairing rule of the job marker above; TERM, KILL 10 s later). Test suites start daemons that leave the group with `setsid` (tmux
  `-L` servers, vite, playwright); without the sweep they outlive a cancelled job and become load. The count is
  recorded with the result so a task that leaks shows up. This is cleanup, not a boundary: a process that clears its
  own environment escapes it, which is accepted for declared tasks (D9).
- **Quarantine** (`internal/wwd/worker/quarantine`): when the sandbox cannot prove the unit stopped (`run.Result.Err`), the runner
  keeps the workspace and the lock hold, and the worker records an entry (owner, job, origin, claim, directory, keys, unit,
  since) in a marker file `<hash of owner>.json` (0600, written through a temp file, fsync and rename, so a crash leaves no half
  file). **After a restart** `Restore` takes the hold of every entry again, so a start with one of its keys is refused until the
  entry is cleared; a key another owner already holds is returned as an error to the caller (call `Restore` before anything else can take a lock), the marker stays, and every `Sweep` tries to take the hold again. **Release** is by proof only: `Sweep` asks
  the unit checker (Linux: `systemctl show -p ActiveState` is `inactive`, `failed`, or the unit is not loaded) and, when it
  answers "gone", removes the directory, the marker and the hold, in that order. An unreadable answer, an entry without a unit
  (macOS has no sandbox) or an unconfigured work root keeps everything; only `Clear` (a human) releases an entry without
  proof. The directory is removed only if it is a clean absolute path, a direct child of the work root and not a symlink;
  a work root that is not a real path (a symlink), a marker that is not a regular file, whose file name does not match its owner, whose unit is not `wwd-<job id>`, or that does not parse, is logged and ignored, never obeyed; `Sweep` and `Clear` act only on the entry generation they looked at, so an `Add` of the same owner in between is not undone. The
  leftover sweep above skips directories `Quarantined(dir)` reports.
  **The marker is written before the command starts** (sandboxed hosts, `Store.Begin` through the runner's `Guard`, right before
  `Exec.Run`), not after it ends: a daemon that is killed while the unit runs would otherwise leave nothing that gives the job's
  keys and workspace to the next process (a killed `systemd-run` client leaves the service running). While the run goes on the
  entry is *live*: `Sweep` leaves it alone (the unit may not exist yet, and "no unit" would read as "gone"), and the hold is the
  runner's. When the command has ended and its unit is proven gone the marker is dropped (`Discard`: the marker and the entry only;
  the hold and the directory are the runner's and the executor's); when it is not, the run is quarantined: the guard settles the
  entry at once (`Settle`: memory only, the marker has been on disk since `Begin`, so it cannot fail and a sweep can clear the
  entry whatever happens to the delivery), and the delivery goes on (the marker is already durable, so nothing is written again: a write after a
  sweep that had cleared the entry would bring it back without its hold). A host that has no guard writes the marker when the run has
  ended (`Add`), before anything is delivered and retrying until it is written, because the delivery of a quarantined job is a release
  that lets another worker run it. A marker written by another process is never live: after a restart `Restore` and `Sweep` treat
  a job that was running as any quarantined one — its keys come back, and `Sweep` clears it once its unit is gone. If `Begin`
  fails the command is not started and the job goes back as an infrastructure failure. A host without sandbox units has no guard
  (a marker nothing could clear would hold its keys for good) and does not write pre-run markers.
  **The entry's states** are `none`, `running` (Begin; the hold is the runner's) and `quarantined` (Settle, Add, or a marker loaded
  after a restart; the store holds the keys). Operations and what each does in each state — one lock, one place for removal, anything
  not listed is refused and changes nothing:

  | operation | none | running | quarantined |
  |---|---|---|---|
  | `Begin` | → running (refused unless the owner holds exactly the keys) | refused (exists) | refused (exists) |
  | `Add` | refused (no hold — a marker needs its hold; allowed once the owner holds exactly the keys, as on a host with no guard) | → quarantined | → quarantined (marker rewritten) |
  | `Settle` | – | → quarantined (memory only) | – |
  | `Discard` | – | → none (marker and entry; never hold or directory) | refused (not running) |
  | `Sweep`, unit gone | – | skipped, the unit is not asked | → none (marker, entry, hold; then the directory) |
  | `Sweep`, otherwise | – | skipped | unchanged |
  | `Clear` | refused (no entry) | refused (running) | → none (marker, entry, hold; then the directory if safe) |
  | `Restore` | – | skipped | hold taken again (an error if another owner holds a key) |

  Invariants: an entry has its marker on disk; a retired entry is not brought back by an operation that saw it earlier (every
  operation acts on the entry's generation it saw); a running entry is never swept, cleared or asked about; a hold is released only by
  proof (Sweep) or by a human (Clear). The table is the package doc of `quarantine` and is tested cell by cell, and every operation is
  also run in each outside-the-lock stretch of every other (the invariants are checked after each pair).
  **How an operation is made**: `Add`, `Begin`, `Settle` and `Discard` are done whole under the store lock (the marker file is written
  and fsynced there too, so there is no stretch outside the lock to slip into). `Sweep`, `Clear` and `Restore` take a snapshot of the
  entry without the lock (`Sweep` asks the unit checker, a systemctl call, in that stretch); under the lock the entry is looked at again
  (same generation, a state the table allows) and only then are the entry, the hold in the lock table and the marker changed —
  otherwise the whole operation is given up. Every transition, Settle included, gives the entry a new generation. The job directory is
  removed after the commit, for the entry this commit removed; if that fails the error is logged and the leftover sweep takes it.
  Lock order is the store lock, then the lock table, never the other way.
- **Summary**: parsed from the task's report (`go-json`: `go test -json`; `vitest-json`: the JSON reporter; `junit`:
  phpunit / jest junit; `plain`: the last 40 lines). Shape: `{passed, failed, skipped, failures: [{name, file, message}],
  tail: [lines]}`. The agent reads the summary, the full log only when needed.

### 5.1 Infrastructure failures

Snapshot fetch, workspace or dependency setup failing is not the command's result: the worker calls `release` with
`reason: "infra"` (the job returns to `queued`, attempt counted), this host is held off for that repo for 5 min, the
reason is recorded. If the origin cannot be reached for `release`, the lease simply lapses. A red test is red: the result is never re-run
elsewhere to get another answer.

**The origin's own failure is not this host's (#3379).** When the origin *answers* the snapshot request with an error that is its own
(a 5xx such as "the commit of this job is not pinned", a status the client cannot act on, `503` still busy after the retries), the worker
calls `release` with `reason: "reclaim"` (the attempt is not counted) and a `detail` that names it: `origin snapshot <status>: <the first
200 characters of the body>` (or `origin snapshot busy`). The repo is **not** held off. Instead that one job is not picked again by this
worker for 15 s, doubling with every failure of the same job in a row up to 5 min (in memory; a restart begins again at 15 s), and the
worker's log carries the same words, because the origin's queue does not keep the `detail`. A failure that is this host's own (unpacking,
disk, git) and a connection that could not be made or broke stay `infra` with the 5 min hold-off: whose network that is cannot be told.
A job the origin keeps refusing stays `queued` and ends as `expired` when its `queue_timeout` runs out (default 2 h); the reason is in the
workers' logs, not in the job.

### 5.2 Local fast lane

When the task allows it (`local`), the submitter is on this host and `headroom` allows, `pdx test` runs the command in
the caller's own working tree at once (no snapshot), holding a local slot (today's gate light-slot code), and records a
job with the result. Single-file tests always take this lane and never leave the host (D12).

- **Never queued** (10-18, D12 / #3255): a task that takes this lane is never handed to `Submit`. When the lock table
  answers `LocksBusy`, `pdx test` waits on this host: it asks again every 2 s and prints one line naming the keys. The
  lock wait and the slot wait share one deadline, the task's `queue_timeout`; the gate waits only for what is left of
  it. Past the deadline the run ends with exit `6` (expired); the caller leaving ends it with `130`. `--detach` on
  such a task is refused with exit `4`. With wwd not running the command still runs here, unrecorded.
- **Expired is a signal, not a guess** (#3260): the gate reports "waited until `WaitMax`" explicitly and the fast lane
  maps only that to expired; any other gate refusal is an infrastructure failure, however long it took.
- **Recording** (10-18, WWD-3b-1b / 3e): `POST /v1/local-runs` (socket only) with a `LocalRunRequest` (a
  `JobSubmission` plus `git_dir`) first checks this host's **lock table**, then has the queue record a job with
  `local: true` directly in `running`, and answers `{id, claim_id, lease_s, renew_s}`; a lock conflict answers `409`
  with `LocksBusy` naming the keys and their holders. Heartbeat, result and log use the ordinary `claim_id` routes.
- A local job runs in the caller's working tree: no snapshot is taken (the record names HEAD for reference only, the
  tree may be dirty), the manifest is read from the tree, local-only tasks (`args = "pass"`) are allowed, and it is
  never read from or written to the result cache. Peers never see it (not listed, a claim gets `409`, its events are
  dropped on the peer side). When its lease lapses it is `failed` with reason `lost`, never requeued.
- **Lock table** (`internal/wwd/worker/locks`, WWD-3e-1): one per host, inside wwd; check, hold and record happen
  under one mutex; a hold is bound to its owner and generation, so releasing an old attempt never frees a newer one.
  Local runs hold their keys there now; WWD-4a registers cross-host claims in the same table.
- **Slots** (10-20, ed3920-60): the fast lane's slot is wwd's own, taken at the same `POST /v1/local-runs` that checks the
  locks: a declared task takes a **light** slot, an adhoc command a **heavy** one (shared with queue jobs). No room
  answers `429` with `SlotBusy` (`slot`, `reasons`); the caller asks again every 2 s, like for `LocksBusy`, under the same
  deadline. Light is stopped by zone `danger` and by its slots; heavy by any zone but normal, its slots, a hold and
  `gate_full`, `disk_low` (heavy only). The owner at the keyboard and the worker being off do not stop either (the owner asked for the run).
  `facts.worker.running` is the live count: queue jobs (heavy) plus the fast lane's runs by their slot. The admission
  reads memory only (the latest record, the gate's last reading) and is not first-come-first-served: a caller that polls
  can lose to another that polls just before the slot frees.
  The command is run by `fastlane.Direct`, with no gate slot: its own process group (the caller's, at a terminal), SIGTERM
  then SIGKILL when the caller ends, and what is left is ended at the end — the group, then whatever still carries the run's
  `WWD_JOB` mark (a server after `setsid`). A run that is not recorded has no mark, so at a terminal (no group of its own: a
  background group would be stopped by SIGTTIN) only the terminal's own signals reach its tree, and a TERM sent to `pdx test`
  from elsewhere leaves its grandchildren; no job id is made up for it (the usage tracker would take it for a real job).
  **Without a slot from wwd there is no limit**: wwd not running, or an older wwd without the route (the CLI is upgraded first),
  runs the command unrecorded and unbounded, as the gate no longer bounds it. That is accepted (no dual track with the gate,
  10-20); a deploy upgrades the daemon with the CLI.
- **A fast-lane run belongs to its caller** (10-18, WWD-3c-2b): ending `pdx test` (Ctrl-C, TERM) ends the command,
  the run is recorded `cancelled` and `pdx test` exits 130. D5 ("a job outlives its caller") is about queued jobs;
  work that must outlive the caller goes through the queue. When `pdx test` dies without cleaning up (SIGKILL, a tool
  timeout), the run's lease lapses, the job ends `failed` / `lost`, and wwd ends whatever still carries its
  `WWD_JOB` marker (the §5 marker sweep).

## 6. Task manifest — `.wwd/tasks.toml`

```toml
[entry]
mode = "rewrite"            # advise | rewrite | deny — what the hook does with an undeclared test/build command

[tasks.spa-file]
run     = "pnpm vitest run --reporter=json --outputFile={report} {files}"
cwd     = "spa"
args    = "files"           # files | packages | none | pass (pass: local-only tasks)
local   = true              # true | false | "files<=N" | "packages<=N"
summary = "vitest-json"

[tasks.spa-related]
run       = "pnpm vitest related --run --reporter=json --outputFile={report} {files}"
cwd       = "spa"
args      = "files"
class     = "merge"
labels    = ["os:darwin", "repo:purdex"]
deps      = ["pnpm-lock.yaml"]
cacheable = true
timeout   = "30m"
summary   = "vitest-json"
qualify   = { args = ["src/lib/fleet/parse.test.ts"], reference = "air26" }
```

- **No shell** (10-18, after three review rounds each found a new way through quote scanning): `run` is split into argv
  when the manifest is parsed — whitespace separates words, single or double quotes only group literal text, nothing is
  expanded — and the worker execs that argv directly (the exec helper, never `sh -c`). `$`, backticks, `*` or `~` in a
  word are literal characters. An unquoted shell operator (`|`, `&&`, `;`, `<`, `>`, `$(`, a backtick) is a manifest
  error that says to call a script in the repo instead; this is a clear message for authors, not the security boundary.
- Placeholders: `{files}` (paths relative to `cwd`, validated to exist in the snapshot, no `..`, never starting with
  `-` so a file name cannot become an option), `{packages}` (Go package patterns, allow-listed form), `{report}` /
  `{junit}` (output files inside the workspace). The multi-value `{files}` / `{packages}` must be a whole word and
  expand to one argv element per value; the single-value `{report}` / `{junit}` may sit inside a word
  (`--outputFile={report}`) and are replaced in place.
- Fields: `run`, `cwd`, `args`, `local`, `class` (default `dev`, the maximum a caller may ask), `labels`, `locks`,
  `deps` (lockfiles for the dependency cache key), `cacheable`, `interruptible`, `timeout`, `queue_timeout`, `env`
  (allow list and fixed values), `db` (`per-job`), `db_env` (`db`, the default, or `wptests`; only with `db`: `db` gives the job
  `DB_*`, `wptests` gives it `WP_TESTS_DB_*` and `WP_PHPUNIT__TABLE_PREFIX` for WordPress's test suite), `summary`, `qualify`.
- The test tiers become tasks: development (`spa-file`, `go-pkg`), merge (`spa-related`, the changed packages, `lint`,
  `execstat-guard` run on its own without `-run`), release (`go-all`, `spa-full`, `tsc-force`, `mod-all`).
- Manifests for purdex, aigora-v2 and at-inwin-plugin are written in WWD-3 / WWD-6.

## 7. Labels and qualification

- **Automatic labels** from facts: `os:darwin|linux`, `arch:arm64|amd64`, `tool:node24`, `tool:go1.26`, `tool:php80`,
  `tool:xcode16`, …; `repo:<name>` once the host has a prepared clone of that repo.
- **Prepared clones** (10-18, WWD-5a): there is no registry. `config.toml` has a `[repos]` table, `<repo name> =
  "<clone path>"` (empty by default). A path counts only when, at read time, it is a git repository owned by the
  wwd user (a directory it owns whose `.git` is a directory, or a file reading `gitdir: <dir>` with `<dir>` an
  existing directory — a linked worktree); otherwise that repo gets no label and nothing fails. The check is cached and redone at the facts cadence;
  a change sends a `labels` event. One function answers "name → verified clone path" for both the `repo:` label and
  the worker's `MaterializeIn.Clone` (WWD-4a), so the two never disagree.
- **Earned labels** `task:<repo>/<task>`: granted after a qualification job — the task's `qualify` args run on this host
  and on the reference host at the same snapshot, with the same pass/fail sets. The fingerprint (tool versions, OS
  version) is stored with the label.
- Every wwd advertises `host:<alias>`. It narrows who may claim a job and grants nothing. The origin does not check
  labels at claim, so a qualification pair counts only when `result.host` of each half is the host it was meant
  for; otherwise the pair is void (no label, no disagreement) and is queued again under the rate rule below.
- Qualification is queued automatically into the queue of the host that lacks the label, as `dev` class, when that
  host's worker is on, it has the task's `repo:` and `tool:` labels, the task has `qualify`, and it is not the
  reference. At most one unfinished pair per (host, task); after a mismatch or a void pair, the next automatic try
  waits for a fingerprint change or 24 h. `pdx wwd qualify <repo>/<task>` starts one by hand (the 24 h wait does not
  apply). The reference host holds the label without qualifying; its drift invalidates only its own reuse entries.
- **Drift**: a fingerprint change revokes the host's earned labels for the affected tools and queues a `dev`-class
  re-qualification.
- **Disagreement**: the same snapshot + task with different outcomes on two hosts quarantines the label on the
  non-reference host until re-qualified. The original result stands. The origin records outcomes and offers, on a
  pool read, the disagreements that concern a host; each wwd reads them and quarantines its own labels (no peer
  write route). Only outcomes recorded by the same origin are compared.
- A job's `labels` may name earned labels; a host without them never claims it.

## 8. Entry, enforcement and observation

### 8.1 CLI

- `pdx test <task> [args…] [--class dev|merge|release] [--detach] [--json]` — submit and wait; prints the summary; exit
  code = the job's exit code; `124` timeout, `130` cancelled, `3` wwd unreachable, `4` manifest or argument error, `5`
  no host can ever take it (labels), `6` expired in the queue. Waiting long is fine: the mod moves a waiting foreground
  call to the background. A completion notice (§10) is best-effort; the job's state, read with `pdx jobs show`, is the
  authority.
- `pdx test --adhoc -- <argv…>` — an undeclared command as an ad-hoc job (§8.3).
- `pdx test --list` · `pdx jobs [ls|show|log|cancel] …` · `pdx wwd [status|pool|worker on|off|exception start|stop]`.

### 8.2 Hook (successor of `hooks/gate.js`)

- Recognises a test or build tool call (go test/build/vet, vitest, jest, tsc, phpunit, pest, swift build/test,
  xcodebuild, pnpm build/test/check, make lint/test, composer test).
- Matches the repo manifest's tasks by command shape → rewrites to `pdx test <task> …`.
- No match → by `[entry].mode`: `advise` (let it run, say which task to use), `rewrite` (run it as an ad-hoc job),
  `deny` (refuse with the task to use). It no longer decides heavy versus light.

### 8.3 Ad-hoc jobs

An undeclared command run through the entry. Conservative: heavy class, local host only (an arbitrary command is never
executed on another host), recorded as `undeclared`.

- `pdx test --adhoc -- <argv…>` (10-18, #3276): the argv runs without a shell, here, in the caller's working tree,
  through the fast lane on a heavy slot. Its wire class is `dev` (the job's priority; heavy is the slot). It is recorded
  with `adhoc: true`, never queued; `--detach` is refused (exit 4); the output streams to stdout as it runs. The hook
  (§8.2, mode `rewrite`) uses it only for a single plain argv, and advises otherwise.

### 8.4 Observation

Process trees that belong to no job but use more than a threshold (CPU × duration or memory) are recorded with their
session, command and peak — codex trees included. A periodic list feeds manifest and hook rules. Nothing is blocked or
killed.

How the records are made (WWD-6c):

- **A tree** is a process and its descendants, rooted at a process whose parent is an *anchor*: a Claude Code session process, or
  part of codex's harness (the app-server broker, its npm wrapper, the `codex` binary, `codex-code-mode-host`). The harness
  itself is never a tree, residents are not (a dev server is not a command, §9), and anything a job started is that job's. A tree
  stops at another tree's root, so a command codex runs inside a shell a session started is counted once. On mlab the codex broker
  is reparented to pid 1 (broker → wrapper → `codex` → `codex-code-mode-host`), so its session comes from the session id in its
  environment (§3.1, WWD-6c-0), and a tree under it is `via: "codex"`; a tree whose session cannot be named is `session: "orphan"`.
- **Totals** are kept per 5 s sample while the tree runs: the CPU time of the whole tree (CPU share × time; the time one sample
  is charged is at most three intervals, so a sleep or a stopped wwd is not CPU), the most CPU it used at once (percent of one
  core), the most memory it held at once, and the most processes it had.
- **Recorded** when the tree ends and its CPU time reached `observe.min_cpu_seconds` (default 60) or its peak memory reached
  `observe.min_mem_mb` (default 1024); a tree still running and over a threshold is listed as live (`ended_at` null).
- **The command** is the root's command line, with secrets hidden (the value of `--token`/`--password`/`--api-key`-like flags,
  `NAME=value` with a secret-looking name, `Bearer`/`Basic` credentials, the user:password of a URL, well-known token shapes),
  control characters dropped and at most 200 characters; **the signature** is its short form ("pnpm vitest run", "go test",
  "swift build") that the undeclared list groups by. Records are kept in `wwd.db` for 14 days.

Reading them (WWD-6c-2; both surfaces, the socket also takes `?host=<alias>` and forwards like the worker routes):

- `GET /v1/observations?since=<RFC 3339>` → `{host, since, observations: [...]}`: the stored records and the live ones (a tree
  still running and over a threshold, `ended_at` null), each once, oldest first. `since` defaults to the last 24 hours.
- `GET /v1/observations/undeclared?since=<RFC 3339>` → `{host, since, groups: [...]}`: the same records grouped by signature,
  the biggest total CPU first. A group has `signature`, `count`, `cpu_seconds` (the total), `max_mem_mb`, and the latest one's
  `last_at`, `last_session`, `last_via` (`session` or `codex`) and `last_command`: whose it was, so a person knows whom to ask
  about a manifest or a hook rule. `since` defaults to the last 7 days. An empty answer is `[]`, never `null`.
- `since` never reaches back farther than the 14-day retention. One answer carries at most the newest 1000 observations, or the
  500 groups with the most CPU; when more existed, `truncated` is true, so a busy host cannot make an answer the pool's
  forwarding refuses. A truncated observations answer also carries `next_until`, the start of its oldest record: ask again with
  `until=<next_until>` (inclusive, so a record can come twice; drop repeats by `id`) to read the ones before, back to `since`.
  Send `next_until` back exactly as it came, do not re-format it: it has a fraction of a second, and cutting it to whole seconds
  would skip the records of that second that began before the boundary. The Purdex daemon passes both ways untouched (§10: `GET
  /api/pool/hosts/{alias}/observations?since=&until=` and `/undeclared?since=`, capability `pool.observations.v1`): `since` and
  `until` must be RFC 3339 (else `400 bad_request`, wwd is not asked) and go to wwd as given, and wwd's answer comes back as wwd wrote
  it, the cursor included. A
  truncated undeclared answer is narrowed with a later `since`.
- `[observe]` in `config.toml`: `min_cpu_seconds` and `min_mem_mb` (0 or unset takes the default; a negative or non-finite
  value is refused).
- A finished record whose write to `wwd.db` fails waits in memory (at most 256, the oldest dropped) and is written on the next
  sample, in order; the routes answer from memory and the store together while it waits.

### 8.5 Job usage

For every job a host runs, wwd records one row of **what it used** and **what the host was like around it**, so that a week or
two of data can later set the cost a job is admitted at and how much of air26 stays open while its owner is there. It is
**recorded only**: nothing in admission, slots, the worker or a result reads it, and a failure to write a row is logged and goes no
further (the job's result and report are never touched). It covers jobs the worker ran from the queue (here or claimed from another
host) and the local fast lane (`pdx test`), on the host that ran them.

| Group | Field | Where it comes from |
|---|---|---|
| who | `job_id`, `host`, `repo`, `task`, `slot_charged` (heavy/light), `class` (release/merge/dev), `source` (`queue`/`fast_lane`), `result` (the final state), `reason` | copied from the job |
| time | `started_at`, `ended_at` (the duration is worked out on read, from the two) | the run |
| CPU | `cpu_seconds` (user + system, the whole process tree), `cpu_source` | `rusage` (the process's rusage at exit, which includes the children it waited for; macOS), `unit` (the sandbox unit's cgroup, Linux), `sampled` (the integral of the 5 s samples: a fast-lane job's process is the caller's, not wwd's, and its exit code is all the gate returns), `none` (nothing was measured: `cpu_seconds` is null) |
| cores | `peak_cores` + `peak_cores_measure` (the average, `cpu_seconds` over the duration, is worked out on read, so a row cannot contradict itself) | the facts sampler, every 5 s: the CPU use of the job's process tree (attributed by the `WWD_JOB` mark, §3.1), highest of the samples → `sampled`; no sample (a job shorter than one, or wwd restarted before the first) → `none` |
| memory | `mem_peak_mb` + `mem_peak_measure` | macOS: the highest sum of the tree's footprints over the 5 s samples → `sampled`; Linux sandbox: the unit's `memory.peak` → `exact`; none of these → `none` |
| host | `jobs_at_start`, `jobs_peak`, `zone_at_start`, `zone_worst` | jobs running on this host (this job included) at the start and at most; the pressure zone at the start and the worst during the run |
| owner | `owner_at_start`, `owner_seen` | the owner rule (§3.1) at the start and whether it was ever active during the run; **null** on a host with no owner rule (all but air26) |
| trust | `partial` | true when the sampled figures may miss the beginning of the run: wwd was restarted while the job ran, or the job's own start time was missing and the first sample stands in for it (an `exact` figure is whole) |
| trust | `lower_bound` | true when the run left processes behind when its command returned: the exact figures (`rusage`, `unit`) are a floor |

A sampled peak is the highest of the samples, so a spike shorter than 5 s can be missed; the row says which figure is which so that
macOS and Linux rows are not mixed up in the analysis. A figure nobody could measure is **null**, never 0, and its source or
measure says `none` (and `none` only goes with null): a reader that averages or sums the column leaves the unknown ones out by
itself instead of counting them as nothing. An exact figure that could not be read (a Linux unit without the cgroup files) falls back
to the sampled one when there is one, and to null when there is not. A row with a null figure is still a row.

The exact figures are read by `run`, not by the usage hook: an unsandboxed run takes the process's rusage after `Wait` (user + system,
the children it waited for included; `run.Result.Usage`, from `rusage`; no memory figure, the process's maxrss is one process and not
the tree); a Linux sandbox unit is unloaded by systemd as soon as it ends well, so `systemctl show` cannot give `CPUUsageNSec` or
`MemoryPeak`, and the command's wrapper reads them from the unit's own cgroup (`cpu.stat` `usage_usec`, `memory.peak`) after the command
ended and before the shell exits, and leaves them with the exit code in the status file (three lines: code, microseconds, bytes; the
last two empty when unreadable). `memory.peak` counts page cache the unit touched as well as its processes' memory. The reading is made when the command returns, so a process the command left running in the unit (a daemonized helper) and what it uses after that are not in it: its figures are then a floor, and the row says so: **`lower_bound`** is true when the run left processes behind when its command
returned. A sandbox unit knows it from `cgroup.procs` (the wrapper counts the processes besides itself with its own `read`, before it
forks the helpers that read the figures, and writes the count as the status file's fourth line); an unsandboxed run knows it from a
process group that still had a member after the leader exited, or a process outside the group found by the job mark. A sampled
figure sees the leftovers while they run and is not what the flag is about. An analysis that needs whole figures leaves the
`lower_bound` rows out of the exact columns. A process that moves itself out of the unit on purpose (a `systemd-run --user --scope` of its own) is not seen: the tasks are declared tasks of our own repos and a same-user process is not defended against (§11); `false` means "nothing was seen left behind", not a proof. Reading them
never changes the exit code and never fails the run; the wrapper refuses an empty or root cgroup, so a figure is never the whole
host's.

- **Kept 30 days** in `wwd.db` (table `job_usage`, host schema 4), counted from the clock, not from the row, so a row with a
  wrong time cannot erase the history or revive what has aged out; independent of how long the queue keeps the job itself (7 days).
  A row already past the retention is not stored; one that ends more than a day in the future is refused. The same job is written
  once (a second write changes nothing). **Deploying schema 4 needs a `.backup` of `wwd.db` first** (the migration only adds a
  table and can be run again).
- **Read** on the local socket only (TCP never serves it, and a `?host=` for another host is refused: ask that host):
  `GET /v1/usage?since=<RFC 3339>&after=<job id>&limit=<1..1000>` → `{host, since, records, truncated, next_since, next_after}`;
  `since` defaults to the last day and never reaches back farther than the retention; `limit` defaults to 200. Rows are oldest first
  by end time (ties by job id). When more rows follow, `truncated` is true and `next_since` and `next_after` are the end time and the
  job id of the last row: ask again with `since=<next_since>&after=<next_after>` for the rows after it, none twice and none skipped
  however many jobs ended in the same millisecond (send `next_since` back as it came, it has a fraction of a second). A row that
  no longer decodes is left out and does not count toward `limit`. Every row is validated as in §14a.
- `pdx wwd usage [--since 6h|7d|<RFC 3339>] [--limit N] [--json]` prints a table (a `~` after a figure marks a sampled one; `partial`
  in the last column) or the whole answer as JSON.
- When the C2 fault hooks are on, the row records the real zone (`derived.zone`; the hook's override lives in
  `derived.zone_override` and is not recorded). The owner state a hook makes up (reason starts with `fault:`) is not the owner,
  so the owner figures are null for that sample. An owner first known after the job began has no "at start", so the row keeps both
  owner figures null (they are both set or both null).
- **Written** by the host that ran the job, from two places. A **job the worker ran** (from this host's queue or a peer's) is written
  when its run ends, from the run itself (the loop's `Config.Usage`, through `ForWorker`, once the origin has accepted the run's result; the
  loop reports a run only then, a rule the worker's reporter gives the loop (`Reporter.Delivery`), which lands after the recorder): the exact figures of
  `run.Result` (§8.5 above), the samples for the rest, and `lower_bound` from the run's leftover processes. Only a run that is a
  result of the job gets a row: one that is cancelled, or ends by itself, by its timeout or by an OOM; a run whose job goes back to
  the queue (released as infra or reclaim, a lease that was lost, a unit not proven stopped, a log not kept, a command that never
  started) has none, since the job's next run is the job's row (what was sampled of the run that went back is dropped; samples are kept per job, not per run,
  so a job given out again and sampled before that drop, which takes the microseconds between the origin accepting the release and the
  loop's call, loses those first samples). A **fast-lane job** is written from its final event (its process is
  the caller's, so the figures are the samples'). Either way the row is handed to a writer goroutine (the callback never waits for
  the store; a row that does not fit the writer's queue of 256 is dropped and logged), and at shutdown the worker is stopped first, then the other makers of a final event (the HTTP
  servers closed with their requests answered, the queue's sweeper, the fast lane), then the writer, then the store; a row whose event is
  made after the writer drained (a request still in flight when the servers' 3 s close limit ran out) is lost. A fast-lane job that never started has no row. A job no sample saw (it ended between
  two) has a row whose samples-only figures are null; a fast-lane result with no start or finish time (a lease that ran out, a
  release) still gets a row when the samples saw the job: the first and last sample stand in for the times, and the row is
  `partial`. `partial` is also true when the job began before this wwd did. The `slot_charged` is the slot the job was charged under the host's
  current admission, not a property of the job: `heavy` for a queue job the worker runs (the worker claims against the heavy slots), and
  for a fast-lane job the slot its request named (`heavy` for an undeclared command, `light` for a declared task). When two writers record the same job, the first row stays (a second write changes nothing).

## 9. Exceptions and worker settings

- wwd routes (local socket; and TCP with the pool token, where the caller is a peer wwd forwarding for its own host's
  Purdex daemon, §10): `GET /v1/worker`, `PUT /v1/worker` `{enabled, slots: {heavy, light}, owner_rule}` (persisted in
  `wwd.db`, emits a `worker` event); `POST /v1/exceptions` `{name, until | pid, holds: ["heavy", "light"]}`,
  `DELETE /v1/exceptions/{name}` (emit `exception` events).
- Turning the worker off (`PUT /v1/worker` with `enabled: false`) stops new claims only: a job already running finishes (the
  loop stops running jobs only for an owner yield, `worker/loop/loop.go`).

- `pdx wwd exception start <name> [--until <time>|--pid <pid>]` / `stop`; the Purdex daemon calls it for the App's
  dev-page auto packaging; known packagers (electron-builder) are recognised by their process too.
- While one is active the local worker takes no new heavy job (light too if declared); other hosts are unaffected.
- Dev servers and watch mode are never jobs; they count in facts and therefore in `headroom`.

## 10. Purdex daemon integration

- The Purdex daemon reads only its local wwd (socket): `GET /v1/pool`, `GET /v1/events`, job queries. It never holds the
  pool token or a peer's address.
- **Per-host fallback in pool mode** (10-18, found at the C1 switch): a host the pool gives no fresh facts for — not
  listed, listed but unreachable (air19 asleep, a wwd down), or stale — is read by the old SSH probe until the pool has
  it again. The App never shows a host offline only because its wwd is missing or down. The whole-fleet fallback (the
  local wwd unreachable for 20 s) stays as it is.
- **No host sampling of its own in pool mode** (10-18, C1 audit): while the pool can read a host, the Purdex daemon
  takes none of that host's CPU, memory, pressure, page rate, disk or load itself, and writes no `host_minutes`; the
  gate's `pressure.json` is fed from wwd facts. What stays is listed in the plan's C1 acceptance (process trees, gate
  holders, the gate CLI until WWD-9a, the assist probe until WWD-9b, the connection check, per-session `ps`, fallbacks).
- **Forwarding through the local wwd** (10-18, A line's 2a question): a read or change about another host goes to the
  local wwd's socket with `?host=<alias>` — `GET /v1/facts/history`, `GET` / `PUT /v1/worker`, `POST /v1/exceptions`,
  `DELETE /v1/exceptions/{name}`, and (WWD-8) `GET /v1/alerts`, which answers `wire.AlertList`; a reader that gets the
  `alert` event, or reconnects, reads the list again. The local wwd answers for itself, or forwards to that peer over
  TCP with its pool token and the peer's address from its config, returning the peer's answer as is, or `502 {host,
  reason}` when the peer cannot be reached. Only the socket side forwards; a TCP request carrying `host` gets `400`
  (no multi-hop, no relaying through a token holder). The Purdex daemon's `GET /api/pool/facts/history?host=<alias>`
  hands the question to the local wwd with `?host=` and returns its answer: a peer that cannot be reached is `502
  wwd_error`, wwd not running `503 wwd_unavailable`, a 4xx of wwd's (an alias it does not know is `404`, a bad query `400`)
  is passed on with its status as `wwd_rejected`.
- **For the App**: `GET /api/pool/hosts` (the four hosts: info, latest facts, worker state, labels, and — capability
  `pool.assess.v1`, null for a host without facts — `headroom_reasons` (§3.2) and `load {score, driver}`: the fleet ring's
  composite 0–100, the largest of the CPU %, the memory %, the memory-pressure level (1 → 30, 2 → 75, 4 → 100), the page rate
  (pages/s, at most 100) and the fullest disk % from 85 up; `driver` is that one, `cpu` | `mem` | `pressure` | `paging` | `disk`,
  the first on a tie. The App only translates the codes into words), `GET /api/pool/facts/
  history?host=…`, `GET /api/pool/facts/series?host=&since=&step=` (capability `pool.series.v1`: the same history cut down to
  what a chart draws — `at`, `zone`, `cpu_idle_pct`, `mem_available_mb`, `pressure`, `page_out_rate`, `disk_max_used_pct`
  (the fullest disk; null when none), `headroom {heavy, light}` — about 200 bytes a point instead of a whole facts record's
  7 KB. `since` is an RFC 3339 time or a duration back from now up to 14 days (`1h`, `24h`); `step` is `5s` or `1m`, by
  default `5s` for a window of 2 hours or less and `1m` for a longer one; wwd's per-minute rollups serve `1m`; the host that has the data cuts the points (`GET /v1/facts/series`, §3.3), so a remote host's 24 h or 14 d series is not held back by the peer-forwarding cap on a body; a wwd from before that route answers 404 and the daemon then fetches the full history and cuts it itself, which works for about an hour of a remote host and a day and a half of the local one (#3489). **At most 2000
  points**: more and the latest are kept and `truncated` is true; a chart of 24 h at 1 m (1440) or 2 h at 5 s (1440) is whole),
  `GET /api/pool/jobs?…`, `GET /api/pool/jobs/{id}` (+ log), host events `pool.changed` and
  `jobs.changed`; capabilities `pool.v1`, `jobs.v1`. During migration `/api/fleet` and `fleet.changed` are produced from
  the pool (same `FleetHost` / `FleetFast` / `FleetQueue` shapes) so the App changes nothing until WWD-7.
  **Heavy or light (S11, MD-4)**: every job the two jobs routes answer (each job of the list, the `job` of the detail) is wwd's `Job`
  with every field as wwd sent it and one more key, `slot` (`"heavy"` | `"light"`), added by the Purdex daemon (`PoolJob`,
  `internal/module/jobs`): the slot is `wire.JobSlot` — a declared fast-lane task is light, everything else (a queue job, an adhoc
  fast-lane command) heavy. `wire.Job` and wwd's own answers do not change. **Known limit**: a fast-lane run that is waiting for a slot
  (it was answered 429, §5.2) is not registered yet, so it is in no list; seeing the waiters would need wwd to record them.
- **Which daemon is a pool host** (capability `pool.identity.v1`): `GET /api/info` carries `wwd {host_id, alias}`, the identity of the
  wwd on this machine (its own `host_id`, not the Purdex daemon's `host_id`). The pool module's watch reads it from the first peer of the
  local `GET /v1/pool` (wwd lists this host first) and keeps it in memory, so `/api/info` never calls wwd; the key and the capability are
  missing, not empty, before the first read and while wwd cannot be read. The App matches a pool host to a daemon by `info.host_id` of the
  pool host equal to some HostConfig's `/api/info.wwd.host_id`, and no longer by `/api/fleet`'s alias or kind (WWD-9 removes them).
- **Observations for the App** (capability `pool.observations.v1`, §8.4): `GET /api/pool/hosts/{alias}/observations?since=&until=` and
  `GET /api/pool/hosts/{alias}/undeclared?since=` read a host's process-tree records through the local wwd (`host=<alias>`; a peer's is
  forwarded). The answer is wwd's `ObservationsResponse` / `UndeclaredResponse` as wwd wrote it. A bad `since` or `until` is `400`, a
  host whose wwd predates the routes is `{host, known: false, observations: []}` / `{host, known: false, groups: []}`, and the other
  errors are the exceptions read's (`wwd_rejected`, 502, 503). A device token gets 403 (a process's command line may carry a secret
  even after the redaction of §8.4): only the admin token reads them, which is what the Mac App's host fetch uses; a phone's event page
  would need that decided first. Paging back with `next_until` is inclusive:
  the record that began at the boundary is on both pages, and the reader drops the repeat by `id`.
- **Known gaps for the App's pool view**: in pool mode `/api/fleet`'s `slow.queue` is empty (WWD-7b1 works it out from the job
  list instead; `facts.queue.queued` has a value from release 756). The App reads jobs from the Purdex daemon of the host that
  has one (mlab, air26) and, for mserv and air19, through `?host=` forwarding, which shows the peer's view (no fast lane, no
  ad-hoc runs). mserv and air19 have no Purdex daemon, so there is no `jobs.changed` for them and the App polls every 10 s.
- Mutations for the App, admin token only (device tokens 403): `PUT /api/pool/hosts/{alias}/worker`,
  `POST /api/pool/hosts/{alias}/exceptions`, `DELETE /api/pool/hosts/{alias}/exceptions/{name}`; the daemon calls its
  local wwd with `host=<alias>`, which forwards (above). Announced as capability `pool.control.v1` (same condition as
  `pool.v1`). The body is checked here against the wire types first (a refused one is `400 bad_request`, wwd is not
  asked); wwd's own `4xx` comes back with its status as `wwd_rejected`, a `5xx` or an unreachable peer as `502
  wwd_error`, wwd not running as `503 wwd_unavailable`; changes are never cached. A host alias is 1–128 bytes of UTF-8 without control characters (`wire.ValidAlias`); wwd's config
  enforces the same rule on its peers and on its own alias, so every alias the pool lists can be named here.
- Holds of a host's exceptions, read-only (#3479 G4): facts' `exceptions[]` carries no `holds`, and the facts wire is not changed for it.
  wwd serves `GET /v1/exceptions` (`[]Exception`: name, until/pid, holds, allow, flags; `?host=` forwarded from the socket like the
  worker routes; refused with `host` on TCP). The Purdex daemon serves `GET /api/pool/hosts/{alias}/exceptions` →
  `{host, known, exceptions}`, asked of the local wwd with `host=<alias>`; a device token may read it (it is in the allow-list). A host
  whose wwd predates the route answers 404 through the forward and the reply is `known: false` with an empty list — "not known", never
  a 500. The errors are the history read's (an alias the local wwd does not know is `404 wwd_rejected`, an unreachable peer `502
  wwd_error`, wwd not running `503 wwd_unavailable`). Cached for a second like the other reads.
- Job control for the App, admin token only (device tokens 403, the routes are not in the device allow-list):
  `POST /api/pool/jobs/{id}/cancel?host=<alias>` (the local wwd cancels the job or forwards the cancel to that peer) and
  `POST /api/pool/jobs/{id}/position` with `{"position": "front"|"back"|"hold"|"normal"}`. A job's place is set on the host
  it is queued on (wwd's `POST /v1/jobs/{id}/position` is local-only and takes no `host`), so `host` is accepted only when it
  names this daemon's own wwd; any other is `400 host_not_local` and wwd is not asked. Both answer wwd's job as it is then;
  wwd's own `4xx` (a job that has ended is `409`, no such job `404`) comes back with its status as `wwd_rejected`, an
  unreachable peer as `502 host_unreachable`, wwd not running as `503 wwd_unavailable`. Capability `jobs.control.v1` (same
  condition as `jobs.v1`); without it the App does not show the "⋯" menu.
- Pool events for the App: the host event `pool.changed` → `{host}` (the alias, as `/api/pool/hosts` names its entries) is produced
  by the Purdex daemon's pool module. A watch reads the local wwd's `GET /v1/pool` every 5 s and compares each host's entry, the
  same one `GET /api/pool/hosts` answers, with the last read, so it covers everything that answer can change, facts' numbers
  included: a host whose facts move is announced about every 5 s, which is what replaces the App's polling. A host that
  changes, appears or disappears is announced. At most one notice per host per 2 s; a change inside the window is not
  dropped but merged into one notice at its end. The first read is only a baseline and announces nothing. After a baseline,
  when wwd goes away every known host is announced once (the answer of `/api/pool/hosts` is an error now), and the first
  read after wwd is back announces every host there was or is: an App that stopped polling keeps its connection to this
  daemon when wwd's drops, so without these notices it would keep an old pool until something else changed. Capability `pool.events.v1` is announced only while that watch runs (not before `Start`, not after `Stop`), so
  an App that sees it may stop polling `/api/pool/hosts` and read on each `pool.changed`, on a host-events reconnect and when
  the page becomes visible again; an App that does not see it keeps polling.
- `monitor` host readings, RT-5a `spawn_resources` and the watcher detector read `derived` / facts from wwd.
- Completion notice: when the submitter's session lives on this host, the Purdex daemon tells it (the same per-session
  notify path assist X1b uses), in addition to the waiting `pdx test` process — for every terminal state of a queued job:
  succeeded, failed, cancelled, superseded, expired, lost, and a cache hit. Delivery is at-least-once and best-effort: the
  notice is queued once per job (deduplicated by job id), but a crash between a send and its record can send it again, and
  a job whose notice fails 6 tries in a row is given up (`internal/module/jobnotify/store.go`, `maxTries`). The job's
  state (`pdx jobs show`) is the authority. A fast-lane run and an ad-hoc run (§5.2, §8.3) are not announced: `pdx test`
  prints their outcome itself, and only a `lost` run is told.

## 11. Security

- **Threat model** (10-18, after review rounds kept chasing same-user races): wwd defends against what comes from
  **another host** — peers' requests, snapshots, bundles, tars, logs and results — and against an origin or worker
  that misbehaves or is malicious with the pool token. It does **not** defend against processes of the same user on
  the same host: they can already write anywhere wwd can, so a race in which a concurrent same-user process swaps a
  symlink or file inside a workspace, the work root or `wwd.db` is out of scope. Reviews cite this line to close such
  findings instead of adding layers. Jobs are declared tasks from our own repos (D9): cleanup of what they leave
  behind is best effort, not a boundary.
- TCP requires the pool token; the local socket is trusted (same user). Submissions only on the socket. Forwarding to a
  peer (`?host=`) only from the socket; TCP rejects it (§10).
- A worker runs only manifest tasks for remote jobs; arguments are validated against the task's `args` kind.
- Snapshots, heartbeats, releases, results and logs need the job's live `claim_id` (a per-claim capability); the
  shared pool token alone is not enough, so one peer cannot act for another's claim.
- **Host identity and earned labels** (10-19): the pool token is shared, so the origin cannot tell which host a claim
  comes from — `ClaimRequest.Worker`, and the `result.host` it becomes, are what the claimer says — and labels are
  not checked at claim. Qualification, earned labels and result reuse are therefore correctness mechanisms among the
  pool's own hosts, not a boundary against a malicious token holder, which can already post a false result for a
  job it holds. The defence above against a malicious token holder covers what the receiving host does with the
  data (claim capabilities, paths, sizes, validation), not the truth of results or host names. Per-host tokens, with
  the origin binding a claim to its host, come before any host we do not own joins the pool (#3392).
- A worker rejects a remote job whose task is not in the repo's manifest at the snapshot, or whose arguments fail the
  task's `args` validation; the origin never lists ad-hoc jobs to peers.
- Tailnet-only bind; no route is exposed through `mcp.mlab.host` or Cloudflare.
- **mserv sandbox and groups** (M-L2): the sandbox keeps wake's groups, and wake is in `docker` — the docker socket is
  root on that host, and `NoNewPrivileges` does not stop it. The unit sets `InaccessiblePaths=/run/docker.sock`
  (verified in WWD-4d by a job that tries the socket and must fail); if that cannot be made to hold, the worker runs as
  a dedicated account without the `docker` group.
- **sudo on mserv**: wake has `NOPASSWD: ALL` today, so nothing is needed now. If it is ever narrowed, never allow
  `systemd-run` with a wildcard (a caller could append `--uid=root` or override the sandbox); allow a root-owned wrapper
  (`/usr/local/sbin/wwd-run`, fixed sandbox, taking only the workspace and the command) plus
  `systemctl stop|reset-failed 'wwd-*'`. `systemctl show` and `journalctl -u` need no root (wake is in `adm`).
  Changing sudoers is the host owner's call.

## 12. Migration and compatibility

- The gate (shim, classifier, slots) keeps working until WWD-6 switches the entry; removed in WWD-9.
- During the migration (until WWD-6) a queue job is outside the gate's slots, so the worker counts the gate: on a host with a gate,
  `headroom.heavy` is 0 while the gate's heavy slots are all held (a gate that cannot be read counts as full, and is logged); a host
  without a gate is unaffected. The watcher's `unmanaged_heavy` labels a tree carrying `WWD_JOB` as `wwd_job`: recorded, nobody woken.
  (#3447)
- The other direction, the same period (#3502): on a host with a gate, **each queue job the worker runs holds one of the gate's heavy
  slots while it runs**, so the two keep one account and a heavy command arriving then queues behind the job instead of making one more
  heavy thing on the host. The worker takes the slot without waiting, as a ticket behind the commands already waiting (it does not
  pass them), just before it claims a job; no slot, no claim. It first asks the gate's own admission (`[gate.admission]` as configured:
  the pressure and page-rate lines, which may be stricter than the zone, and the free-disk floor): while the gate would hold a new heavy
  command, no job is claimed. A quarantined job (its command could not be proven stopped) keeps its slot until the quarantine clears it,
  and a restart takes a slot for each quarantined job before anything is claimed (beyond the gate's size if it must; tried again each round
  until all are counted). The record names it `wwd job <id> <task>` (with the submitter's session),
  so `pdx gate status` and the watcher show whose it is. It is given back when the job is over, however it ends; a wwd that is killed
  loses the lock with the process, and a record left beside a free lock is stale and ignored. A host without a gate is unaffected. Both
  directions go at WWD-6 / WWD-9.

## 13. Advisor (the watcher's successor, WWD-8)

Rules first. What a rule can decide is decided by wwd or the Purdex daemon; an agent is woken only to judge, never
"to have a look". (10-19, from the WWD-8 inventory, the watcher's answers and the first review.)

### 13.1 Contract and storage first (8a-c)

- Every payload change in this section is one PR to `internal/wwd/wire` before any producer or consumer (§14a):
  Facts gain `mem.decompress_rate` and `queue.queued`; Exception gains `allow` and `flags` (§13.4); new payloads
  `Alert` and the alert list (§13.3).
- **Two phases**, because the decoders are strict and a release reaches the hosts one after another: the contract
  release raises `proto` to 2 and teaches every reader the new fields (optional; absent means unknown) and the new
  route, while no writer fills them yet. A writer fills them only once every pool host reports `proto` ≥ 2 in
  `/v1/info`, so an older reader never meets a field it would reject. A reader treats `404` on `/v1/alerts` as
  "this host has no alerts yet". A host rolled back below the contract makes the writers stop again, since they see
  its older `proto`. Tests cover the mixed pool: an old reader with a gated writer, a new reader with an old
  payload.
- **Holds are not gated at run time either** (8b-3, 2026-10-20): every host runs a build at proto ≥ 2 (758 on), and so does every
  reader of the facts (Purdex daemons, the App since 7a), so `POST /v1/exceptions` takes `allow` and `flags` without asking the pool.
  A hold is kept in `wwd.db` (host schema 7: two nullable columns of `exceptions`, NULL for an exception made without them); a wwd that
  predates schema 7 refuses the file, so a roll back across it restores the backup (`docs/wwd-deploy.md` §5). A pre-contract peer that
  is sent a hold answers `400` (its strict decoder), which the CLI reports as "this host's wwd does not know holds yet".
- Alerts are not behind the gate: rules run, and alerts are stored and listed by `GET /v1/alerts`, whatever the pool reports, because no older reader is shown one: the route is new (an older reader never asks it; a forwarded request to an older peer gets `404`, read as "no alerts"), and the `alert` event goes out on the socket stream only, whose reader is the same host's Purdex daemon, never older than its wwd (deploy order, docs/wwd-deploy.md §5); the peers' TCP stream never carries it. Only the new Facts and Exception fields wait for the gate. (10-19, lead: an unreachable host must not silence the other hosts' alerts.)
- wwd.db migrations `wwd_starts` (started_at, version, previous exit if known) and `alerts` (key, kind, level,
  since, last, cleared_at, detail): each re-runnable, tested from the deployed schema, preceded by the per-host backup of
  §12, with the restore steps in `docs/wwd-deploy.md`.

### 13.3 Alerts (8a)

- Each wwd evaluates the rules below for its own host and keeps its **active alerts** in `alerts`. `GET /v1/alerts`
  (local socket; pool TCP read for peers; added to §10's forwarding list) returns them. An `alert` SSE event is
  only a hint that the list changed: a reader that starts or reconnects reads the list again, so a dropped stream
  loses nothing.
- The **deliverer** is the Purdex daemon holding the fleet `primary` role (mlab while it is healthy; the fleet
  module's election decides the takeover, not a separate one), and it delivers only while its push module is ready;
  a standby with push ready also delivers when the primary reports no push or does not answer; otherwise a `standby`
  or `off` daemon reads and does not push. Each deliverer polls every host's `GET /v1/alerts` every 30 s (the `alert`
  event may shorten that later), sends `push` alerts through the push module (APNs), and gathers `digest` alerts for
  the daily digest.
- **For the App** (capability `pool.alerts.v1`): `GET /api/pool/hosts/{alias}/alerts` answers `{host, known, alerts}` — the local wwd is
  asked `GET /v1/alerts?host=<alias>` (a device token may read it; there is no write route), each alert is wwd's `Alert` unchanged and a
  `silence` alert also carries `silence`: `"wwd_down"` (the peer's wwd does not answer, its host does) | `"host_down"` | `"unknown"`
  (any other words), worked out by `wire.SilenceKind` from the alert's text, since `wire.Alert` has no field for it (§13.3 above: the
  list is read strictly). A host whose wwd predates the route is `known: false` with `alerts: []`. The host event `alerts.changed`
  `{host}` is a notice to re-read that route: the Purdex daemon reads every host's list every 30 s (the local host asked without a host,
  a peer by its alias) and announces a host whose list differs from the last look — `last` is left out of the comparison, it moves at
  every evaluation — and the local wwd's `alert` event reads the local host's list at once; another host's `alert` event never reaches
  this daemon (§13.1), so a peer's change is at most 30 s late. Same rules as `pool.changed`: a host's first look is only a baseline,
  at most one notice per host per 2 s with the changes inside the window merged into the one at its end; while the local wwd cannot be
  read every host looked at before is announced once, and the first read after it is back announces each of them once more. The
  capability is announced only while that watch runs.
- Sending `push` alerts to the phone is behind the host setting `wwd_alerts.push` (each Purdex daemon keeps its own; default **off**;
  an unreadable setting counts as off; read at every push). While it is off the alerts are written and gathered as usual and nothing
  is recorded as sent, so those that still hold when it is turned on are sent then (`docs/wwd-deploy.md` §7).
- Delivery is **at least once**: during a failover or a partition both deliverers may push the same alert, which
  is preferred to neither pushing it. Each deliverer keeps its own ledger (key, at) in its own store. An alert is
  recorded as delivered only when the push module confirms that APNs took the push, never when it is merely queued;
  until then it is handed over at most once per 5 minutes. A key is not pushed again by that deliverer within an hour
  of a confirmed delivery unless it cleared first, its restart included. air26's daemon always reaches the App on the
  Mac; APNs from air26 needs `[push]` there (confirmed by the user 2026-10-20: air26 has `[push] apns_dir` set and declares `push.v1`).

- **The exception to "a duplicate over a miss": the alert source cannot be read.** A deliverer that cannot read its own host's wwd
  (down, or no alerts route) or cannot read the pool (so the peers' lists cannot be enumerated) reports its push as not ready
  (`push_ready` false in the fleet role answer, from the `AlertsReadable` the alerts module publishes; true until its first pass), so
  the standby takes over — and it pushes nothing itself meanwhile, even from the lists it did read, since the same shared alert would
  otherwise go out from both for as long as the pool stays unreadable. **Fallback when both are blind (#3610):** a daemon that can
  read its own host's wwd but not the pool, and has seen the other fleet daemon unable to push for **two passes in a row** (its
  `PeerPush`: the answer said `push_ready` false, or the other could not be reached; nothing known yet, or an older daemon whose
  answer carries no `push_ready`, is not a confirmation), pushes the alerts of **its own host's list** and nobody else's — that is the
  only list it has. It holds for primary and standby alike, so each tells its own host's alerts (a disk low on the standby is not lost
  because the pool is unreadable). The fallback ends at the first pass that does not meet the conditions (the pool readable again, the
  other daemon ready again, the local wwd unreadable too), and the normal rule applies at once. A shared alert (the same `silence:`
  failure on both lists) may go out once from each: a duplicate, which this section accepts. When a daemon recovers, the alerts it
  already told stay in its ledger and are not told again; at most one further push per alert can come from the other side. With the local
  wwd unreadable as well there is nothing to push and nothing is (the App still shows "wwd offline").

| Alert | Level | Rule |
|---|---|---|
| disk low | push | free < 12 GB on a host's work volume; once raised it clears only at free ≥ 12.5 GB, so a disk hovering at 12 GB is one alert, not a raise and a clear every pass (a cleared key may be pushed again) |
| disk falling | digest | free < 14 GB, or falling ≥ 2 GB/h with < 10 GB projected within 6 h |
| pressure held | push | zone ≥ warning for ≥ 5 min and swap +≥ 1 GB in that window |
| mserv service | push | mserv unreachable (for as long as the silence rules say, below), or production PSI some avg60 ≥ 10 for ≥ 2 min, or MemAvailable < 1.5 GB. The last two are judged by mserv's own wwd (Linux only; PSI over the last two whole minutes and still high; MemAvailable is the latest reading, no duration, and once raised clears only at 1.75 GiB so a reading hovering at 1.5 GiB is one alert; an `expect_pressure` hold (§13.4, 8b-3: no hold can carry the flag before that) suspends only the PSI part); "unreachable" cannot be reported by the host itself and is the silence rules' (below, 8a-3): the matrix there says 3 min of failed pool reads, the earlier text of this row said 2 min, and 8a-3 settles the one number for both |
| worker crash loop | push | ≥ 3 wwd starts within an hour that followed a run that did not end cleanly (#3843) |
| silence | push | see the matrix below; per-host `alert_unreachable` (off for air19). Keys: `silence:<peer alias>` (this host's pool reads of that peer failed ≥ 3 min) and `partner_down` (`[advisor] partner_check`, only on a host with a Purdex daemon: its deliverer has not read this host's alerts on the socket for ≥ 3 min). The number is 3 min for every host, mserv included (the earlier 2 min of the mserv row is retired) |
| thrash | digest; starts the broker reclaim (below); an incident only if it persists ≥ 10 min after that, at most once per 2 h per host | macOS: compressor > 4 GiB and decompress_rate > 80 000/s for ≥ 60 s |

**The watcher's pressure rules (WWD switch S3-2).** Level `watch` is told to the watcher alone: the Purdex daemon wakes it and neither pushes it
nor gathers it in the digest, and a level this build does not know is told to nobody. Three rules, judged on this host's own 5 s samples
(`LocalRecent`, not behind the proto 2 gate) and never on the zone, since a host's zone can sit at warning for page-out alone (air19, with a
Windows VM paging about 92/s, has `mem.pressure` 1 all the while). A *pressure sample* is macOS `mem.pressure ≥ 2`; Linux PSI at the warning
line (`facts.PSIWarn`: some10 ≥ 10 or full10 ≥ 1, without the available-memory and swap conditions of the zone). **A sample whose memory source failed to read is a hole**
(`Mem.TotalMB` 0, no level, no PSI): it is neither calm nor pressure, and it breaks "every sample of the last 60 s", whatever the samples around
it say (the rules never judge on the few samples that were read). A sample whose *other* sources failed (cpu, disk, the process table) but whose
memory was read is judged on that memory: the process scan is the source most likely to time out when memory is short, and it must not blind
the rules then (lead's ruling 2026-10-21).

| Alert | Level | Rule |
|---|---|---|
| pressure watch | watch | every sample of the last 60 s is a pressure sample, or the host went from no pressure to pressure ≥ 2 times in the last 30 min (no swap condition). Clears after 10 min with no pressure sample |
| pressure danger | push (the phone and the watcher) | macOS: any one sample with `mem.pressure == 4`; Linux: PSI at the danger line (`facts.PSIDanger`: full10 ≥ 10 or some60 ≥ 25). Judged at **every sample** (the sampler wakes the evaluator, which runs it in the same goroutine as the 30 s pass, never beside it), so the alert is raised within 5 s of the sample; the deliverer's 30 s read makes the wake at most about 35 s after it. Clears after 2 min with no such sample |
| swap growth | watch | the swap in use grew ≥ a threshold over the last 30 min (last whole minute minus first). The threshold is 500 MB up to 16 GB of RAM and RAM / 16 GB × 500 MB above it (24 GB: 750 MB); `[advisor] swap_growth_mb` sets it per host. Clears when the 30 min growth is under half of it |

They are written only where `[advisor] watch_rules = true` (default **false**): a reader that does not know level `watch` or the three kinds
refuses the whole alert list, and wwd refuses its own stored list the same way, so every reader (the four wwds, the Purdex daemons) has this
build before a host turns them on, and a host turns them off and waits for the alerts to clear before it goes back to an older build
(`docs/wwd-deploy.md` §15). `[advisor] off = ["pressure_watch", "swap_growth"]` takes single rules out of a host that has them on (only these
three kinds are accepted; air19 lists the two that mean nothing for a laptop with a resident VM); `off` never turns a rule on.

**Silence: who notices, who tells.**

| Down | Noticed by | Told by |
|---|---|---|
| a host's wwd (the rest up) | the other wwds: pool reads fail ≥ 3 min, an alert on their own lists | the deliverer |
| a host's Purdex daemon (its wwd up) | its wwd: the partner check fails ≥ 3 min, `partner_down` on that wwd's list | the deliverer; air26's when the daemon down is mlab's |
| a host's wwd and daemon, or the whole host | the other wwds | the deliverer; air26's when the host is mlab |
| both deliverers | the wwds | nobody can push — a stated gap; the App shows both offline |
| a partition | each side sees the other unreachable | the deliverer on its side |

The App shows "wwd offline" for a host whose wwd is unreachable even while §10's SSH fallback still answers its
facts, so the fallback never hides the failure.

Noise suppression for known residents applies only while the host has ≥ 50 % memory available and swap did not
grow in the window; otherwise the item stands. The daily digest replaces the watcher's 30-minute report
**[to be confirmed by the user]**: counts per alert, thrash episodes, broker reclaims and compressor freed, disk
trend, member count, open incidents. `pdx wwd report --last <dur>` answers "how is it now" at any time.

- **Broker reclaim** is booter's (its `codex` checker), never the advisor's: no active job (re-scanned the moment
  before the signal), no client on the broker's socket, the worktree's last job ≥ 60 min ago, the youngest
  descendant ≥ 60 min old, the tree's root found along the ppid chain (the owner need not be Claude); thresholds
  are judged per tree (wake/mlab#37).
- **Release slots**: while a `release` hold (§13.4) is on a host, its light slots drop to 1 — the gate's and the
  worker's, until WWD-9 retires the gate.
- In pool mode (`fleet.source = pool`) the Purdex daemon's E1 detector neither pushes nor wakes anyone (it retires
  in WWD-9c); undeclared heavy trees come from wwd's observations (§8.4), which never count launchd-parented apps or
  the simulator as trees.

### 13.4 Holds (8b-3)

- A hold is an Exception (§9) with two new fields: `allow: {classes: [release|merge|dev], repos: [<name>]}` —
  while it is on, the host's worker admits a job only if its class or its repo is listed (both empty: none) — and
  `flags: [release, expect_pressure]`. `holds: [heavy, light]` keeps its meaning (local slots). An Exception
  without the new fields means what it meant before.
- `pdx wwd hold <host> --for <dur> --reason <text> [--allow-class <c>…] [--allow-repo <r>…] [--release]
  [--expect pressure]`. A line that needs a host quiet asks wwd, not an agent.
- Holds travel in the facts' `exceptions[]`, so every reader sees them from the pool facts — including, until WWD-9
  retires them, the gate's assist intake (air26) and the manual mserv offload's self-check, which wait while a
  hold is on.
- **When a hold takes effect.** `POST /v1/exceptions` answers once the hold is saved, but the worker decides from the facts, which the
  sampler writes every 5 s (and the worker reads again before each try within a round). So **a hold is in force for the worker at the
  latest when the next sample shows it** — a job claimed in between runs on; admission never touches a job that is running. A caller that
  must know the host is quiet (the CLI, a script) waits until the hold shows in the facts' `exceptions[]` and treats a timeout as a
  failure; the POST alone is not that proof. (The same holds for every exception, with or without `allow`.)
- `release`: the slot rule in §13.3. `expect_pressure`: for a deliberate stress test, suspends only the PSI part of
  the "mserv service" push while the hold lasts; MemAvailable and swap still push.

### 13.5 Incidents and the advisor (8b)

- Incidents live in the Purdex daemon on mlab, the one place that opens advisor sessions (`incidents`: id, host,
  kind, alert key, opened_at, snapshot, state, session, resolution, tokens). It opens one from an incident-worthy
  active alert of any host (§13.3), deduplicated by alert key, and re-reads every host's active alerts when it
  starts, so a restart loses none. Claiming is a local transaction: an incident is never taken twice. With mlab
  down there is no advisor; push alerts still go out from air26.
- Kinds: an undeclared heavy tree persisting ≥ 10 min; zone ≥ warning ≥ 10 min with nothing queued (residents, not
  jobs); thrash that outlived the reclaim; resident growth under pressure; a qualification disagreement (after
  WWD-5); a disk cleanup decision; a worker crash loop; a question sent to the advisor.
- One advisor session per incident (Sonnet by default), at most one at a time, with the incident and a facts
  snapshot; it records its resolution and token use and ends. Caps: 150k context, 30 minutes **[to be confirmed by
  the user]**. No session starts while mlab itself is in the danger zone or thrashing, except for a push-level
  incident.
- **Capability profile**, enforced by the session's tool permissions, not by its prompt: read files, `pdx wwd`
  reads, facts, incidents, observations and an allowlist of read-only commands (`ps`, `vm_stat`, `df`, …); write
  only its incident's resolution and structured proposals on it; `pdx msg` to the lead and the lines. No file write
  or edit, no process signal, no service control, no settings change, no other shell.
- A **proposal** (`reclaim_broker` → booter, `cleanup` → the user's yes in the App, `hold`, `issue`) is carried out
  by its owner after the owner's own checks, never by the advisor.
- **Untrusted input**: question text, snapshots, process command lines and file contents are data. They reach the
  session in a marked data block, and nothing in them changes the profile.
- A message to the advisor's address while no advisor session is live opens a `question` incident with that text.
- Durable knowledge (known-harmless processes, cleanup rules) is a reviewed rules file on the mlab repo's main
  branch (`advisor/rules.toml`, named by `[advisor] rules_file` in config.toml), read by wwd — not the watcher's
  branch, which never merges and retires in 8c. Incidents are records, not knowledge.
- The name 「顧問」 (code `advisor`) **[to be confirmed by the user]**.

## 14a. The wire contract

All payloads in §3–§4 and §9–§10 (facts, history, events, pool, job, claim/lease calls, results, summaries, worker and
exception settings, the App's pool and jobs API) are defined once as versioned Go types in `internal/wwd/wire`, with a
JSON fixture per type and round-trip tests (WWD-0c). Every track imports it; a change to the contract is a PR to that
package first.

Decisions made while writing it (#3195), now part of the contract:
- Event payloads: `exception` → `{host, name, active, exception}`; `labels` → `{host, labels}`; the Purdex host events
  `pool.changed` → `{host}` and `jobs.changed` → `{host, job_id, state}` (notices; the App re-reads the resource).
- `mem.pressure` is never null (0 = unknown); the other platform readings are pointers serialised as `null`.
- The submission answer omits `result` unless it is a cache hit (`{id}` / `{id, result}`, §4.4) — the one field that
  is omitted rather than `null`.
- `Exception` takes exactly one of `until` / `pid`, and `pid` > 0; collection responses validate every nested value.
- `ClaimRequest` needs a worker; `WorkerSettings.owner_rule` is free text; `fingerprint` is a string map;
  `FactsHistoryResponse` is `{step, records}`.
- WWD-3b adds the submission request type (`JobSubmission`) and `interruptible`, `queue_timeout_s`, `adhoc` on the
  job (§4.1) in its own small PR before the queue itself.
- `JobsListResponse` is `{jobs, cursor, epoch}` (#3293, #3309); a cursor is a decimal string of the origin's change
  counter (`wire.ValidCursor`), an epoch 32 hex digits (`wire.ValidEpoch`); a cursor the origin did not make is `400`.
  `epoch` is a required field and the decoders are strict, so wwd and the Purdex daemon / `pdx` are always deployed at
  the same version.
