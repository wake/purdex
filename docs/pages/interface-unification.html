0結論

標竿產品已經收斂到同一個做法：語意層共用，元件依能力出現，外殼依裝置變形。Purdex 缺的不是一套新介面，而是一份統一的對話模型：兩種底層都輸出到這份模型，Mac App 和 iOS App 都只讀它。

  • 介面統一做得到，而且已經有人做出來：
    • Collie 1.17（10-06）起，agent pane 預設開 Chat 畫面。
    • herdr-web-ui 讓同一個 pane 在 chat 和 terminal 兩種檢視（lens）間切換。
    • Orca 每個分頁都能在 Chat 和終端之間切換。
    • tuios 讓 TUI agent 和 headless agent 共用同一套狀態與 Inbox。
    • Nimbalyst 的「真 CLI 模式」只少了三個元件：plan 核准、todo、背景任務。這跟使用者的原則「terminal 有、worker 沒有的，頂多那個介面出不來」是同一件事。
  • Codex：兩種底層會變成同一條 app-server。TUI 用 --remote 接上 app-server，0.157 起也可以由共用 daemon 自動接上。介面、權限、通訊都走這一條。HAPI 已經做到 TUI 和 Web 同時操作同一個 thread。
  • Claude Code：沒有公開的同等協定，只能拼：
    • 結構化內容從 transcript 來，狀態和權限從 hook 來，再加上狀態檔。
    • 使用者回覆時把字寫進 PTY。這是使用者本人的輸入，不違反「不替使用者打字」的原則。
    • Purdex 已經有 10 個 hook 事件、statusline proxy、完整對話檔渲染（E6）。還缺權限和提問的作答通道，要先做 spike。
  • 「讀」和「答」分開：
    • 對話串流只負責呈現。權限、提問、計畫固定在輸入框上方的 dock，三種介面共用，terminal 介面也有。Collie 和 T3 都這樣做。
    • 答不了的直接說「到終端回答」，例如 CC TUI 的 plan 核准。這是 Claude agent view「peek 答不了就 attach」的規則。
  • 桌機＋行動：
    • 沒有任何一家讓同一個元件在兩邊長得一樣。大家共用的是語意層：狀態詞彙、事件歸併、工具摘要、待回應請求。
    • iOS App 在另一個 repo，所以語意層最好放在 daemon，兩個 client 只負責畫。
  • chat＝對話式介面（10-08 定案，已更正第 7 節）：主角是對話本身，工作過程退到背景；標竿是 agent chat 類產品（Grok Bot、Meta Muse、OpenAI Dots、OpenClaw）。
  • 通訊：
    • Codex 走 thread/queue/add，用的是同一條 app-server。不打字；對方忙就排隊、閒著就喚醒；訊息存在 SQLite，不會掉。
    • CC 維持現在的 peer socket，它在 8 月已經成為官方文件化的 cross-session messaging。
    • herdr 的做法是把字打進對方 pane，正是 peer bridge 當初拒絕的路。

1定案：名詞兩軸與三條原則

使用者 2026-10-07 定案。worker 收斂成 Nexen 的 execution；chat 和另一個新名詞只用來稱呼介面，因為 worker 和 chat 本來就只差在介面。

底層（誰在跑 agent）

terminal：互動式 TUI 跑在 tmux（CC／Codex）

worker：Nexen execution（claude -p stream-json／codex app-server）

E2 定案仍然成立：一個對話同一時間只有一種底層狀態，分別是 terminal、worker、休眠、消失。

介面（使用者看到什麼）

terminal真終端，只有 terminal 底層才有

新名詞（取代 room）完整的結構化紀錄

chat定位見第 7 節

後兩者兩種底層都能用，元件依能力出現。

原則一：介面統一，由能力決定顯示什麼。兩種底層用同一套介面語言（同樣的名詞、同樣的元件）。底層有提供的能力，元件就出現；沒提供，元件就不出現。不做降級版，也不討論哪種底層適合哪種使用情境。

原則二：一套名詞、一套元件，同時適用桌機和行動。每個元件在兩種裝置上各有呈現方式。

動機：worker 和 chat 當初就是為行動版準備的。但 -p 和 terminal 本質不同，所以手機端最好能不放棄 terminal 模式。Collie 這類標竿都建立在 terminal 底層上，要學它們，介面就得接得上 terminal 底層。

連帶影響（尚未定案）

  • 狀態列三顆鈕（殼層整理 D-下）混了兩個軸：「terminal→worker」其實是換底層（Hand to nex）。照新模型，三顆鈕應該只切換介面，換底層另外做成一個獨立動作。
  • 「工作區」名詞衝突：Purdex 的 workspace 是一組分頁；業界（Paseo、Orca、Happy）的 Workspace 是一個 cwd 或 worktree。

共識

  • Workspace 指 cwd 或 worktree。Subagent、Plan、Approval、Question、Compaction 這幾個詞大家通用。
  • 需要使用者處理的狀態一定放第一位：Needs you、Needs input、Waiting on you。很多家把「要你回答」和「要你核准」分開（HAPI、Collie、Happy、Nimbalyst）。
  • 每一輪結束時顯示「Worked for N」，失敗的那一輪不摺疊。
  • 「Ready for review」（做完、還沒看過）和 done 分開，Claude、Collie、T3 都這樣做。

分歧

  • 一等單位：Paseo 以 agent session 為主，herdr 系和 Collie 以 pane 為主（agent 只是 pane 的屬性）。
  • 檢視模式在切什麼：細節多寡（Claude、Paseo、HAPI、Buzz）或底層呈現（Collie、Orca 的 chat／terminal）。沒有人切泡泡和全寬。
  • 失敗狀態：Collie 和 Buzz 沒有 error 狀態，其他家有。
  • 一輪叫什麼：T3 叫 Run，其他家都叫 turn。Paseo 明文禁用 Run。

3.2 能力宣告：五種粒度

原則一需要一個機制，讓介面知道「這個元件該不該出現」。標竿產品的做法由粗到細如下：

做法代表形狀元件缺席時
資料驅動Paseo有 AgentCapabilityFlags，但 UI 幾乎只看資料：modes、models 陣列是空的就不畫隱藏，不 disable（docs/forms.md）；舊 daemon 不做降級版，只提示更新
布林T3 CodeOrchestrationV2ProviderCapabilities，12 組布林有三種處理：隱藏（fork、Plan）、停用並說明（Steer）、降級（steer → queue → 中斷重來）
列舉Orcasteering: inject｜queue、approvalEnforcement: provider｜orca沒宣告的欄位當成「沒宣稱」，看不懂的值退回最保守的處理
分級、fail-closedNimbalyst窮舉所有 provider，沒有選填欄位；contextReporting: none｜token-counts｜context-window沒宣告到的 provider 一律當沒有能力
兩層＋原因HAPI、Buzz、Happy靜態的 flavor 表＋session 執行期能力；每個欄位都附「不可用原因」永久不支援就隱藏（Happy 的理由：「灰掉會被誤以為能開」）；暫時不行就停用並附原因；缺席要給具名理由（Buzz）；「資訊未知」≠「不支援」

對 Purdex 的含意：兩種底層的能力差異是結構性的。例如 worker 的背景任務撐不過一輪、CC TUI 的 plan 核准答不了，這些都是永久的，所以預設應該是隱藏。只有「暫時」的狀況（daemon 版本太舊、連線中）才停用並寫原因。Codex 在 terminal 和 worker 底層走同一條 app-server，所以能力差異主要在 CC 這一側。

4統一元件清單草案（C01–C25）

已過時（10-08）：這張表寫在 mod 實測之前。CC terminal 底層的逐字串流、權限、用量都能透過 Purdex mod 拿到；worker 的背景任務（Nexen N3）與收訊（Nexen peer mailbox）也不是 ✗。最新版本見 設計文件 v0.2 §4 事件簿。

「業界共識」欄是把各標竿實際做法歸納後的結果。後三欄是每個元件在 Purdex 兩種底層上的資料來源。✓ 表示拿得到（有出處，或 Purdex／Nexen 已經在用）；△ 表示推論或還沒驗證；✗ 表示拿不到，依原則一這個元件就不出現。Codex 的兩種底層走同一條 app-server，所以合成一欄。

6桌機＋行動：一套元件兩種呈現

查了 Happy、T3、Nimbalyst、HAPI、Conductor、Claude、Codex 七家同時有兩種版本的產品，沒有一家讓同一個元件在兩邊原封不動，大家共用的是語意層。Claude 官方文件寫：「The app is the same for each; they differ in where the work happens.」

共通規則

  1. 語意層一定共用，元件不一定。狀態詞彙、事件歸併、工具摘要、待回應請求都放在純邏輯層，例如 T3 的 client-runtime、HAPI 的 golden fixtures。導航、輸入框、通知這些外殼則用各平台原生的做法。
  2. 換容器，不換導航樹。畫面寬就並排，窄就堆疊。草稿和目前選取放在樹的上層，旋轉或縮放時不會遺失。Nimbalyst 的規範明文禁止依 size class 換導航樹。
  3. 斷點只看可用寬度，不看裝置。高度不參與判斷，因為鍵盤把高度壓縮時不應該改變導航。每個元件有自己的門檻，例如 Happy 是 768／1100，T3 是 720／980，HAPI 是 920。
  4. 輸入方式和寬度分開判斷。觸控（pointer:coarse）改變的是互動：Enter 不送出、可點範圍至少 44、hover 才出現的操作改成常駐、終端加一列特殊鍵。寬度改變的是版面。
  5. 權限和提問在手機上要放大：按鈕 44pt；只露兩顆主按鈕加 ⋯，或全部攤開；提問直接取代輸入框。
  6. 細節移出對話串。桌機在原地展開或開側面板，手機推入整頁或用 sheet。diff 在手機上一律單欄。
  7. 推播只負責把人帶回現場。使用者正在看時不推；能從通知直接答的，只有二選一的權限和文字回覆。狀態指示用同一份快照，依顯示空間決定放多少，例如 Nimbalyst 的選單列放 1 個名稱、鎖定畫面放 3 列、Dynamic Island 放 1 個數字。

分歧

  • 共用到什麼程度：
    • Happy 1 代用 React Native 一套程式通吃。
    • Nimbalyst 的對話紀錄是 web 元件，外殼用 SwiftUI。
    • T3 和 HAPI 只共用邏輯。
    • Happy 2 代把桌機另開一個 repo，明文禁止做行動適配。這個反例值得注意：做成一套之後，他們又分開了。
  • Live Activity：T3 和 Nimbalyst 有，Happy 和 HAPI 沒有。從通知直接核准：只有 HAPI 真的做到。
  • 沒有任何一家做「手機預設精簡」的開關。精簡程度寫死在版面常數裡。

對 Purdex 的含意：Mac App 用 React，iOS App 在另一個 repo，兩邊不可能共用元件程式碼，只能共用語意。所以語意層（狀態詞彙、工具摘要、回合摺疊的歸併、待回應請求、能力宣告）最好在 daemon 正規化：daemon 把兩種底層都轉成同一份對話模型，兩個 client 只負責畫。這也是 Paseo（中性的 AgentStreamEvent）和 HAPI（共用 client contract＋golden fixtures）的做法。

7chat 的定位（2026-10-08 定案，已更正）

更正：這一節的第一版拿 coding agent 的介面（Happy、T3、CC Pocket）來比較，比錯了對象，得出「沒人用泡泡」的結論也跟著錯。那些產品其實是「紀錄介面」的參考，不是 chat 的。

使用者定案：chat＝對話式介面。主角是對話本身：你說一句、它回一句；工作過程退到背景，做事時只有一則會原地更新的進度，想看細節就點開紀錄。chat 的標竿是 agent chat 類產品。多人、多 agent 同房是對話式介面自然容納得下的情境，但不是 chat 的定義。

標竿是什麼值得借的
Grok BotxAI（SpaceXAI）的常駐「Bot 同事」，2026-08 beta，桌機＋手機群組 2–6 個 Bot，沒被 @ 時由 Bot 自己決定誰回；右側常駐 Bot 雲端電腦的縮圖；寄信或發訊息前先出草稿
Meta Muse個人 agent，2026-09，iOS／Android／web＋WhatsApp頭像下方一行字顯示正在做什麼；點頭像看完整活動紀錄；敏感動作用核准卡
OpenAI Dots常駐 agent，以 Codex harness 演化而來，2026-09-29 DevDay 發表iMessage 風格（使用者泡泡染成 dot 的顏色）；委派的工作各自成 thread，對話裡只回「摘要＋連結」；另有 Activity 面板；多人場合只聽 owner
OpenClaw自架 gateway，接 24 個以上訊息平台，39 萬星一則會原地更新的進度訊息；做完收成「Worked for 2 分 3 秒 · 2 failed」；多 agent 同房的輪次上限與「沒新東西就不出聲」；看得到核准請求不代表能核准

完整的元件規則見 設計文件 §8。多人、多 agent 同房的發言規則（Hermes Bot Mode、Claude Tag、Buzz 的防迴圈教訓）列在設計文件 §8 的「延伸」，不在 v1。
