# Phone push notifications (APNs) — spec

Date: 2026-10-09 · Owner: interface line lead (`mlab/purdex-88-b8`) · Status: draft for plan review

The daemon sends Apple push notifications to the Purdex iOS App, for the same things the Mac App raises a desktop
notification for, plus the approvals the phone can answer. The iOS side (permission, token registration, tap
handling, in-app banners) is built in the purdex-ios repo against this contract.

Facts the design relies on (measured 2026-10-09):
- The app is signed by a paid Apple Developer Program team (`5AJYV4QYHN`), bundle id `tw.protype.purdex`,
  entitlement `aps-environment=development`; Debug builds installed with ideviceinstaller get **sandbox** tokens.
- The APNs auth key is on mlab: `~/.config/apns/` (dir 700) holds `AuthKey_A5GMQX4588.p8` and `config.env`
  (600) with `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_KEY_FILE`. It is a team key; the topic (bundle id) is per request.
- go.mod has no JWT / HTTP/2 library and none is added: ES256 is `crypto/ecdsa` + `crypto/x509` (PKCS#8), and
  `net/http` negotiates h2 over TLS by itself.
- An approval auto-approved by unattended mode is created **already approved** and only broadcasts `closed`
  (`internal/module/team/unattended.go` `createApprovedLead` / `beginApproved`); an approval that waits for a person
  broadcasts `opened` (`handler.go`, `relay_handler.go`, `ask_handler.go` `openHookRow`).
- The Mac's rule for an agent notification is `spa/src/lib/notification-gate.ts` `shouldNotify` and its content
  `spa/src/lib/notification-content.ts` `buildNotificationContent`; §5.2 / §5.3 mirror both, except the
  `WorkerTerminated` case (workers are out of v1, §2).
- Every live `hook` host event goes out through one place, the agent module's emitter
  (`internal/module/agent/hookemitter.go`), whether the frame came from a hook, the mod stream
  (`modworker.go`), a sweep or a probe.
- `origin.tmux` of an approval is `"<session>:@<win>.%<pane>"` (`internal/team/wire.go`); tmux session names
  cannot contain `:`, so the session name is the part before the first `:`.
- The daemon builds with Go 1.26: `os.Root` (Go 1.24+) opens files that cannot leave a directory, symlinks included.
- `PUT /api/config` accepts only the fields its request type lists (`internal/core/config_handler.go`); a new
  `[push]` section is not writable through it unless added there.

## 2. Scope

In v1:
- Device registration API, stored per host.
- APNs sender (token auth, sandbox and production).
- Triggers: approval opened (R2, R3); agent hook events (R4) through the Mac's gate (R5) and Mac presence (R6).
- Mac presence reporting from the Mac App (SPA), needed by R6.

Not in v1 (follow-ups, each an issue):
- Workers (Nexen executions) — their events come from the nex projection, not the agent hook path. The phone gets
  their notifications only in the foreground (R9) until a follow-up adds them.
- Pushing from a26 / a19 (R1).
- Notification actions (R8), remote withdrawal on close (R7), time-sensitive entitlement (the payload asks for it;
  without the entitlement iOS shows it as an ordinary notification). (The badge spec adds one piece of R7: a silent
  *background badge push* when a card closes, §6, so the App-icon badge drops while the App is not running; removing the
  delivered notification itself is left to the phone's next foreground.)
- Changing the Mac's own notification content ("some content looks incomplete") — separate SPA PR once the cause is
  confirmed from an example; §5.3 is written so that fix and push share one content rule.

## 3. Configuration and capability

`config.toml` gets an optional section:

```toml
[push]
apns_dir = "~/.config/apns"   # holds config.env (APNS_KEY_ID, APNS_TEAM_ID, APNS_KEY_FILE) and the .p8
```

- Absent section or absent `apns_dir`: push is **off** — the module is not mounted, `push.v1` is not announced, the
  routes do not exist (404). Same pattern as `[nex]` (`cmd/pdx/main.go` registers the module only when enabled).
- Present: at Init the module opens `apns_dir` as an `os.Root` and reads `config.env` and the key file
  **through that root** (`APNS_KEY_FILE` is a name relative to the dir, or a `$HOME/…`, `${HOME}/…`, `~/…` or absolute path that resolves — symlinked directories compared resolved — to a file exactly one level below the dir; anything the root refuses — a path elsewhere,
  `..`, a symlink that leaves the dir, swapped between check and open), reads only those three keys (other lines
  ignored) and parses the PKCS#8 EC P-256 key. The key is never logged, returned, or copied. `~` is expanded.
- **A key that cannot be loaded does not stop the daemon** (push is not a required feature; a moved or damaged key
  file must not keep terminal management from starting). Any failure above, and a device store that cannot be opened,
  **soft-fails the module** (the `[nex]` pattern): the module stays registered, `Init` records the reason in
  `init_error` (never key material, never file content, not even the file name `config.env` asked for) and returns
  nil, the module mounts **no route** (404, as if push were off), announces nothing, creates no `push.db`, and does
  nothing at Start.
- **Boot-only.** `[push]` is read at daemon start; it is not added to `PUT /api/config` (changing it means editing
  `config.toml` and restarting). So "configured" is the same thing for the life of the process; "ready" is whether the
  module got its key at that start.
- `/api/info` gets a `push` block shaped like `nex`: `{configured, ready, init_error}` — `configured` is the core's
  (`[push] apns_dir` is set), `ready` and `init_error` are the module's own report (`ready: false, init_error: ""` for
  a daemon without `[push]`).
- `push.v1` is added to `/api/info` `capabilities` **only while the push module is ready** — the first conditional
  capability; `handleInfo` appends it after the static list when the module's status says `ready`.

## 4. Device registration API

All routes sit behind the daemon token like every other `/api` route.

### 4.1 `POST /api/push/devices` — idempotent upsert

```json
{
  "token": "<hex APNs device token>",
  "bundle_id": "tw.protype.purdex",
  "env": "sandbox",
  "platform": "ios",
  "device_name": "iPhone 8",
  "host_label": "mlab",
  "locale": "zh-TW",
  "prefs": {
    "agents": { "cc": { "enabled": true, "events": { "Stop": false }, "notify_without_tab": false } },
    "tabs": ["<session code>", "..."],
    "muted": ["<session code>", "..."],
    "badge_push": false
  }
}
```

- `token`: 64–200 hex chars (lowercased on store). `bundle_id`: must equal the configured topic list — v1 accepts
  exactly `tw.protype.purdex` (400 otherwise). `env`: `sandbox` | `production`. `platform`: `ios`.
- `device_name` ≤ 64 runes, `host_label` ≤ 32 runes (what the phone calls this host; used in titles, §6), printable,
  no control characters. `locale`: `zh-TW` | `en` (anything else stores `zh-TW`).
- `prefs` mirrors the Mac's `NotificationSettings` per agent type (`enabled`, `events` keyed by the normalised
  event name, `notify_without_tab`) plus `tabs`: the session codes this phone has open as tabs **on this host**
  (≤ 500). A missing agent type means the Mac default (`enabled: true`, no event off, `notify_without_tab: false`).
  `muted` (badge spec §3.1) are the session codes this phone muted: ≤ 500, validated like `tabs`; per phone, so another
  phone's mute never reaches this one. `badge_push` (bool) asks for the background badge pushes of §6; a phone sets it
  only on a host that lists `push.badge_bg.v1`. Both are optional JSON in the stored prefs (no migration); an older App
  sends neither, and a daemon older than this ignores them.
- The same token again replaces every field (last write wins) and bumps `updated_at`. Answer 200 with the stored
  row (token masked, §4.3) and its `device_id`: the first 16 hex chars of SHA-256 of the lowercased token. The
  token itself never appears in a URL.
- The phone re-POSTs on every launch, when the token changes, and when its tabs or settings change (debounced on the
  phone side; the daemon does not rate-limit beyond the body size cap of 64 KiB).

### 4.2 `DELETE /api/push/devices/{device_id}`

204 whether or not it existed. (By `device_id`, not the token: a token in a URL would reach traces and logs.)

### 4.3 `GET /api/push/devices`

For debugging: `{devices: [...]}` with `device_id`, `token` shown as its first 8 and last 4 chars
(`ab12cd34…ef90`), `env`, `device_name`, `host_label`, `locale`, `created_at`, `updated_at`, `last_sent_at`,
`last_error`, `tabs_count`. Never the full token — not here, not in an error body, not in a log line.

### 4.4 Storage

`push.db` in the data dir (own small store, like `hostconfig`), one table:

```sql
CREATE TABLE IF NOT EXISTS push_devices (
  token TEXT PRIMARY KEY, device_id TEXT NOT NULL UNIQUE,
  bundle_id TEXT NOT NULL, env TEXT NOT NULL, platform TEXT NOT NULL,
  device_name TEXT NOT NULL, host_label TEXT NOT NULL, locale TEXT NOT NULL, prefs TEXT NOT NULL,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  last_sent_at INTEGER NOT NULL DEFAULT 0, last_error TEXT NOT NULL DEFAULT ''
);
```

The module reads all rows into memory at Start and keeps the cache in step with every write; the send path never
touches SQLite.

## 5. Triggers and the gate

### 5.1 Approvals

- Source: a new narrow feed in `internal/team` registered in the Registry (like `ApprovalFeed`):
  `SubscribeApprovals(fn func(op string, a Approval)) (open []Approval, unsubscribe func())`. It takes the open
  rows and registers the subscriber **in one step under the team module's `eventMu`**, so no `opened` / `closed`
  falls between the snapshot and the first delivery (the push module rebuilds its open-`hook_ask` set from `open`).
- Delivery is a hub like `turnEndHub`: `broadcast` does only a non-blocking send on each subscriber's bounded
  channel (drops counted); the callback runs on the subscriber's own goroutine, **never under `eventMu`**. The hook
  and team handlers never wait for push, whatever the callback does.
- Push on `opened` when `kind` ∈ {`lead`, `self_relay`, `member_relay`} or (`kind == hook_ask` and payload `terminal_only` is false).
  `hook_permission` and `adopt` are not pushed in v1.
- Unattended auto-approvals never send (they never broadcast `opened`). An `opened` row that the unattended sweep
  approves later has already been pushed; that is accepted (the tap shows "already closed", §7).
- Approvals go to **every** registered device, regardless of tabs (the Mac raises them regardless of tabs), except R6:
  not pushed while a present Mac shows the approval's origin session (§5.4).

### 5.2 Agent events (mirror of the Mac's `shouldNotify`)

- Source: a new agent-module hub, built like `turnEndHub` (`internal/module/agent/turn_end_hub.go`), published from
  **the emitter's single `hook` broadcast point** (`hookemitter.go`) — so frames from hooks, the mod stream, sweeps,
  probes and detail-only updates are all covered — for **tmux** sessions only, as
  `{SessionCode, SessionName, SessionID, Event NormalizedEvent}` (the frame the `hook` host event carries).
  Non-blocking send to bounded per-subscriber channels (drops counted); subscribe-time replays (`Snapshot`) are not
  published.
- Evaluation, per event, in this order (normalised event name `ev`, derived status `st`):
  - **Event stage** (once per event):
    0. Fresh: `BroadcastTs` is greater than the last one seen for this session code (the Mac's persistent dedup; a
       sweep or probe that re-emits a frame does not push again). Seen timestamps are kept in memory; a daemon
       restart forgets them (no replays are published, so nothing old comes back).
    1. `st` ∈ {`waiting`, `idle`, `error`}.
    2. Not `detail.notification_silent == true`.
    3. Not (`st == idle` and `ev == Notification`) — informational notifications.
    4. Not R6: no present Mac shows the session (§5.4).
  - **Device stage** (per device; the devices that pass are the recipients):
    5. Device prefs for the agent type: `enabled`, and `events[ev]` is not `false`.
    6. `SessionCode` is in the device's `tabs`, or `notify_without_tab` is on for the agent type — **except** that a
       team member (below) needs the tab whatever `notify_without_tab` says.
    6a. `SessionCode` is not in the device's `muted` (badge spec §3.1). A muted session gets no agent push, tab or not.
       Approval pushes (§5.1) ignore `muted`: a card is something the person must act on.
  - **Membership** (badge spec §3.1), read **once per event**, before the device loop, only for events that can push
    (rule 1). A session is a *team member* when `team.MembershipReader.Membership(SessionID)` says so: its id is (a) a
    local member row (a seat running on this host, never a lead) in state `active` of a team whose `ended_at = 0`, or
    (b) an `active` remote member row (adopted by a lead elsewhere, running here). A lead is not a member, an event
    with no session id is not a member, and no team module means no members. The agent push of a member carries
    `purdex.member: true` (§6). **A read error is "member, unknown"**: rule 6 applies the member rule (the quieter side)
    and the payload leaves `member` out, so the phone counts the event (an over-count beats a silent miss). The read
    runs on the agent hub's subscriber goroutine (a 64-event queue that drops when full), so it is bounded: one read at
    a time, an event waits at most 250 ms; a read that is late, or still outstanding from an earlier event, counts as
    an error ("member, unknown").
  - **Send stage** (once per event, only if at least one device passed):
    7. `st == error`: the daemon-wide error debounce passes — key (session code, `ev`, error string), trailing-edge
       sliding 60 s window, same as the Mac (`ERROR_NOTIFY_WINDOW_MS`), at most 1000 keys (oldest evicted). One
       evaluation per event, so every recipient of that event gets it and the next identical error is silenced for
       all of them.
    8. Not a duplicate of an AskUserQuestion push. A `waiting` event is **held 2 s** before this stage (the
       `hook_ask` `opened` comes through the team feed, which is not ordered with the agent hub). The push module
       keeps, per session, the interval each answerable `hook_ask` was open, `[opened_at, closed_at)` (still open =
       up to now; kept for a minute after it closes). The event is skipped only if **its own window** — from its
       arrival to the end of its hold (arrival + 2 s) — **overlaps** one of those intervals. An ask that was opened
       and answered before the event arrived does not hide it (the user answers on the phone, the agent goes on and
       asks for a permission a moment later: that one needs them). "Same session": the `hook_ask` origin's
       `session_id` equals `SessionID`, or its tmux session name (§1) equals `SessionName`. A `terminal_only` ask is
       not pushed and does not count.
    9. Content exists (§5.3 returns one).
- Rules 1–3, 5–7 are the Mac's (6 gains the member rule; 6a is new); 0 is the Mac's dedup; 4 replaces the Mac's "the window is focused and shows it";
  8 exists because the phone also gets the `hook_ask` push.

### 5.3 Content (shared with the Mac's rules)

Same cases as `buildNotificationContent` minus `WorkerTerminated` (workers are out of v1); the title is the
session's name:

| `ev` | body |
|------|------|
| `Notification` | `detail.message`, else by `notification_type`: `permission_prompt` → 「需要授權核准」, `elicitation_dialog` → 「需要輸入資訊（MCP）」, else 「新通知」 |
| `PermissionRequest` | 「需要授權：{tool_name}」 (no tool → 「需要授權：未知工具」) |
| `Stop` | `detail.last_assistant_message`, else 「任務完成」 |
| `StopFailure` | `detail.error_details`, else `detail.error`, else 「任務異常中斷」 |
| other | no push |

Then the body is normalised for a lock screen: Markdown markers (`**`, `__`, backticks, leading `#`, `>`, list bullets,
link syntax → its text) stripped, runs of whitespace and newlines collapsed to one space, cut at 240 runes with "…".
The strings are the zh-TW / en values of the SPA keys `notification.*` (the daemon keeps its own copy for both
locales, chosen by the device's `locale`). The Mac's own content fix will adopt the same normalisation in the SPA.

The session's name: the tmux session name the sessions list shows for `SessionCode`; else the code.

### 5.4 Mac presence (R6)

- `PUT /api/push/presence` (token-authenticated), body ≤ 16 KiB (`http.MaxBytesReader`, 413 over),
  `{client_id, active, sessions: [{code, name}, ...], ttl_ms}`:
  - `client_id`: the Mac window's id (the SPA's client identity plus the window id), 1–64 printable chars.
  - `active`: the window has focus **and** saw user input (key, pointer, wheel) in the last 120 s.
  - `sessions`: the sessions **on this host** shown in the active tab's panes (every pane, as
    `isAgentVisibleInActiveTab` counts them), each with its session code and its tmux session name; ≤ 200.
  - `ttl_ms`: 1000–60000; the daemon forgets the entry after it. Answer 204.
- Bounds: at most 64 entries. Every PUT first drops expired entries; a new `client_id` when 64 live entries exist
  replaces the one that expires soonest. (Anyone holding the daemon token can already do anything the API allows;
  the bounds keep a buggy client from growing memory, they are not an access control.)
- The SPA sends it to each connected host that announces `push.v1` (each host gets only its own sessions) on change
  and every 20 s while `active`, with `ttl_ms: 45000`; when it stops being active it sends once with
  `active: false`. A closed window simply expires.
- "A present Mac shows session X" = some unexpired entry has `active: true` and X among its `sessions`:
  - for an agent event, X matches by session code;
  - for an approval, by the tmux session name taken from `origin.tmux` (the part before the first `:`, §1); an
    approval whose origin has no tmux is never suppressed.
- Kept in memory only; lost on daemon restart (a Mac re-sends within 20 s).

## 6. APNs payload

```json
{
  "aps": {
    "alert": { "title": "...", "body": "..." },
    "sound": "default",
    "thread-id": "<host id>",
    "interruption-level": "time-sensitive",
    "mutable-content": 1
  },
  "purdex": { "host_id": "...", "kind": "...", "approval_id": "...", "session_code": "...", "session_id": "...",
              "session_title": "...", "event": "...", "member": true, "open_approvals": 2,
              "open_approval_keys": ["a:ap-9", "c:3f2a…", "s:c0de01"] }
}
```

- `aps.mutable-content: 1` is on every push, so the iOS Notification Service Extension (NSE) runs.
- `purdex.member` (`true`, or absent) is on an agent-event push of a team member (§5.2 membership), so the phone does
  not count its unread event. Absent means not a member **or unknown** (a failed read); it is never sent as `false`.
- `purdex.open_approvals` (an integer, 0 is valid) is the number of **cards the badge counts** open on this host when
  the push is sent (badge spec §3.1, `push.CountsForBadge`): every open approval of kind `lead`, `self_relay`,
  `member_relay`, `adopt`, `hook_ask` (terminal-only included) or `hook_permission` — whether or not it got a visible
  push (§5.1 still decides that alone), including the one being pushed when it is an approval push; agent-event
  pushes carry it too. It is present when the
  daemon read the open set for this push; absent means unknown (the NSE keeps that host's last known value). The
  daemon reads it from the team store at send time and keeps no counter, so it cannot drift; if the read fails (or no
  reader is wired) the field is left out, never sent as 0. Why: the app-icon badge is the open approvals (summed over
  hosts) plus phone sessions with unread events, and while the App is not running the NSE updates it from each push.
- `purdex.open_approval_keys` (an array of strings) names WHICH sessions have those open approvals, so the badge counts
  sessions, not items: `"s:<session code>"` when the approval's tmux session resolves to a session code, else
  `"c:<origin session id>"` when the approval has an origin Claude Code session id of at most 64 bytes (several cards
  of one unresolved session count 1; a longer id is not a real one — a UUID is 36 — and would push every payload of the
  host past 4 KiB while the card is open, so that card keys by its own id instead), else `"a:<approval id>"` (an approval with neither counts 1 on its own). It is built
  from the same read as `open_approvals`, de-duplicated, sorted, and capped at 32 keys (`open_approvals` still reports
  the full count). Present only when `open_approvals` is; absent = unknown, never `[]` for a failed read. The NSE counts
  the union of the `s:` and `c:` keys with its own unread sessions, plus the `a:` keys (a key of a prefix it does not
  know counts like an `a:` key, so a newer daemon never makes the App under-count).
- `GET /api/info` lists the capability `push.badge.v2` (same condition as `push.v1`) for: the badge kinds, `c:` keys,
  `purdex.member`, the member rule of §5.2 and `prefs.muted`.
- Approval pushes carry `purdex.session_code` when the origin's tmux session resolves (agent-event pushes always
  did), so the phone opens the right tab without a GET; absent when it cannot be resolved.

Headers: `apns-topic: tw.protype.purdex`, `apns-push-type: alert`, `apns-priority: 10`, `apns-expiration: now + 1 h`,
`apns-collapse-id`: the approval id for an approval; `agent-<session code>` for an agent event (a newer event of the
same session replaces the older one on the phone). Push type and priority are per notification; these are the visible
push's, and a background badge push (below) sets its own.

### 6.1 Background badge push (`push.badge_bg.v1`)

Badge spec §3.1. When an approval whose kind `push.CountsForBadge` names reaches `closed` — by whatever path: decided,
timed out, lease expired, answered locally, terminal override, dismissed; the team module broadcasts one `closed` for
all of them — the devices with **`prefs.badge_push: true`** get a silent push, so their App-icon badge drops while the App
is in the background. (Best effort: iOS may delay a background push, and a force-quit App receives none; the next
foreground corrects the badge.) An `opened` approval never triggers it, and neither does a kind the badge does not count.

- **Coalescing** sits before the sender queue. The first close of a burst opens a **fixed 2 s window** (not sliding, so
  the latency is bounded); closes inside it only add their ids; when it ends, one `badge` job is enqueued. The job reads
  the open set when the sender processes it (the freshest value) and **sends nothing if that read fails**. A full queue
  drops the job with a log line. `Stop` cancels a window that has not ended. Devices are chosen when the window ends, and a
  device whose `badge_push` was switched off since is skipped when the job runs.
- **Headers**: `apns-push-type: background`, `apns-priority: 5`, `apns-expiration: now + 1 h`, no `apns-collapse-id`.
- **Body**: `{"aps":{"content-available":1},"purdex":{"kind":"badge","host_id":…,"open_approvals":n,
  "open_approval_keys":[…],"closed_approval_ids":[…]}}`. No `alert`, `sound`, `mutable-content`, `badge` or `thread-id` in
  `aps`. `open_approvals` / `open_approval_keys` are as in the list above.
- **Size**: `closed_approval_ids` holds at most 16 ids (the first 16 closed; the rest are left out, and their delivered
  notifications are cleared at the next foreground). The payload stays ≤ 4096 bytes with 32 keys of maximum length plus
  16 ids; the builder drops ids before keys if it ever would not, and keys only when no id is left.
- `GET /api/info` lists `push.badge_bg.v1` (same condition as `push.v1`). A phone sets `badge_push: true` only on a host
  that lists it.

| trigger | title | body | `purdex.kind` |
|---------|-------|------|---------------|
| `lead` | 「{host}：{session} 申請成為 lead」 | the lead's `reason` (normalised as §5.3) | `lead` |
| `self_relay` | 「{host}：{session} 申請接力（已用 {pct}%）」 | 「核准後這個 session 會寫接力檔、清空並在原處接手（約 1 分鐘）」 | `self_relay` |
| `member_relay` | 「{host}：{lead} 要幫 member {member} 接力（context {pct}%）」 | 「member 額度用完，要核准嗎？」 | `member_relay` |
| `hook_ask` | 「{host}：{session} 在等你回答」 | the first question's `question` text (normalised) | `hook_ask` |
| agent event | 「{host}：{session}」 | §5.3 body | `agent` (+ `event` = `ev`) |

- `{host}` is the device's `host_label`; `{session}` is the origin's title, else name, else ref for approvals
  (as the Mac's approval title), the session name for agent events. `{pct}` is `used_percentage` rounded.
- en strings are the SPA's `approval.notify.*` en values; the `hook_ask` and agent-title strings are new keys in both
  locales (daemon side only in v1).
- The payload stays under 4 KiB: the body is already ≤ 240 runes; titles are cut at 120 runes.

## 7. Sending

- One sender goroutine per module with a bounded queue (256); triggers enqueue and never block (a full queue drops
  and counts). Each job fans out to the matching devices.
- Token auth: JWT header `{alg: ES256, kid: <key id>}`, claims `{iss: <team id>, iat: <now>}`, signed with the .p8;
  cached and reused for 40 minutes (Apple: not more than once per 20 minutes, valid for an hour).
- Host by the device's `env`: `api.sandbox.push.apple.com` / `api.push.apple.com`, port 443, HTTP/2, one shared
  client, 10 s per-request timeout.
- Answers:
  - 200: record `last_sent_at`.
  - 410, or 400 with reason `BadDeviceToken` / `DeviceTokenNotForTopic`, or `Unregistered`: delete the device.
  - 403 `ExpiredProviderToken` / `InvalidProviderToken`: drop the cached JWT, retry once.
  - 429 / 5xx / network error: one retry after 2 s; then record `last_error` and give up.
  - other 4xx: record `last_error` (APNs `reason`), no retry.
- Logs carry the masked token, the APNs reason and the apns-id; never the full token, the JWT or key material.

## 8. iOS responsibilities (contract only; built in purdex-ios)

- Ask for notification permission; register for remote notifications; POST §4.1 to every host that announces
  `push.v1`, on launch, on token change, and when tabs / notification settings change; keep the returned
  `device_id` per host and DELETE `/api/push/devices/{device_id}` when a host is removed.
- A notification settings page mirroring the Mac's (per agent type: on/off, per event, notify without a tab).
- Tap: `purdex.kind` approval kinds → GET `/api/team/approvals/{id}`; open → the approval card; closed → toast
  (「…的申請已結束（狀態）」). `hook_ask` → the conversation's command view (the dock shows the question).
  `agent` → that session's tab.
- Foreground: suppress the system banner and show the in-app banner (R9) unless that session is on screen.
- NSE: set the badge from `purdex.open_approval_keys` (session keys unioned with unread sessions, plus `a:` keys; per host, summed over hosts), falling back to `purdex.open_approvals` when the keys are absent; a push without it (an older daemon,
  or a daemon whose read of the open set failed for this push) means "unknown" for that host - keep the last known
  value for it.
- Clear delivered notifications of approvals that closed, when coming to the foreground (R7).
