### WWD-5 — labels, qualification, reuse (A4)
Decisions of 10-19 (lead, from spec D10, §4.5, §7) are in the spec text; the split below applies them. Code starts after C2.
- **5a** (done, 1d) automatic labels and fingerprints from facts.
- **5-0** (≈250 lines) host store schema 6 (v5 is 8a's `wwd_starts`/`alerts`), **migration** (schema 5 is what 755 deploys; `.backup` of `wwd.db` on the four hosts first):
  `earned_labels (label PK, fingerprint JSON, snapshot, granted_ms, state earned|quarantined)` and
  `result_cache (key PK, rec JSON, host, host_fingerprint JSON, label, created_ms)`. `task_outcomes` is **not** here: it comes with
  5c-2 in its own migration (its shape depends on how the disagreement read is built).
- **5b-1** (≈450) earned labels join the host's advertised labels (only `earned`; a `quarantined` one is not advertised); every wwd
  advertises `host:<alias>`; a change sends a `labels` event; `pdx wwd labels` lists earned and quarantined with their fingerprints.
  The reference host holds `task:<repo>/<task>` without qualifying when it has the task's `repo:` and `tool:` labels.
- **5b-2** (≈650) qualification: queued automatically into the queue of the host that lacks the label (`dev` class; conditions
  and rate rule in spec §7), plus `pdx wwd qualify <repo>/<task>`. Both halves at the same snapshot with the `qualify` args, one
  for the host and one for the manifest's `reference`; the comparison (same pass/fail sets and exit state) is a pure function.
  A pair counts only when `result.host` of each half is the host it was meant for (the origin does not check labels at claim);
  otherwise it is void. Mismatch: no label and no exception (it only records `qualify_attempts` and the retry waits), retry after a fingerprint change or 24 h. A qualification job is
  never answered from the result cache. Add `qualify` to purdex's `tsc` task (SPA) beside the existing `spa-related`.
  Split into **5b-2a** (pure: the trigger rules and the pair comparison, `internal/wwd/qualify`), **5b-2b** (the coordinator library:
  submits the two halves, settles them, grants the label) and **5b-2c** (everything that starts it: the automatic trigger wired to the
  facts cadence, `POST /v1/qualify` and `pdx wwd qualify`; the first PR that makes a production host start a pair).
  **5b-2b is dormant**: it adds the coordinator and its tests and wires nothing: `cmd/wwd` does not construct it, no trigger is
  registered (not on the facts cadence, not at start-up), and no route can start a pair. A test pins that nothing in the daemon's
  options or routes reaches it, so 5b-2b alone deployed has no way to submit a pair or grant a label.
  **5b-2c must fill `qualify.Task.DefHash` from the parsed manifest's `Task.DefinitionHash()`** (the clone's `Source.Tasks`): the
  coordinator compares the task's identity again when a pair is done, so a result of an older definition (run, cwd, env, summary, qualify
  args) never earns the label. `Check` refuses a task with an empty `DefHash` (nothing is queued or granted), so a missed hookup fails
  closed; 5b-2c's tests must show that a change to a non-qualify field of the manifest changes the `DefHash` the source reports.
  **Digest dependency (lead, 10-20): 5b-2c must not go out before the passed-test digest does.** `wire.Summary` carries the number of
  passed tests, not which ones, so two hosts that ran different tests and passed as many cannot be told apart; 5b-2a compares counts and
  says so in the code. The digest closes it, in two releases because the decoders are strict (`docs/wwd-deploy.md` §5): **5b-2r** (the
  readers: `Summary.passed_digest`, `wire.Proto` 3, the comparison that treats a missing digest on either half as a mismatch) goes out
  and is on every wwd and both Purdex daemons first; **5b-2w** (the writers: the three summary parsers fill it, only while
  `wire.PoolAtLeast(peers, 3)` holds) goes out one release later. 5b-2c waits for 5b-2w. If the digest is late, 5b-2c is.
- **5c-1** (≈350) drift: each facts sample compares the stored fingerprint of an earned label with the current one for the tools
  and OS version that label needs; a difference revokes it, sends the event, queues re-qualification, and calls the reuse
  invalidation (a no-op until 5d-1). A reference host's drift invalidates only its own entries.
- **5d-1a** (≈300, no label store needed) the cache key and the lookup as pure functions: spec §4.5 key, and the four lookup
  conditions each with its own named test (the host-validity condition takes the earned-label state as an argument).
- **5d-1b** (≈300, after 5b-1) the `result_cache` read/write, the host-validity check against the real earned labels,
  invalidation by label, 10,000 entries (oldest out; equal `created_ms` broken by key, so the choice is stable).
  **Retention** (lead, 10-19): an entry lives 3 days, the log retention (`queue.logRetention`); the log is not kept longer and the
  cache keeps no copy of it. A test pins `cache retention ≤ log retention ≤ job retention`, so it goes red when any of the three
  is changed.
- **5d-2** (≈400) submit-time lookup: a `cacheable`, non-local, non-qualification job is answered from an entry as a `succeeded`
  record with `cache_hit: true` and the original log; otherwise queued, and a `succeeded` result is stored. `pdx test --no-cache`.
- **5c-2** (≈550, last) disagreement: `task_outcomes` (own migration), the origin records outcomes and offers the disagreements
  that concern a host on a pool read (a new read-only GET, strict as §14a; attack review looks at it); each wwd reads it at the
  facts cadence and quarantines its own label with an exception; `pdx wwd` can quarantine/release on the local socket only.
  Only the same origin's outcomes are compared (stated limit).
- Order: 5-0 → (5b-1 ‖ 5d-1a) → 5d-1b → 5b-2 → 5c-1 → 5d-2 → 5c-2. About 3100 lines, 9 PRs, each ≤800.
- Tests: a hit only for the same os / arch / toolchain / definition hash and only when `result.host` meets the lookup
  conditions; a darwin result never answers a job that names `os:linux`; only `succeeded` is stored; drift invalidates entries;
  a void pair gives nothing; a member's result on a qualified mserv answers a lead re-verification on mlab.
  Named tests for the rules that bound work and storage: at most one unfinished pair per (host, task) with two automatic
  triggers racing; the automatic retry after a mismatch or a void pair waits (23:59:59 no, 24:00:00 yes) unless the fingerprint
  changed, and `pdx wwd qualify` does not wait; the reference host holds the label without a pair; the 10,000th entry stays and
  the 10,001st pushes out the oldest (and the same `created_ms` picks the same one every time); an entry never outlives
  its log or its job (the retention ordering test above); a hit just before and just after day 3.
- Acceptance (real hosts): mserv earns purdex's A-grade labels (`spa-related`, `tsc`, reference air26) without a person; a lead
  re-verification on mlab of a member's job that ran on mserv hits the cache. The PHP labels are checked in 6d.
- **Trust (decided 10-19)**: the origin cannot tell which host a claim came from (one pool token; `ClaimRequest.Worker`, which
  becomes `result.host`, is the claimer's word), so qualification, earned labels and reuse are correctness mechanisms among our own
  hosts, not a boundary against a malicious token holder (spec §11). 5b-2 does not wait for per-host tokens (#3392, Backlog).

#### WWD-7 design (B line, 10-19; design page `pages.mlab.host/wake/purdex-b-line/wwd7-design.html`)

**Scope.** The Mac App (SPA) only. iOS is out of scope and gets its own task later.

**Principles.**
- *Same look, new source.* Host cells, the hover card, the host tab's gauges and charts keep today's look and read
  `/api/pool/*`. New facts (worker, headroom, owner, exceptions, process owners, residents) go into the existing blocks.
- *One judgement, one place* (D2). Headroom reasons and the cell ring's load score are computed once, in Go, by the
  Purdex daemon and served on `/api/pool/hosts` (#3478, capability `pool.assess.v1`): per host
  `headroom_reasons: {heavy: [...], light: [...]}` with the codes `worker_off`, `zone_warning` / `zone_danger` /
  `zone_unknown`, `exception:<name>`, `owner_active`, `slots_full`, `gate_full` in spec §3.2 order, and
  `load: {score: 0–100, driver: cpu|mem|pressure|paging|disk}` (`internal/fleet/load.go`). The App only turns codes
  into words. #3478 (with its spec §3.2 notes and its fixture) is the contract for these shapes: 7a-1a types them from
  that fixture as optional fields (its PR being open is enough), and an unknown code is shown as is, never an error.
- *wwd down is not host offline* (spec §10). A host the pool cannot read but the fleet still reads over SSH is shown
  with the fleet's readings and a "wwd 沒有回應" line, never dimmed.
- *A zero always says why.* Headroom 0 shows its reason (e.g. air26 today: the gate's slots are held, #3450).

**One host state** — `lib/pool/host-view.ts` `poolHostView(poolHost, fleetView, now)`; every surface reads it.

| State | When | Readings | Cell | Card / Hosts page |
|---|---|---|---|---|
| live | pool `reachable` and facts not null and `facts.at` within 30 s | pool facts | as today | worker, headroom, owner, sessions room |
| fallback | pool unreachable, stale or not listing the host, and the fleet host `status: ok` in a fleet snapshot that is not stale (`useFleetStore` `stale` false; the store keeps its last snapshot, so `ok` alone is not enough) | fleet `fast` | as today, not dimmed | "wwd 沒有回應（hh:mm 起）"; worker and headroom "不明"; sidebar dot yellow |
| offline | neither reads it | none | badge 40 %, ring track only | "離線" + the newer last-ok of pool and fleet |
| old daemon | no connected daemon announces `pool.v1` | fleet | today's UI | one notice in the Hosts page section |

Zone words keep 正常 / 偏高 / 過載 and add 未知 (`unknown`, text-muted). Pool host ↔ fleet host is matched by alias
(daemon hosts also by `host_id`).

  null), Session (`sessions_room`); the "等待主方 / 主方不在這台 App" lines go. Linux hosts add PSI some10/full10 after

  session; ties by `created_at`; manual `back` after them by `manual_seq`; `hold` last and dimmed. Each card shows

**Data flow and cadence.**
- Hosts: `GET /api/pool/hosts` from the first connected daemon (host order) announcing `pool.v1`
  (`useNexHostStore` `daemonCapabilities`); a failure is handled by the error table (next daemon or the same one
  again); every 5 s; **paused while `document.visibilityState` is `hidden`, read at once when it turns visible, then
  polled again** (7a-1b). When the source daemon announces `pool.events.v1` (#3479: `pool.changed`, merged per host
  within 2 s) the poll stops and the App reads on each `pool.changed`, on host-events reconnect and on turning visible
  (7a-1c); losing the capability (another source) brings the poll back.
- Fallback readings and the gate: the fleet store as today, until WWD-9.
- Jobs: per origin `GET /api/pool/jobs?host=<origin>&after=<cursor>`, from the origin's own daemon when the App is
  connected to it (only it lists fast-lane and ad-hoc jobs), else forwarded through the pool daemon (spec §4.4):
  - the first read of an origin is `after=0&limit=1000`, page after page until a page is shorter than the limit (as the
    daemon's own catch-up does, `internal/module/jobs/events.go`); keep every job not yet ended and the newest 200
    ended ones; keep `{epoch, cursor}` from the last page;
  - every later read is `after=<cursor>`; a job that comes again (a log uploaded after it ended) replaces its copy by
    id; an answer whose `cursor` is empty keeps the previous cursor;
  - `cursor_ahead` (409) or another `epoch`: drop that origin's jobs and read from 0; the App keeps nothing across a
    restart, so a restart also reads from 0;
  - `jobs.changed` → re-read that job; host-events reconnect → read after the cursor; origins without a daemon
    (whose queues no daemon announces) are polled every 10 s while the jobs tab or a host tab is visible. Read
    through `?host=`, those lists are the peer view (no fast-lane or ad-hoc jobs), as expected.
- History: 5 min from `/api/pool/facts/history?step=5s`; longer ranges in memory until `pool.series.v1`, then
  `GET /api/pool/facts/series?host=&since=&step=` (points carry `at`, `zone`, `cpu_idle_pct`, `mem_available_mb`,
  `pressure`, `page_out_rate`, `disk_max_used_pct`, `headroom`; memory % takes `total_mb` from the host's facts).
- Detail and log: on open, again on that job's terminal `jobs.changed`; never polled.
- Changes: `PUT /api/pool/hosts/{alias}/worker`, `POST` / `DELETE …/exceptions`; never cached; the next facts decide.
