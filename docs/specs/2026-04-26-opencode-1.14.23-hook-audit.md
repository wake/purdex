## 2. Bus events full list

**Source**: `packages/opencode/src/**` — 48 distinct event keys（含 41 個 `BusEvent.define` + 7 個 `SyncEvent.define` runtime bus-register；`global.disposed` 重複 define 但 last-write-wins）。

**Bus abstraction**:
- Define API: `BusEvent.define(type: string, schema)` (`bus/bus-event.ts:10`)
- Publish APIs: 3 mechanisms (重要 — 非全部都進 typed `Bus.subscribe(def, cb)`):
  1. `bus.publish(def, props)` — typed Bus → 進 typed pubsub + SSE
  2. `GlobalBus.emit("event", { payload })` — bypasses typed Bus → **typed `Bus.subscribe(def, cb)` 收不到，但 `subscribeAll()` 收得到**
  3. `PubSub.publish(wildcard, ...)` (僅 finalizer use) — wildcard only
- Subscribe (Purdex 用): `bus.subscribeAll()` (plugin/index.ts:248) → 收所有三種

**Implication for Purdex**: Since Purdex's `event:` hook 走 `bus.subscribeAll()` fan-out, Purdex **可以收到所有 48 個 events**（包含 GlobalBus-only 的 `worktree.*` / `project.updated` / `workspace.*` 等）。但 catalog manifest 仍須 per-event 標註 publish mechanism（type-only / global-only / mixed）以 future-proof（若日後改用 typed `Bus.subscribe(def, cb)`，會錯過 GlobalBus-only 事件）。

### 3.1 Decision 1 — `chat.message`

**驗證結果**: Strong hook only（NOT a Bus event）。Single live `plugin.trigger("chat.message", ...)` callsite at `session/prompt.ts:1237`。`grep BusEvent.define ".*chat" + bus.publish.*chat.message` 全 zero results。

**Decision**: **retain** — 維持現有 strong hook 訂閱方式

**Rationale**: 
- 上游 `chat.message` 為 strong hook（不是 Bus event）— audit 確認
- Purdex 端已正確用 strong hook key — 程式碼確認
- 1 callsite 穩定，payload (sessionID + messageID + agent + model + variant) 充足支撐 UserPromptSubmit
- 無 deprecation marker

**Triggers template change?**: **No** — Purdex template 已正確；不需動 §2.5 plugin template

### 3.3 Decision 3 — `session.idle`

**驗證結果**: 
- Definition: `session/status.ts:37` 帶 `// deprecated` (line 36)
- Publish: `session/status.ts:75` — fired only when `status.type === "idle"` inside `set()`，與 `session.status` 同一 code path（先 publish Status，再 publish Idle if idle）
- 實際是 `session.status({type:"idle"})` 的 strict subset

**Decision**: **switch** — Purdex template 換訂閱 `session.idle` → `session.status` filter `{type: "idle"}`

**Rationale**:
- 跟著上游 explicit deprecation migration path = 架構正確性（canonical event 取代 deprecated subset）
- 單一 code path，無 Map / 無 dedup logic / 無 OC1c test → 不膨脹
- dualSubscribe 的「resilience」**不對稱**：只擋上游無 deprecation notice 直接移除 `session.idle` emit 的低機率場景；擋不了 `session.status` 自身語意變化
- 真正的版本漂移防線是 Phase 4a-style audit cycle（per minor version refresh）+ `events.json` catalog freeze，不是 plugin 內 dual-path defense

**SupportedVersion 是 observability indicator，不是 install gate**:
- 今日行為：`internal/agent/opencode/hooks.go` 的 `CheckHooks` 比對 live `agent --version` 與 audit-frozen 1.14.23，超出時回傳 `ExceedsSupport=true`；SPA Settings → Hosts → Hooks card 顯示一條黃色警告。**Install 與 check 路徑照常進行**，不會被擋下。
- 真正的失敗模式：若上游在未來某 minor version 直接移除或改名 `session.status`，Purdex 仍會 rewrite 同一份 JS template，`if (status.type === 'idle')` 永遠不命中，Stop 不再 emit，session 視覺上卡在 Running。SupportedVersion gate 的黃色警告不會阻止這個漂移發生。
- 今日存在的緩解：`events.json` catalog freeze（plan v1.3 §2.4 的 manifest）+ HC5 / HC5d catalog 對齊測試會在 audit 時抓到上游 schema 變動 — 是 audit-time guard，不是 runtime guard。觸發機制是「跑下一輪 minor version audit」，不是「使用者升級時自動擋下」。
- 未來方向：把 ExceedsSupport=true 升級成真正的 install hard-gate（CheckHooks 回傳 `Installed=false` / InstallHooks 拒寫 plugin / SPA 渲染 blocking state）追蹤於 [issue #665](https://github.com/wake/purdex/issues/665)。本 PR-4a-0 不在範圍內。

**為何不選 dualSubscribe**:
- 觸發 `feedback_skeleton_convergence.md` 「parallel registry」bloat 徵兆 — 兩條 subscription path 對應同一邏輯事件
- 永久複雜度（Map + dedup function + OC1c test）換取低機率場景 + 不對稱防護
- 違反「跟著上游 migration path」的架構意圖

**Triggers template change?**: **Yes** — Commit 5 必須執行（plan v1.3 §2.5 條件 (5) 不成立 — `decision !== "retain"`）

**Plan v1.3 §6 H6.4 (d) 對齊**: `decision: "switch"` → `switchTarget: "session.status({type:\"idle\"})"` 必填 + `templateConsumesAt` 同步更新指向新鍵 + OC1 期望值更新

**Catalog 雙邊變更**:
- `session.idle`：原 installable (Stop) → 改 `ignored`，reason 標 "superseded by session.status({type:idle}) per Decision 3 switch"
- `session.status`：原 unsupported → 改 installable (Stop)；events.json 加 `notes` 欄說明 plugin 內的 payload filter `status.type === "idle"` + busy/retry 變體 receive-but-no-op (per Decision 4 defer)

### 3.4 Decision 4 — `session.status` non-idle

**Type definition** (session/status.ts:10-23):
```ts
Info = idle | retry { attempt, message, next } | busy
```

**Per-variant**:

| Variant | Emit sites | Semantic | Purdex mapping |
|---|---|---|---|
| `idle` | status.ts:73 (every set call) + then 75 (idle special) | session 進入 idle | (covered by Decision 3) |
| `retry` | processor.ts:572-577 inside `Effect.retry` policy | LLM transient failure + auto-retry | **detail** preferred (surface "Retrying attempt N: <msg>") OR `ignored` fallback |
| `busy` | processor.ts:219, run-state.ts:60, prompt.ts:1317 | session 在處理（LLM 生成 / tool 執行 / 步驟間） | **status: Running** (cleanly) |

**Decision**: **defer adoption** — busy/retry 變體 receive-but-no-op 在 Decision 3 switch 後的新 plugin handler 內

**為何 defer 而非採用（不是「schema 不夠」是「現在沒有使用者價值」）**:

| 變體 | 採用價值 | 何時應採用 |
|---|---|---|
| `busy` | **0** — Purdex 已有 `chat.message` strong hook 作為 Running trigger；busy 在每次 runLoop iteration（processor.ts:219 + run-state.ts:60 + prompt.ts:1317）都 fire，是高頻 redundant signal，對 frame state machine 是噪音不是新資訊 | 永遠不採用，除非未來 chat.message 失效 |
| `retry` | **0 (no UI surface)** — 三欄資訊 (`attempt` / `message` / `next`) 是有用 telemetry，但需 Dev Inspector / status line UI 才能轉為使用者價值；無 UI 之前 catalog 條目是 dead weight | Dev Inspector / status line 加 retry 顯示時 |
| `idle` | (由 Decision 3 處理) | — |

**Catalog handling**:
- `session.status` 已被 Decision 3 switch 改為 installable（Stop，filtered to `idle` 變體）
- busy/retry 變體在 plugin handler 內 explicit no-op (`if (status.type !== 'idle') return`)
- events.json 對 `session.status` entry 的 `notes` 欄記錄三變體處理：`idle → emit Stop`、`busy → no-op (redundant with chat.message)`、`retry → no-op (no UI surface)`
- 不擴 catalog schema、不加 synthetic keys（per 不膨脹原則 — 沒使用者價值前不預建抽象）

**未來 adoption trigger 條件**（建獨立 gh issue 追蹤）：
- busy: 若 `chat.message` strong hook 在某 OpenCode minor version 失效，busy 為 fallback Running trigger 候選
- retry: 當 Purdex 加 Dev Inspector / status line retry 顯示 UI 時，採用 retry → detail mapping（需擴 catalog schema 加 sub-typing 或 synthetic key `session.status.retry`）

**Triggers template change?**: **No new template change beyond Decision 3 switch**（Decision 3 switch 後 plugin 訂閱 `session.status`，內含 `if (idle) emit Stop` filter；busy/retry 自動 no-op，不需額外 case branch）

## 7. Audit notes & uncertainty

### 7.1 高信心發現

### 7.2 GlobalBus-only / SSE-only 發布機制
- 7 events 走 `GlobalBus.emit` only（`worktree.*` / `project.updated` / `workspace.restore` / `workspace.status` / `global.disposed` + partial `server.instance.disposed`）— typed `Bus.subscribe(def, cb)` 收不到，但 `subscribeAll()` 收得到

- **Purdex 用 `bus.subscribeAll()` 都收得到** — 但 events.json 必標 `publishMechanism` 欄 future-proof

### 7.3 Subagent 推測的 false positive（已澄清）

### 7.4 不確定 / out-of-scope
- `tool.execute.after` cancellation gap：TaskTool path interrupt 時不 fire after-hook（lines 630-649 in prompt.ts）；其他 tool path（custom + MCP）的 cancellation 行為未完整驗證；對 Purdex `SubagentStop` 影響：cancelled subagent 的 activeSubagents Map entry 不會清，需 periodic GC（**out of PR-4a-0 scope；建獨立 issue 追蹤**）
