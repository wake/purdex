派工架構 · 合成檢討

ai-coop 的委派 × Purdex M0 的派工

兩套系統在做同一件事的兩個切面：把一段人的意圖交給 agent 去跑，並把過程與結果收回來。 coop 走「對話驅動的即席委派」，Purdex M0 走「工單驅動的非同席派工」。 這頁把兩邊的機制逐軸攤開對照，找出可以互相移植的資產與各自的結構性缺口。

結論先講。coop 已經把「一次委派的執行期語意」做得比 Purdex M0 完整——對話續接（--resume）、增量餵食（watermark）、過程步驟流（agent_steps）、中斷雙層保險四項都是現貨，而這四項正好是 Purdex M1／M1.5 的清單。 反向，Purdex 已把「跨行程／對外可稽核」的地基做完——穩定 handle、原子 outbox、admission 鎖、sandbox clamp，而 coop 這四項全缺，且其中一項（repo 併發）在 coop 現有功能下已可觸發真實資料事故。 兩邊不是誰抄誰，是兩層不同高度的東西，最終應該疊在一起。

二 · 逐軸對照

同一個問題，兩邊各自怎麼答。最右欄是我的判讀：誰的答案更完整，或兩邊在解不同的問題。

軸ai-coopPurdex M0判讀
委派單位 房間 × provider → agent_session → agent_turn（三層） issue → dispatch → execution → attempt → session（五層） Purdex 五層是為「一 issue 多次執行／多 attempt」預留；coop 的 session 是長命對話、turn 才是執行單位。兩邊的「session」不同義，見 §五-Q3。
觸發模型 push · 記憶體鎖 · pending 深度 1（後蓋前，不排隊成串） pull · 輪詢 + claim · dispatch_id upsert 冪等 解不同問題 coop 人在場，延遲優先；Purdex 要穿內外網分離（Ploom 純 server），只能 pull。
provider 抽象 執行期多型：AgentAdapter 介面（createSession / send→AsyncIterable<AgentEvent> / interrupt / compact? / release? / readQuota?），optional method＝capability 宣告 跨行程契約：wire contract + golden fixtures 為 provider 中立；daemon 內只有 claude launch adapter，codex 僅 observe 骨架（launch 排 M1） coop 已證明兩種截然不同的行程拓樸可以藏在同一介面後。Purdex M1 要做的正是這件事，介面形狀可直接照抄。
行程拓樸 claude 每輪 spawn（一次性）／codex 單例 app-server 多 thread。依據是實測記憶體，與計價無關 一 execution 一 tmux pane，pane 內 pdx relay -- claude -p … coop 有數字 實測：one-shot 與 long-lived 延遲無差異（穩態 2190 vs 2345ms），差別只在記憶體與耐重啟；claude long-lived 364MB／session。Purdex 的 tmux+relay 拓樸吃的就是這個量級，見 §五-Q2。
對話續接 UUID 由我們產生，首輪 --session-id、之後 --resume，兩者互為 fallback。狀態在 ~/.claude 磁碟，關機數日仍接得回 無。claudeBaseCommand 不帶 --session-id，跑完即散 coop 完勝 這是 M1.5「free-text follow-up」的前置，且移植成本近乎零（launch 時多一個旗標）。見 §三-1。
餵什麼進去 watermark：每輪餵 (from, to] 增量；只在成功時推進，失敗重試不漏訊息。純函式，三種初值情境（首次／後加入／/clear） 一次性 buildPrompt(title + body) coop 完勝 一旦 Purdex 要續談，「這輪該餵什麼」立刻是問題。coop 的答案語意剛好對得上 Ploom 的 issue_event append-only 時間軸。見 §三-2。
過程可觀測 agent_steps：ref 配對 upsert（claude tool_use id／codex item id）· kind 分 tool/command/file/search/thinking/commentary · SSE 不帶 detail，detail 走展開 API pointer-first artifact（diff numstat + untracked，無 blob）。執行過程對 Ploom 是黑箱 coop 更細 兩邊同一個原則（pointer-first），但 coop 在 step 層也套用了，Purdex 只在 artifact 層。見 §三-3。
中斷／逃生 interrupt → 30s 寬限 → forceStop 讓事件迴圈脫身（adapter 掛死也走得掉）＋整輪 10min timeout M0 完全沒有控制面（ExecutionControlRequest 於 V1 整個移出契約，stop/interrupt 歸 M1） coop 形狀值得照抄，而且 Purdex 更需要——它多隔一層 WS relay，掛死面更大。
授權／沙箱 三級 off/workspace/full · 房間層 + oneShot（僅下一輪）：不落盤、讀取即刪、失敗不退還、/clear 作廢、/compact 不消費。每輪明確傳（codex override 是 sticky） sandbox_profile = dispatch 的 request；daemon host policy 為唯一權威，clamp 只能降不能升，unknown → 最嚴（read-only） Purdex 的權威模型對／coop 的時效語意對。coop 房間可自行升到 full（明文接受，互信前提）＝產品前提而非架構能力。兩者互補，見 §三-4／§四-2。
路徑圍堵 assertUnderRoots：allowlist + 雙 realpath + 分隔符邊界（防 /root 涵蓋 /rootette）· 每次使用都重驗 · 壞設定安全回退成預設目錄 allowed_repo_roots fail-closed（未設一律拒）· canonical EvalSymlinks + segment 邊界 高度一致 兩邊獨立收斂到同一組防護（realpath + 邊界 + 每次重驗）。差別只在壞設定的處置：coop 回退、Purdex 拒絕。
子行程 env buildAgentEnv 白名單（PATH/HOME/SHELL/TMPDIR/LANG + 明示 extra）· COOP_* 出現就 throw 而非靜默剔除 relay 繼承 daemon 環境（M0 未見等價白名單） coop 「寧可炸在測試也不要默默漏密」這個取向值得移植——Purdex daemon 環境裡有 token。
崩潰一致性 串流 delta 逐筆落盤（不節流）→ 重整／斷線／重啟接得回。三支 boot repair：訊息標 interrupted、busy session 復位、running steps 收尾＋回填 count。
但 pending／oneShot／鎖／額度門檻全在記憶體，重啟即失（設計如此）		 outbox 併入 execution DB，四個複合交易單 txn（狀態轉換＋enqueue 原子）· 單調 seq · ack cursor · 重啟 replay · reconcile 矩陣 + manual reclaim Purdex 完勝 coop 是「單機單行程、重啟就重來」的假設；一旦要對外回報或跨主機，這假設立刻破。這正是 Purdex F1 那一刀（兩獨立 DB → 單一原子交易）解掉的洞。
穩定 handle 無。對外座標＝房號 + provider，指不到「那一次執行」 execution_id（早於 session_code 抽出）· session_name 為 crash-recovery handle · session_code 為衍生 deeplink handle Purdex 完勝 coop 不需要（人就在房裡）；Purdex 沒有就整個派工閉環不成立。
併發正確性 鎖只到 roomId:provider。跨房共享資源無協調：同一顆 codex app-server 單例、同一份訂閱額度、（自訂後）同一個 workDir admission：canonical repo → 同 repo 單一 live execution + head_at_start/dirty_at_start 快照 + per-repo lock 消 TOCTOU Purdex 完勝 且 coop 這個缺口已可觸發真實事故，見 §四-1。
帳號／額度 claude 多 OAuth token：每輪解析帳號並落 agent_turns.account 供事後歸帳；額度門檻按 provider:account 各自追蹤；即時查額度不花 token（/api/oauth/usage、account/rateLimits/read） 無此維度 coop 「零 API 成本 ≠ 免費」的具體管線。Purdex 多 execution 併發撞額度時會需要同一套歸帳。
三 · 可移植資產：coop → Purdex

每張卡＝一個 Purdex 現況缺口 + coop 的現成答案 + 我對移植成本與落點的判讀。排序按「價值 ÷ 成本」。

1自產 session UUID → --resume

Purdex 現況缺口

claudeBaseCommand ＝ claude -p --verbose --input-format stream-json --output-format stream-json，沒有 --session-id。execution 跑完，那段對話 context 就撿不回來。M1.5 的「free-text follow-up／rerun」等於要從零重述整個 issue。

coop 的答案

UUID 由我們產生並存進 DB，首輪 --session-id、之後 --resume，兩者互為 fallback（首輪失敗後磁碟 session 可能已存在，反向亦然——實測踩到）。session 狀態在 ~/.claude 磁碟上，後端可重啟、換版本、關機數日。

移植

launch 時多一個旗標，UUID 從 execution_id 衍生（或另存一欄）。M0 不加，M1.5 就得補一次 launch 路徑改動——現在加最便宜。

成本 極低落點 M1（或 M0 補丁）解鎖 M1.5 follow-up

2watermark 增量餵食

Purdex 現況缺口

prompt ＝ title + body 一次性。沒有「上次餵到哪」的概念，所以也沒有「續談時該餵什麼」的答案。

coop 的答案

watermark_seq 存在 session 上，每輪餵 (from, to]，只在 done 時推進——失敗／中斷保持原位，重試不漏訊息。三種初值情境明確（首次 0＝餵全歷史／後加入 0／/clear 從當下 seq）。整個機制是 38 行純函式，DB 讀寫留在上層。

移植

語意天然對得上 Ploom 的 issue_event（append-only + seq）：execution 記「餵到哪個 event」，follow-up 就是餵增量。這是兩邊資料模型少見的直接咬合點。

成本 低落點 M1.5咬合 Ploom issue_event

3step 事件流（過程透明度）

Purdex 現況缺口

M0 只回 pointer-first artifact（diff numstat / transcript 指標）。執行過程對控制面完全是黑箱——Ploom 看不到 agent 現在在跑哪一步。而業界研究早已定調「thread＝控制面＋通知面」需要輕量狀態訊號。

coop 的答案

agent_steps：UNIQUE(turn_id, ref) 以 adapter 事件的天然 id 配對 upsert（claude tool_use.id／codex item.id），started 可重複發（後到豐富 label 不新建列），finished 無前置也能直接插。kind 六類。started 走 content_block_start 搶即時性、assistant 事件再校正 label——即時與精確兩件事分開拿。
關鍵取捨：SSE 不帶 detail（省流量、降暴露面），detail 只從展開 API 取。

移植

Purdex relay 目前只逐行 tee stdout→WS、完全沒 parse。要做 step 層就得在 daemon 側加一個 stream-json parser——這是真成本，但 coop 的分類表與 upsert 語意可整套照搬，省掉設計輪。

成本 中落點 M1.5／M4需 relay 端 parser

4oneShot 一次性授權的邊界語意

Purdex 現況缺口

sandbox_profile 是 per-dispatch 的 request + clamp，權威模型正確；但沒有「僅這一次」與「語境換掉即作廢」的時效語意。M1 一旦有了控制面（stop/interrupt/attach），就會需要「這次准、下次不准」。

coop 的答案

oneShot 刻意不落盤（重啟即失效＝該輪未開跑視同未授權）。邊界全部明寫：消費時點在取得鎖之後、建 turn 之前；讀取即刪，不論 done/error/interrupted 都不退還；busy 中設定 → 排隊的下一輪吃到；/compact 不消費；/clear 清除（換 session＝授權語境失效，安全取向）。

移植

是一套決策，不是一段程式。Purdex 抄的是這張邊界表，尤其「失敗不退還」與「換語境即作廢」兩條安全取向。

成本 極低（設計移植）落點 M1

5interrupt 的雙層保險

Purdex 現況缺口

M0 沒有控制面。M1 要做 stop/interrupt 時，會直接撞上「adapter／relay 掛死怎麼脫身」。

coop 的答案

三層：整輪 10min timeout → interrupt → 30s 寬限後 forceStop 讓事件迴圈自己走掉（Promise.race([stream.next(), forceStop])，不等對方回應）。刪房收尾另有 45s 上限並「逾時放行，殘留交給 boot repair 兜底」。

移植

Purdex 多隔一層 WS relay，掛死面比 coop 大。這個「永不無限等待 + 殘留交給 reconcile」的分工，跟 Purdex 已有的 reconcile 矩陣是同一套哲學，接得上。

成本 低落點 M1

6optional method ＝ capability 宣告

Purdex 現況缺口

Purdex 的 provider 差異目前散在契約層與 config；daemon 內只有一種 launch 路徑。M1 加 codex launch adapter 時需要一個表達「這家有／那家沒有」的地方。

coop 的答案

AgentAdapter 用 optional method 直接當能力宣告：compact?（未實作＝不支援）、release?（未實作＝無常駐資源可釋放）、readQuota?（未實作＝查不到）、supportsPdfInput?。呼叫端一律失敗容忍。比 capability flag 表乾淨——能力與實作綁在同一處，不會漂移。

移植

Go 沒有 optional method，但等價形狀＝小介面 + type assertion（if r, ok := a.(Releaser); ok）。這是慣用 Go，不是硬套 TS。

成本 極低落點 M1（codex launch adapter）
四 · 反向：Purdex 有而 coop 缺的

不是「coop 應該變成 Purdex」——coop 的取捨多半合理（單機、互信、人在場）。但有一項不是取捨，是缺口。

!自訂 workDir 指向真 repo ＝ 無防護的併發寫

現況（已可觸發，非假設）

coop 支援自訂工作目錄：COOP_WORKDIR_ROOTS allowlist + 覆蓋鏈 room.work_dir ?? workspace.work_dir。路徑圍堵做得很好（雙 realpath + 邊界 + 每次重驗），但圍堵解決的是「跑到界外」，不是「界內互相踩」。

缺什麼

一旦 roots 指向真 git repo：沒有 per-repo 鎖、沒有「同 repo 單一 live」、沒有 base_commit／dirty 快照。兩個房間（或同房 claude + codex，兩把鎖是 roomId:provider 各自獨立）可以同時在同一顆 working tree 上寫。加上 accessLevel: full ＝ bypassPermissions，agent 能 commit。

這正是 Purdex admission 想擋的

Purdex 的 「repo clean OR 同 repo 單一 live execution」admission rule 是 codex review 硬塞進 M0 的（原話：不補後面一定 rework），理由就是「無 worktree 下防 dirty tree／併發資料事故」。coop 落在同一個區域，只是還沒被踩到。

建議

最小修法不需要整套 admission：把鎖從 roomId:provider 升到「canonical workDir」維度（自訂目錄時才生效，預設 per-session 目錄天然無衝突）。這跟 coop 現有的鎖機制同構，改動很小。要更穩再加 dirty 檢查。

關聯 高信心 高複雜度 低（升鎖維度）

2沒有 clamp：授權是產品前提而非架構能力

現況

coop spec §1 明文：暱稱即身分、無帳號，無法限制誰能授權。任何在房裡的人都能把 agent 升到 full（完全存取主機）。風險由房主承擔，UI 標紅字警告。

判讀

在「房主自己主機 + 5 人互信」下這是合理取捨，不是 bug。但要注意它的性質：缺的不是設定，是「請求 vs 權威」的分層。Purdex 的 sandbox_profile = request、host policy = 唯一權威、clamp only-down、unknown → 最嚴——這一層 coop 完全沒有。

什麼時候會痛

coop 已經有 admin／帳號／密碼分享（v0.20/v0.21 在做的正是這些）。一旦房間可以分享給非互信的人，clamp 這層就得補，且補的時機晚於「分享功能上線」就已經遲了。

關聯 中（隨分享功能升高）信心 高複雜度 中

3記憶體狀態的邊界

現況

coop 的 pending trigger、oneShot、執行鎖、額度警示門檻、codex 的 liveThreads／世代計數／idle timer 全在記憶體。串流內容本身逐筆落盤（很好），但「排隊中的那一輪」重啟就沒了。

判讀

對 coop 是正確取捨——人在場，重啟後再按一次就好，反而比「復活一個沒人記得的排隊輪次」乾淨。Purdex 不能這樣，因為 Ploom 那頭有一個 dispatch row 在等，不回報就永遠卡著（這正是 F1／F2 兩個 finding 的本質）。

要留意的是

coop 若哪天加了「排程觸發／非同席委派」（人不在場也要跑），這個取捨立刻失效，且會以「任務靜默消失」的形式出現——最難查的一類。

關聯 低（現況）信心 高複雜度 高（若要改）
五 · 尖銳問題 · 待驗證

前三題是我在對照過程中發現的、需要拍板或實證的；標紅的是我沒有驗證過的推論，不要當結論用。

Q1 · Purdex M0 的 execution 真的會 terminal 嗎？未驗證
Purdex 的 terminal 時點權威是 process exit（relay 在 subprocess 退出時送 binary terminal frame 帶 exit code；result event 只當 enrichment）。 但 relay 的 stdin 是 WS → subprocess stdin 的長命管線，直到 WS 收線才 stdin.Close()。 而 coop 的 claude adapter 是寫完一則就 stdin.end()——那正是它保證行程會退出的手段。
→ 問題：claude -p --input-format stream-json 在 stdin 未關閉時，答完一輪會自行 exit，還是繼續等下一則輸入？若是後者，M0 的 execution 只會靠 timeout／reconcile 收尾，terminal report 的時點就不是設計預期的那個。
→ 怎麼驗：真跑一個 dispatch（非 fake subprocess 的單測），看 claude 行程在 result 之後是否還活著。M0 全套單測用 fake，這條路徑天然測不到。
Q2 · Purdex 選了 long-lived 拓樸，但拿到的是 one-shot 的語意——值得嗎？設計拍板
coop 的實測給了兩個硬數字：(a) one-shot 與 long-lived 延遲無差異（瓶頸在 API 來回 1.4–1.7s，spawn 只 ~0.5s，低於 API 抖動）；(b) claude long-lived ＝ 364MB／session／行程。 Purdex 每個 execution 起一個 tmux session + 一個 pane + 一個 relay + 一個 claude，成本在 (b) 的量級，但因為跑完就散、又沒帶 --session-id，換不到 long-lived 該有的好處（續接）。
→ 拍板題：tmux 這一層在 M0 買到的是什麼？我的判讀是「非 Claude 子進程的 runtime 現場」＋人可 attach 的逃生艙（這也是 codex 先前的定調：--resume 只解模型對話續接，不解整個 terminal process tree）。若同意，那 §三-1 就不只是加旗標，而是把兩邊好處都拿到：tmux 保現場、--session-id 保續接。
Q3 · 兩邊的「session」不同義，五層模型少了一層概念釘死
coop 的 session ＝ 對話續接單位（externalId ＝ claude UUID／codex threadId，長命、跨行程、跨重啟）。 Purdex 的 session ＝ tmux/relay 的 runtime 生命週期（session_code）。 兩者同名不同物。
對到五層 issue→dispatch→execution→attempt→session：Purdex 的 session 對應的是 coop 的 process，而 coop 的 session（對話續接）在 Purdex 五層裡沒有位置。 → 這解釋了為什麼「M0 沒有 --session-id」看起來像小疏漏、實際是模型層缺一格：沒有那一格，follow-up／rerun 語意就無處掛（rerun ＝ 新 dispatch 新 execution，那 follow-up 掛哪？）。
→ 建議：M1.5 設計時先把這一格命名清楚（例如 conversation 或 agent_session，明確與 tmux session 區分），別讓兩個 session 在同一份 spec 裡打架。
Q4 · 兩邊都在長「同一個東西」，要不要收斂？戰略
coop 的 AgentAdapter + step 流 + watermark，本質是「provider 中立的 agent 執行期」——跟 Purdex 想在 daemon 裡長的東西高度重疊，只是一個在 TS 一個在 Go、一個服務聊天室一個服務工單。
→ 不建議做成共用元件（跨語言、兩邊生命週期不同、YAGNI）。 建議把 coop 當成 Purdex 執行期的參考實作與踩雷紀錄：它已經在真實使用中跑過 sticky override、崩潰後 resume 自癒、per-thread mutex、commentary 誤分流、空 thinking block 這些坑。 M1 加 codex launch adapter 時，coop 的 codex.ts（641 行）幾乎是一份可讀的規格書——它把 app-server JSON-RPC 的生命週期全部處理完了（idle unsubscribe 15min + 退避重試 3 次 + 世代計數防 race + 崩潰清 liveThreads 觸發 resume）。
六 · 共同體質債

兩邊同型的問題，寫在一起比較省事。

A單一巨型方法／檔案

coop：server.ts 1995 行；turns.ts 的 #run 一個方法約 340 行，做七件事——plan + prompt 組裝 + 附檔處理 + 事件迴圈 + 收尾交易 + 產圖回收 + watermark 結算 + pending 補跑。

Purdex：M0 已刻意拆檔（execution 18 檔／dispatch 8 檔），這點比 coop 健康；但 dispatch/module.go 已 16.7KB，是同一個徵兆的起點。

判讀

coop 的 #run 是會在 codex「檔案體質」視角被抓的典型。抽法很清楚：事件迴圈（switch 十一個 case）可獨立成 turn event processor，附檔處理可獨立成 attachment resolver，兩塊各自可測。

Bprovider 中立做在不同高度，兩層都需要

coop 做在 執行期介面（同行程多型），Purdex 做在 wire contract（跨行程契約）。兩邊各只做一層。

判讀

這不是二選一。Purdex 未來要在 daemon 內同時 launch claude 與 codex，缺的正是 coop 那一層；coop 若要把 agent 執行移出行程（或跨主機），缺的正是 Purdex 那一層。兩層之間的介面該是同一組事件語彙——Purdex 的「中性事件契約」與 coop 的 AgentEvent 是同一件事的兩個版本，合併時應該對齊而非各長一套。

C執行期的 activity 都靠 stdout 解析

兩邊都在做同一件苦工：把 CLI 吐的 stream-json／JSON-RPC 反解成結構化事件。coop 已經解完（claude.ts 412 行 + codex.ts 641 行），Purdex relay 刻意只 tee 不 parse（M0 決策，避免動 relay）。

判讀

Purdex 遲早要 parse（step 流／terminal 分類已經需要 result event）。M0 已經在 daemon 側開了 seam（SetTerminalHandler）並且 P.8 有 captureInitMetadata——parser 的落點已經有了，不是從零。要做的時候，coop 的兩支 adapter 是免費的欄位地圖。

七 · 我建議的動作
立刻（低成本、擋住未來 rework）
① coop：把執行鎖從 roomId:provider 升到 canonical workDir 維度（§四-1）——自訂 workDir 指真 repo 的併發寫是現成風險，改動小。
② Purdex：launch 帶 --session-id（§三-1）——一個旗標，換到 M1.5 的前置與「重試接得回」。
③ Purdex：驗 Q1（真跑一次 dispatch 看 claude 行程是否自行 exit）——若推論成立，terminal 時點的設計前提要修。
M1 規劃時帶進去
④ 控制面（stop/interrupt）照 coop 的三層逃生（timeout → interrupt → forceStop 寬限）＋oneShot 邊界表。
⑤ codex launch adapter 直接把 coop 的 codex.ts 當規格讀（sticky override 每輪明傳、崩潰後 thread/resume 自癒、per-thread mutex + 世代計數）。
⑥ 介面形狀用 Go 的小介面 + type assertion 表達 optional capability。
M1.5 之前要先釘死的概念
⑦ 五層補「對話續接」那一格並改名，別讓兩個 session 打架（§五-Q3）。
⑧ watermark 語意對齊 Ploom issue_event（§三-2）——這決定 follow-up 餵什麼。
⑨ step 流要不要做、做到哪一層（§三-3）：這是 M4「review console」的前置，但需要 relay 端 parser，成本是 M0 以來最大的一筆。
