Ploom ↔ Purdex 派工整合脈絡

從「人在 Ploom 派一張工」到「agent 在 Purdex 跑起來」到「人點連結回到對話」的端到端旅程。用來定位 deeplink 入口（本輪 A+B） 在整條管線裡的角色，以及它與 C 輪詢/派工形狀 的邊界。

Ploom plm · 控制平面／大腦 ↔ 靠 API 串 ↔ Purdex pdx · 執行平面／手腳 連線方向 = Pull：Purdex daemon 持 token 主動輪詢 Ploom
前置（一次性） C — 輪詢/派工形狀（C 前那輪先討論） A+B — deeplink 入口（★ 本輪要做） Ploom 端
P0

前置：daemon 註冊

前置 · Ploom
Purdex daemon 綁一個 Ploom is_agent 帳號 + S4 token。
Ploom 存 daemon entity = { id, name, host(network 位址), account_id }
⚠️ Ploom 這時記下的是 daemon 的「network host」（如 100.64.0.2:7860）—— 之後組 deeplink 用的就是它。

P4

daemon 回報 → Ploom 組 deeplink

C 本輪不做 · Purdex → Ploom
daemon → POST /daemon/dispatches/{id}/report { session_code, status:running }
Ploom → 存 session_code；用 daemon.host + session_code 組 deeplink，存上 issue、秀出來
deeplink 在這裡「誕生」，用的是 P0 存的 network host。這一步定義了 deeplink 該長怎樣。
▼
P5

人點 deeplink → 回到對話

★ A+B 本輪要做 · 人 + Purdex App/SPA
人在 issue 頁點 purdex://…
→ OS 喚起 Purdex App　← A：scheme 註冊（setAsDefaultProtocolClient / open-url）
→ App/SPA 解析 deeplink、定位／開啟對應 session tab　← B：resolver
本輪只做這一段的「消費端」。但消費端能吃什麼格式 = 替 Ploom 定義了 P4 該組什麼，所以 deeplink 格式帶契約性質。
這張圖的三個結論

1deeplink 是 P4↔P5 的契約

本輪只做 P5 消費端，但「Purdex 能解什麼格式」等於替 Ploom 定義了 P4 該組什麼。所以 deeplink 格式雖在 Purdex 側先定，本質是跨兩平面的契約，也就是它踩到「派工形狀」的地方。

2host 對應張力的根源

P0/P4 用 daemon 的 network host；P5 定位 tab 用 Purdex 的 前端隨機 hostId（HostConfig.id，每 client 私有、Ploom 不知道）。兩套識別體系天生對不上，中間只能靠 daemon 的 host_id 搭橋。

3單 daemon 下 host 維度可極簡

第一切片是單 daemon／單 host 假設。只有一台 host 時「指向哪台」是廢話：resolver 大可只帶 session_code、掃本地所有 host 找哪台有它。host 對應的真正複雜度要到多 daemon（S6a，DEFER）才爆發。

業界參照與實例（列入評估）

我們不是憑空設計。同型模式（thread／channel ↔ AI coding agent）業界已有 7 家在做，且有人自建整套、公開了踩坑結論。這些都拿來反推「派工形狀」。

🏢 業界七家的共識

Claude Code in Slack ／ Devin ／ Cursor bg agents ／ Copilot ／ Codex ／ Factory ／ Amp。一致做法：thread（≙ issue）＝控制面＋通知面，摘要／狀態／按鈕放 thread，plan／diff／transcript 放執行端用 deeplink 導流；觸發＝@mention＋自然語言＋結構化參數；狀態用輕量 badge（⏳✅❌）；「blocked-on-human」是公認缺口；issue : session 別寫死 1:1（Devin Managed 是一母任務多子 session）。

🧪 Flycoder ／ Custie 實例（蔣定宇）

有人把 Slack 改 AI 工作台用了半年，結論「方向對了，房子錯了」：Slack 為「人跟人聊天」蓋，AI 進來「只能睡沙發」，缺 中斷跑到一半的 agent、看它做到哪一步、指定 skill／同時多 agent／agent 再開 subagent。於是自建：channel＝工作目錄、agent/subagent 點名聊、每步 activity 可見、隨時喊停或給下一步指令。尖銳點出 Slack 隱喻的天花板 ＝ Ploom 該超越處。

★對本輪 B resolver 的直接啟示：deeplink ＝ 穩定 handle，落點三段式

deeplink 不是「跳去看」的一次性連結，而是永不落空的 handle（Claude View Session：session 過期仍留 web history）。resolver 依 session 狀態分級落點，三段 Purdex 剛好都有現成拼圖：

① 執行體活著（tmux session 在）　→　attach 現有 session tab　（原本的 B）
② tmux 沒了、有紀錄　→　workspace snapshot 一鍵重建同 repo/branch/cwd　（剛做完的資產）
③ 完全過期　→　至少開唯讀 transcript　（JSONL 歷史 / B7 線）

另外兩顆種子留給 C（派工形狀）那輪：blocked-on-human 做成一等狀態、dispatch 資料模型預留一對多。
