統一介面語言：一套名詞與元件，兩種底層、兩個 App

這份文件定義 Purdex 的 Mac App 和 iOS App 共用的介面語言：名詞、符號語法、元件、用量、dock、退回終端的規則、能力宣告，以及 daemon 要提供的對話模型。終端機底層（TUI 在 tmux）和執行體底層（Nexen execution）都用同一套；底層提供了某項能力，對應的元件才會出現。

0摘要

控制模式有三種：終端機、指揮台、聊天。daemon 把兩種底層都正規化成同一份對話模型，Mac App 和 iOS App 都只負責畫。CC 的資料以 Purdex mod 為主要來源（終端機底層；執行體底層也可以用，需 Nexen 配合），兩種底層的 CC 送出同一套事件。

  • mod 補齊了 CC 終端機底層（§4，2.1.292 實測）：
    • turn.step 給逐字串流：文字、工具參數、thinking 的 chunk 都有，但 thinking 的內容是空的。
    • tool.call 給工具的起訖和結果，tool.check 給權限判斷。
    • session.measure 在用量一變就推：context、5 小時、7 天、成本。
    • session.append 涵蓋對話裡新增的每一列。
    • 寫入可以走 $.prompt.submit，不必打字。
    transcript、hook、statusline 降成「沒有 mod 時」的退路。
  • 用量是正式元件（§7）：model、effort、context、5 小時與 7 天額度、成本。桌機放在狀態列；手機放在輸入框上方一條，點開是抽屜。
  • 指揮台採用 Collie 式「從 terminal 轉化的語言」。iOS 的 chat-v2 已經是它的現況版，Mac App 的 room 也是同一個方向。
  • 聊天＝資訊更簡略的對談模式（10-09 使用者更正）：同一份對話、同一個 dock，只留你說的和 agent 回的，每回合的工作收成一列；比指揮台簡略，不是另一種資料，也不必等其他底層。多人同房只是延伸的例子。
  • 燈號 v2（§12）：現在的 16 種不準情況中，11 種可以靠 mod 事件、序號和心跳修掉，另外 3 種要改 daemon 和 SPA 的聚合與重連。
  • dock：提問、核准、計畫放在輸入列上方；指揮台和聊天畫，終端機模式只顯示一條提示列（§8）。資料通道是 P8a、P8b（CC 終端機）、Nexen 權限通道（執行體）、app-server（Codex）。
  • 決策紀錄（§17）：使用者 10-08 已全部定案，下一步轉成 docs/specs/ 的正式 spec，從 U1 開始。

1原則；從 iOS 挪用的設計

原則一 定案

介面統一，由能力決定

兩種底層用同一套名詞和元件。底層有提供某項能力，對應的元件才出現；不做降級版，也不討論哪種底層適合哪種情境。

原則二 定案

一套元件，同時給桌機和行動

每個元件在兩種裝置上各有一種呈現。共用的是語意，不是程式碼。

原則三 定案

從 terminal 轉化而來

指揮台採用 Collie 式的語言：CC 風格的符號，加上類別詞正規化。Codex 也照這套呈現。

定案 以整套設計的統一為主。iOS 已經規劃好、而且合適的部分挪過來用，但它不是限制。

iOS 的設計處理理由
只用手機檢視，不搬 session挪用跟「介面不改變底層」的原則一致
需要人回應的事件推給所有 client，任何一邊回答後全部關閉挪用跟 P8a 的分流同形
全寬的「你」框、不加泡泡、7 類工具、≥3 步摺疊、狀態槽、輸入列上方的回答卡挪用就是指揮台的語法（§5）
權限只給「允許」和「拒絕」挪用Collie 也這樣做：持久授權不做成按鈕
送出時有 3 秒緩衝，使用者看不到；停止鈕和送出鈕共用位置挪用，換通道「反悔窗口」的體驗保留。有 mod 時改走 $.prompt.submit，不必打字
多行送出用 LF、不用 bracketed paste；按鍵規則（數字、→、ESC）只當退路這些是「打字進終端」這條通道的實測事實，只在沒有 mod 時用得到
iOS 16（iPhone 8）iOS 端的實作限制不影響介面語言

為什麼是「指揮台 deck」（10-08 使用者從十個候選中選定）：terminal 和 chat 都是在講「用什麼方式操作」，Worker 卻是「做事的人」，詞性不一致；Work 也不夠貼。Deck 是艦上的指揮甲板，貼近「看它做事、也指揮它」的控制模式，中文「指揮台」也跟原本的「指揮室」接得上。

不要使用的同義詞：worker、room、指揮室、對話模式、紀錄介面都統一叫「指揮台」；「對話」只當實體名（E1）；「工作區」只指 Purdex 的分頁群組。

4事件簿：每項資料從哪裡來

4.1 mod 實測（CC 2.1.292）

在 scratchpad 寫一個只負責記錄的拋棄式 mod，用 claude -p --plugin-dir 跑兩個小提示（一個呼叫 Bash，一個要求長思考），記下實際收到的事件：

事件實際收到的補上什麼
turn.step（串流）第 1 步：thinking 3 個、tool 1 個、input 6 個（工具參數邊產生邊送）、stop。第 2 步：text 21 個 chunk，共 138 字。另外還帶 model（claude-opus-5-5）、effort（xhigh），子 agent 時帶 agentId逐字串流（以前標成「transcript 只有整則」的那項）、工具參數的串流、目前用哪個 model 和 effort
thinking chunk有 chunk，但 text 是空字串（thinkLen=0）拿得到「正在思考、想了多久」，拿不到思考的內容。這是 API 端的行為，mod 也拿不回來
tool.call{tool, tool_use_id, command, description}；await next(e) 拿到結果 {result, text, isReadOnly}，花了 1484ms工具起訖、輸入、結果、耗時；可以攔截（P8a 的分流就是這樣做的）
tool.check{decision: "allow", rule: "Bash(echo:*)"}權限判斷，還能知道是哪一條規則放行的。P8b 用它在介面回答權限
session.measure數字一變就推：context {tokens: 42612, window: 1000000, percent: 4}、rateLimits [{five_hour, percentUsed: 34, resetsAt}, {seven_day, …}]、cost，另附 changed 標出哪幾項變了用量（§7），而且是推送，不用輪詢
turn.start／turn.completeturnId、使用者文字；結束原因 answer／aborted／refusal／error，以及 usage（含 cache tokens）精確的回合邊界、中斷、失敗
session.append每一列都會經過，並標出來源：prompt、response、tool-result、attachment、hook-context、notice（另有 delivery、compaction、command），帶 uuid 和子 agent 的 id完整、即時、結構化的紀錄，比 tail transcript 早，也不用自己解析格式

實測是在 -p 模式下做的。mod 本來就是為互動式 TUI 設計的，P8a 也已經在互動式 session 裡用 tool.call。互動式下的事件順序和延遲，會在 U1 的驗收時再量一次 待驗證。

4.2 其他 mod 能力（型別定義有，尚未實測）

  • session.receive：收到其他 agent 的訊息時觸發（peer、relay、Remote Control）。session.compact、session.end（含 /clear）、session.attach／detach（有哪些介面接上來）。
  • 寫入：
    • $.prompt.submit：閒置時開一個新回合，不打字。
    • $.prompt.fill：把文字填進輸入框。
    • $.turn.abort：中斷。
    • $.session.append：在執行中的回合插一列使用者看不到、但模型讀得到的訊息，可以拿來插話。
    • $.command.run：執行 slash 指令，例如切換 model 或模式。
  • 計畫：ExitPlanMode 也是一個 tool.call，可以照 P8a 對 AskUserQuestion 的做法，讓原生對話框和遠端答案同時等，先答的生效 待驗證。
  • 傳輸：$.http.fetch(url, {socketPath}) 能透過 Unix socket 打到本機 daemon。逐字 chunk 要批次送，例如每 100–200ms 或每一步結束送一次，不要每個 chunk 都起一個行程（$.process.run 只留給低頻的指令）。

mod 的前提和風險：

  • mod 要已經載入。mlab 已經用 P5b 的 pdx setup --agent cc 全域安裝（10-08 起是 alpha.586）；a26 還沒確認。沒裝的機器走 transcript＋hook 退路。
  • 用 --safe-mode 開的、或在安裝之前就開的 session，沒有 mod，這時退回 transcript＋hook。
  • mod 的 API 是 early access，會隨版本變動：用 $.session.version() 確認版本，並在 hello 時回報自己的能力。
  • Codex 沒有 mod，Codex 走 app-server。CC 的執行體本來就有 Nexen 事件；加上 mod 則是為了跟終端機底層共用同一套事件（§4.4）。

4.4 執行體也用 mod 定案（方向）

  • 可行：上面的實測本身就是用 claude -p --plugin-dir 跑的，headless 模式一樣會載入 mod。Nexen 啟動 claude -p 時加上 --plugin-dir <Purdex mod> 就可以了。lead／team 的 member 已經固定帶這個參數。
  • 好處：CC 不管跑在哪種底層，都送出同一套 mod 事件，daemon 只需要一個 CC 正規化器。另外還多拿到 stream-json 沒有的東西：用量推送、tool.check 的權限判斷和規則、session.append 的每一列和它的來源、思考了多久。
  • 要 Nexen 決定：Nexen 的一般 profile 刻意帶 --setting-sources ""，不載入使用者的設定和 plugin，這是它的沙箱與憑證邊界。用指定路徑只載入 Purdex 自己的 mod，是一個受控的例外。mod 會以使用者身分執行 $.process、$.fs、$.http，不受 Nexen 工具白名單的限制。
  • 兩條事件流各管什麼：Nexen 的事件帳本負責歷史、重播、成本帳；mod 事件負責即時畫面和燈號。daemon 用 tool_use_id 和 turn 對齊兩條流，不重複計算。
  • 每回合重載：執行體每個回合都會重新啟動行程，mod 也跟著重新載入（每次都觸發 session.start）。所以狀態由 daemon 保存，mod 自己不存狀態。

12.1 現在的燈號為什麼不準

燈號（每個 session 的狀態點）目前由 settings hooks 推算（internal/agent/*/status.go → AgentEventStore → SPA useAgentStore.ts）。不準的原因可以歸成三類：

  • CC 有些情況根本不發 hook：按 Esc 中斷時不發 Stop；不是使用者打字開始的回合不發 UserPromptSubmit。
  • hook 送丟了不會補：逾時 2 秒、不重試，daemon 重啟期間的事件也會漏掉。
  • SPA 重連時不清舊狀態。

11重連後所有閒置 session 都冒出未讀紅點replay 的 idle 被當成需要處理（useAgentStore.ts:286-300）mod 修不了：SPA 不把 replay 標成未讀

12.2 燈號 v2 規則（10-08 定案）

  • 優先序（使用者 10-08 定案）：失敗 ＞ 等你回答 ＞ 工作中 ＞ 閒置。一個分頁有多個 pane 時取最高的；未讀紅點另外疊上去，不參與排序。背景工作怎麼顯示見 §17。
  • 背景工作（使用者 10-08 定案）：背景指令（shell）不顯示。workflow、monitor、排程喚醒（/loop、ScheduleWakeup、CronCreate）在分頁 agent 圖示的左上角打一顆小符號，三種同時存在時只顯示一種，不動主燈。
    • 順序（統籌排）：workflow（TreeStructure）＞ monitor（Eye）＞ 排程喚醒（Clock）。越接近「現在就有東西在跑」越優先：workflow 正在開 agent、花 token；monitor 隨時可能叫醒；排程要等時間到。滑鼠移上去列出全部三種的明細。
    • 樣式：靜止不呼吸，跟圖示同色、縮小（顏色留給主燈）。燈號關閉（icon 樣式）時不顯示；只有點、沒有圖示的樣式（dot）畫在點的左上角。
    • 藍點只算主 agent 自己開的 subagent；workflow 開出來的 agent 由角落符號代表，不佔藍點（一個 workflow 可能開幾十個 agent，會把 3 個點佔滿）。
    • 資料來源：Stop 的 background_tasks（type＝workflow／monitor）與 session_crons。這三種結束或觸發都會喚醒 session 開新回合，所以每次 Stop 的清單就夠追蹤；有 mod 時可從 Workflow／Monitor／ScheduleWakeup／CronCreate 的 tool.call 即時加上。
  • 實作注意：workflow 開出來的 agent 不在 $.agent.list() 裡（d.ts AgentLoop.agentId），心跳對帳不能因此刪掉它們的藍點。
  • 來源分四層：
    1. mod 事件為準，每個 session 帶遞增序號，daemon 丟掉比上次舊的事件。
    2. 沒有 mod 時退回 hook，並先修三點：is_interrupt → idle；帶 agent_id 的 StopFailure 不動主燈；Stop 帶 background_tasks 時的呈現見 §17。
    3. 存活檢查：既有的 sweep 檢查 pid，再加上 mod 心跳。
    4. 畫面偵測只留給還沒接 app-server 的 Codex。
  • 心跳：mod 每 10 秒透過 Unix socket 送一次完整狀態（序號、子 agent 名單）。心跳只用來對帳和補漏，不顯示「失聯」；pid 死了 → clear。心跳同時能補回 daemon 重啟期間漏掉的事件。
  • 聚合：逐 pane 計算狀態，tab 和 session 取最高優先序。SPA 改成用完整快照整批替換、比較序號、replay 不標未讀。
  • Codex：接了 app-server 時以 thread/status/changed 為準，hook 當備援。

需要實測的：

  • CC 2.1.292 按 Esc 後確實不發 Stop 嗎？
  • 拒絕權限後，turn.complete 是 aborted，還是模型會繼續跑？
  • 背景任務、peer 訊息、cron 開始的回合，是否都會發 turn.start？
  • 被中斷的 subagent 會不會發 SubagentStop？
  • mod 能不能在 session.end 約 1.5 秒的上限內送出最後一筆？
  • Codex 共用 app-server 的狀態通知能不能傳給其他 client？

13能力宣告 建議

daemon 在每個對話上附一份能力表。採用分級制，沒宣告到的一律當不支援，再加上具名的理由。

capabilities: {
  source:          "mod" | "transcript" | "nexen" | "app_server",     ← 這個對話的資料主要從哪裡來
  text_streaming:  "none" | "message" | "token",
  thinking:        "none" | "duration" | "summary",
  answer_question / answer_permission / answer_plan: "none" | "terminal_only" | "remote",
  usage:           "none" | "context" | "full",                        ← full＝含 5h／7d／成本
  todo, subagent, background_tasks, peer_inbound: "none" | "partial" | "full",
  send: "keys" | "prompt" | "turn",  interrupt: "keys" | "rpc",  steer: "none" | "partial" | "full",
  reasons: { <能力名>: "no_mod" | "terminal_only" | "pending_p8b" | "not_wired"
                       | "daemon_too_old" | "provider_unsupported" }
}
  • 永久不支援就隱藏，例如 provider_unsupported。
  • 暫時不行就停用並寫出原因，例如 no_mod、pending_p8b、not_wired（像執行體的 peer mailbox）、daemon_too_old。
  • terminal_only 改成 dock 的「只能在終端回答」卡片。
  • 資訊未知不等於不支援：daemon 還沒回報能力時，元件顯示載入中。

GET  /api/conversations/{key}?after=<cursor>    snapshot＋增量

     · approval.request / approval.closed（沿用 P8a）
POST /api/mod/events                         ← mod 批次上報（Unix socket），取代 transcript tail 當主來源
  • golden fixtures：兩種輸入各錄一份。一份是 mod 事件流，從實測 probe 擴充成正式錄製；另一份是 transcript、Nexen 事件、Codex 紀錄。再附上預期的正規化輸出，daemon 和兩個 App 都用它做測試。
  • iOS 解析器的知識搬進 daemon：例如已拒絕的判斷、排隊訊息的比對。iOS 的實測結果直接變成 fixtures。

U1 spec 必須補上的缺口（iOS 10-08 回報，全部採納）：

  1. 寫入端點：送出（$.prompt.submit；沒有 mod 時由 daemon 代打字）、停止（$.turn.abort／Esc）、插話、回答（沿用 P8a 的 decide，計畫的回饋怎麼帶）。要定 POST 介面和回傳（已送出／被拒／只送一半）。沒有 mod 時的打字由 daemon 實作：文字＋Enter 原子送出、copy mode 防護、每回合最多一次 Esc（閒置時連按兩次 Esc 會開 Rewind，iOS 實測）。client 只看 capabilities.send 決定行為。
  2. 送出回執：UserMessage 帶 client 送出時的 client_msg_id，client 才能確定地把本地項目換成正式項目，不再靠「內容相同＋送出後新出現」推測。
  3. pane → 對話的對應：client 的分頁綁的是 tmux session；對話的 key（host＋provider＋session id）會因 /clear、--resume、改跑 Codex 而換。sessions 清單或事件要帶「這個 pane 目前的對話 key」，換對話時要通知。要跟「一個對話＝一個主體」那條線的對話身分對齊。
  4. snapshot 大小與往前翻頁：before 游標、snapshot 的回合數上限、snapshot 層級的截斷標記（之前 37MB transcript、tool_result 內嵌圖片的問題在這裡解決）。
  5. 清單用的摘要：sessions／host-events 層級要有 status、序號、context 百分比、背景符號種類、未讀基準；帳號額度要有 host 層級的來源。client 不可能為了清單每一列都開對話。
  6. 推播：iOS 在背景沒有 WS，靠 APNs。daemon 端要有裝置登記、「正在看」的判斷（focus 回報）、內文帶問題本身（iOS P6 brief §6、§6b）。排進 U2。
  7. 斷線補齊：WS 斷開期間的 delta 和 approval.closed 都要能用 after 游標補回，否則手機會留著已經答過的卡片。
