結論：最小可用不在 M0

M0 只是「能 demo 的 walking skeleton」，不是最小可用。真正的最小可用落在 M1（可靠）+ M1.5（能對結果動作的最小 follow-up）。

Codex 的原話定調：「照你現在的切法，最小可用不在 M0，在『M1 再加一個提前的最小 follow-up 切片』；M0 只是能 demo 的 walking skeleton。」

兩個關鍵理由：

  • 沒有恢復路徑 ≠ 脆，是 demo：M0 無 lease，sleep/crash/daemon 掛就卡死。這不是「可用但脆」，是「還不能每天靠它」。→ 至少 manual reclaim / force requeue 要進 M0，自動 lease 進 M1。
  • 只能看不能改 ≠ 可用：M0–M3 若沒有 review 迴圈，等於「派出去、看結果、再手動切去別處接著做」。→ 「看 diff + free-text follow-up / rerun」要從 M4 前移到 M1.5，inline review console 才留最後。
誠實修正：M0 本身也比我原估重一點——要塞進 idempotency、manual reclaim、base_commit、最薄 attempt、deeplink 實作、repo_location scope 限縮（見下）。原本的「M＝主要接線」偏樂觀。

codex provider、worktree 生命週期、inline review console。

M0 到底要裝什麼（codex 擴充後）

codex 判定「demo-able」和「minimally usable」我原本混在一起。M0 要成為誠實的 walking skeleton，這些是不能省的最小防呆與資料正確性：

  • execution_id 當唯一對外穩定 handle——session_code 不能外洩（session 死/host 換/tmux 重建都會破）。
  • idempotency key（原本我放 M1，錯）——派工按鈕 double-click 就製造垃圾 execution，這是最小防呆不是 reliability polish。
  • manual reclaim / force requeue——沒有任何恢復路徑就只能算 demo；自動 lease 可延 M1，但人工重置要在 M0。
  • base_commit 在 ExecutionAccepted 就記——沒有它，連最小 diff artifact 都不穩（review 看到的會是當下 repo 不是當時結果）。
  • 最薄 attempt row（硬限一 execution 一 attempt，attempt_no=1 從第一天就是真的）——比「契約先放 attempt_no 卻沒語義」好，之後上多 attempt 不用改 event shape。
  • deeplink 不是純接線——Purdex 還沒有 OS protocol / session route（S6 草稿已明寫缺口），承諾 M0 有 deeplink 就要把這塊算進工作量。
  • scope 限縮——Ploom native project 不會自動有 repo_location（projects.go:64），M0 要嘛只支援有 repo location 的 project、要嘛補 repo 選擇綁定，否則「選 host+repo」的 scope 是假的。

worktree 延後的真實代價（比我表上重）

codex：worktree 可延到 M3，但代價比「只是不能並行」重。真正會咬人的是：

  • diff 沒穩定 base → review 看到當下 repo 不是當時 execution 結果
  • 人手動改 tree、agent 再跑 → artifact 歸屬會混
  • retry / follow-up 吃到前一次殘留
  • untracked / 暫存 / branch head 漂移污染結果

硬前提：M0–M2 延後 worktree 的話，必須寫死「同 repo/branch 只允許一個 live execution」，且 ExecutionAccepted 一定要記 base_commit。

A 軸安全：sandbox 模式 + host 邊界（M0 必須定案）

worktree 管的是 B 軸（git 隔離 / 整潔）。真正的爆炸半徑控制是 A 軸，跟 worktree 無關，且 M0 就要決定——因為第一次派工就會有 agent 在某台機器上、以某種權限跑。

三層防禦（defense in depth）

層機制M0 選項
1 · executor 權限/沙箱agent 自己的權限模式（in-agent）codex --sandbox read-only|workspace-write|danger-full-access + approval 門檻；claude --permission-mode + --allowedTools/--disallowedTools（別用 --dangerously-skip-permissions）
2 · OS 隔離把 process 整個關起來container（Sculptor 走這條）/ VM（Cursor cloud）/ 裸 process（現況）。M0 可先裸 process，但要清楚這層是空的
3 · host 邊界派到哪台機器＝爆炸半徑邊界主力開發機 vs 專用 / 可拋棄 exec host。dispatch 已帶 target host

M0 要做的三個決定

  • 每個 executor 的預設 sandbox 等級（建議：codex workspace-write + approval；claude 非 bypass 的 permission-mode + tool allowlist）
  • 契約加 sandbox_profile：dispatch 可請求等級，但由 Purdex（daemon＝信任邊界）依 host policy clamp——Ploom 不能越權要求超過該 host 允許的等級（least privilege）
  • host 邊界策略：execution 跑在使用者主機，還是指定的 exec host
A 軸 × B 軸 = 完整安全。sandbox/permission（A，防 agent 亂搞）＋ worktree/base_commit（B，防撞你的工作 + diff 可重現）。兩者正交、都要，但 A 軸 M0 就得定，B 軸可延到 M3。少了 A 軸，有沒有 worktree 都不安全。
待你拍板的設計點：sandbox 等級由誰定？建議 Purdex 持 per-host / per-executor 預設 policy（daemon 是信任邊界），Ploom 的 dispatch 只能 request、Purdex clamp——只能降不能升。你認同「host policy 為準、dispatch 不能升級超過 host 允許」嗎？
