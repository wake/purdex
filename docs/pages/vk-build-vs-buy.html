1 · 一頁結論

VK 不是候選底層，是「終點藍圖 + 設計參考」。build 在你已有的 Ploom + Purdex 上，不 buy。

  • VK 之所以看起來大，是它把「看板 + 執行」塞進一個單機 App。而這兩塊你已分別做好——看板是 Ploom（更深），執行 runtime 是 Purdex（還有 VK 沒有的多 host + snapshot）。要做的不是重造 VK，是縫合兩個已蓋好的半邊。
  • 拿 VK 當 Ploom 底層＝倒退：技術棧衝突（VK 是 Rust+Postgres，你全家是 Go+SQLite）、VK 缺你全部核心（org/權限/view/分享/wiki）、且 VK 已 sunsetting（2026-04-10 公司收攤、Cloud 多人版 30 天後永久關閉，只剩單機）。
  • 拿 VK 當執行後端也弱：UI 死綁、無對外正式 REST（只有 MCP，且繞它自己的 task 資料模型＝會變第二 SOT）、單機、Rust。同層 CAO / Paseo / Overstory 是更好的「借鑑」，而 Purdex daemon 是更好的「地基」。
  • 真正的新工作 = 一條 dispatch 縫（＝四層…其實是五層資料模型），而這條縫本來就在 roadmap 上（Ploom S6 + Purdex 執行層）——不是額外範圍。
  • 順序（Codex 拍板）：先釘 execution / attempt 模型 → 做 Purdex 執行 runtime → 做 diff review 迴圈 → MM bridge 最後。
兩份評估的共識：主 session 與 Codex 都認為「範圍沒想像大、前提是守 MVP 紀律」。Codex 的關鍵加碼：我原本的四層少了 attempt 一層——追平 VK 的重試/多次嘗試/review-後-follow-up 會沒地方放。已採納，見 §2。

2 · 那條縫：五層資料模型

Codex 獨立評估指出：最小合理形狀不是四層，而是五層。attempt 在 VK 是一等概念（VK 現行實作已從「Task Attempt」演進成 Workspace → 多個 Session，就是多次嘗試）——這與功能盤點交叉印證。

issue → dispatch → execution → attempt → session
各層語義（別混）
  • dispatch＝控制面的一筆派工請求（帶 host/repo/prompt/idempotency）
  • execution＝穩定 handle（execution_id，對外唯一穩定 ID）
  • attempt＝同一 execution 的一次嘗試（重試/換做法/比較）
  • session＝runtime 的 stdin/stdout transport 生命週期，不能再當外部穩定 ID
最小事件契約（Codex 建議）
  • DispatchRequested{dispatch_id, issue_id, desired_executor, repo_ref, prompt_ref, idempotency_key}
  • ExecutionAccepted{execution_id, dispatch_id, host_id, attempt_no}
  • ExecutionLifecycle{execution_id, seq, status, ts} — 狀態機：queued/claimed/preparing/running/blocked/needs_review/succeeded/failed/cancelled
  • ExecutionArtifact{execution_id, kind, ref} — kind：transcript/diff/log/snapshot
  • ExecutionControlRequest{execution_id, kind, payload} — blocked-on-human / permission / follow-up
事件不要把 provider raw event 直接穿過縫。Purdex 內部保留 provider-native stream，Ploom seam 只吃 normalized lifecycle/artifact/control events。

3 · 雙平面落差（有 / 缺）

Codex 讀了兩邊 repo 逐項驗證。綠＝已有、紅＝缺，SML 為工作量。

Ploom 側（控制面）

項目狀態量備註
issue / board / kanban（比 VK 深：dependency/subtask/edit-history/sections）有—S2 已 merge
org / 權限 / view / 分享（VK 全無）有—Ploom 存在的理由
dispatch 資料模型 + API + 授權 + CLI缺M現在只有 issue/comment/view/share 端點
execution / attempt 資料模型缺Lstore 只有 issue/comment/file，無 runtime 單元
issue 詳情頁擴成「工作單 + 執行觀測 pane」缺M現掛 labels/subtasks/activity，無 execution pane
execution timeline / live status / artifacts 區塊缺M–L現有 activity 是社交/編輯事件非執行事件
diff review + inline comment + 回送 follow-up 閉環缺LPloom 最貴、風險最高的一塊
Codex 修正我的直覺：Ploom 最貴的不是 dispatch，是「把 issue 詳情頁變成 execution review console」。

Purdex 側（執行面）

項目狀態量備註
tmux 管理 / Stream 模式跑 claude -p 串流 / WS+Bearer有—執行引擎半邊已在
多 host（Tailscale）/ workspace snapshot有—VK/CAO 都沒有
Codex 基礎（internal/agent/codex/provider.go）半S→M已能「觀測」Codex，缺「當 runtime 啟動管理」的 adapter
provider-neutral launch adapter（codex exec --json 正規化）缺M–L目前 preset 只有 cc=claude -p
execution_id + 狀態機（對外穩定 handle）缺L現外部主鍵仍是 session_code/tmux session
dispatch worker（poll/claim/report + idempotency + lease）缺Mclaim 沒 lease → sleep/crash 卡死
observer/controller 分離 + interactive lease缺Mhandler.go:92 多 subscriber 都能寫 stdin＝現成 race
worktree-per-execution 生命週期缺M / L簡版 M、追平 VK L；單人可先跳過（見下）
diff 擷取 + base/head 錨定 + artifact retention缺M–Ldiff review 迴圈的資料來源
attempt/retry 語義缺M沒這層會把「重跑」和「同 session follow-up」混掉
worktree 對單人自用能不能跳過？可以，但只能當「MVP 降階」：前提是同一 repo/branch 同時只允許一個 live execution、dirty tree 風險自負。一旦要並行執行 / 保留多 attempt / 穩定 diff review / 從 review 回送可重現的 follow-up，worktree 幾乎是必要條件。

4 · 分階規模 P0–P3

階段內容量要點
P0 · 縫五層模型 + 中性事件 schema + dispatch 傳輸M不可跳，本來就要做（＝S6 核心）
P1 · MVP 迴圈issue → 派到某 host → claude -p 跑（已有）→ 串回 → 狀態/結果回填；執行檢視先走 deeplink 借 Purdex 現成 UIM主要是接線，引擎已有
P2 · provider 中立加 codex exec --json adapter（已有 observe 骨架）S不綁死一家
P3 · 執行 polishworktree 隔離 / diff review 迴圈 / attempt compare / PR 建立 / dev serverL逐項獨立、按需求排
有用的 VK 等價 MVP = P0+P1(+P2)。Codex 認定的 MVP 範圍：單 issue dispatch、單 execution、單 repo、單 live runner、live status、deeplink、基本 diff 檔案/patch、free-text follow-up。中大型，但還沒到過度工程。
追平 VK 全部 = 到 P3，範圍「大」。真正貴的是 attempt model + worktree lifecycle + diff review loop + provider-neutral executor + MCP surface 整串一起上——約 MVP 的 2–3 倍，非線性加法。先延後：inline hunk comment、多 attempt UI、PR 自動化、完整 MCP、multi-host scheduler。
是否過度工程？若現在就把 MM bridge + 多 host 調度 + 完整 inline review + attempt compare 全開＝過度。只做 Ploom issue → Purdex execution → 回 issue review＝不過度，反而補上你現在缺的「work item 與 session 對齊」。

5 · 五個一定會踩的坑（Codex）

  • local_dir 不是控制面真相——它是 host-relative path；多 host 下 Ploom 不能拿它當 SOT。
  • session_code 不能做 stable handle——session 死、host 換、tmux 重建都會破。對外只能 expose execution_id。
  • claim 沒 lease 幾乎不夠——laptop sleep / daemon crash 就能把 dispatch 卡死；最晚 MVP 第二刀就要補 reclaim。
  • prompt injection 不只在 MM——Ploom 的 issue 描述 / comment / diff comment 都是 prompt boundary；控制命令（stop/resume/attach）要走控制通道、別混進 prompt。
  • 單人 ≠ 低並發——subagent / resume / review follow-up / multi-host 都是並發，別用「單人」當低並發的藉口。

另：現有 S6 草稿把 daemon.host + session_code 當 deeplink 核心（2026-06-30-s6-purdex-dispatch-design.md），太早綁死 transport，不適合長期演進——這正是要先抽 execution_id 的理由。

6 · 最值得參考的對象（不是拿來用，是拿來抄設計）

競品掃描挖到一整排比 VK 更貼近「控制面/執行面分離」的實作。前五名：

#對象為什麼值得抄
1OpenAI Symphony
Apache-2.0 · Elixir		業界「控制面/執行面分離」最乾淨、有實測（內部 3 週 PR +500%）。核心可抄：issue tracker 只需被輪詢 + 能收 PR 結果，agent 內部狀態完全不用讓控制面知道——跟 Ploom/Purdex 分工同構。抄它的輪詢頻率、per-issue workspace、崩潰自動重啟。
2Centaur (Paradigm)
MIT · FastAPI+K8s		跟你「MM bridge」構想架構圖幾乎一模一樣：Slack thread 當控制入口、服務層管 agent session 生命週期、K8s/k3s 沙盒當執行面、事件串流回 thread。架構文件公開完整＝MM bridge 最佳逐段對照範例（延後做，但先讀）。
3Paseo
AGPL-3.0 · daemon+多client		執行面工具裡跟 Purdex 定位最貼近：常駐 daemon（非雲）+ 用你自己裝的官方 CLI/憑證（訂閱合規）+ 多前端 websocket 連進來。互補維度：Paseo 主打多 provider、Purdex 主打多 host——互相檢視對方沒做的。
4Overstory
開源 · AgentRuntime		headless -p --output-format stream-json → NDJSON → parseEvents → web UI，跟 Purdex Stream 模式幾乎同一套做法。工作量小、優先度高：直接對照「我們的 parseEvents 有沒有漏 edge case」。
5Gastown (Steve Yegge)
開源 · Go		跟 Ploom 完全相反的取捨：控制面不借外部 SaaS，把 issue（bead）直接存進 git + DoltHub 跨機聯邦。即使不採用，它劃出「自建協作平面」光譜另一端，幫你驗證 Ploom 的定位值不值（重了多少、換來 權限/view/wiki/分享）。
次要但要記錄：swarm-protocol（控制面可輕到只剩 MCP 狀態同步——若 Ploom 顯得太重時的下限參照）／Mattermost 官方 mattermost-plugin-agents（MM bridge 的官方技術先例，2026-06 剛修 thread context 遺失）／ACP（若 Purdex 未來要對外開放非 claude/codex 的 agent，優先對齊此協定而非自訂——已被 JetBrains/Google/GitHub/Devin 採用，逐漸成事實標準）。

8 · Vibe Kanban 功能全清單（對標標尺）

務必納入評估：VK 母公司 bloop 於 2026-04-10 宣布關閉，Cloud/多人協作 30 天後永久停止，只剩 Local 單機社群維護版。VK 的「團隊協作看板」是官方主動放棄的產品線——對標基準應以 VK Local 為主。
規劃 / 看板（Issue Management）
  • 六狀態欄：Backlog / To do / In progress / In review / Done / Cancelled（預設只顯前四）
  • 描述富文本＝直接變成 agent 的 prompt；Cloud 可建立時即掛 workspace 開跑
  • 優先序四級（Urgent/High/Medium/Low）；排序 Manual/Priority/Created/Updated/Title（只有 Manual 能拖拉）
  • Sub-issue（parent/child，子完成不自動完成父、不可再巢狀）；issue 關聯 blocking/related/has_duplicate（走 MCP）
  • 篩選：Priority/Assignee(多選OR)/Tags(跨維度AND)；標題模糊搜尋 + Simple ID 跳轉；List View 看全部狀態
  • 兩種「tag」：專案分類 tag ＋ 全域文字模板 tag（@mention 插入預寫內容）
  • 看板自訂（Cloud）：增/改/隱藏欄位。不支援 swimlane / custom fields / workflow automation
任務執行（Workspaces / Sessions）★ 核心對標
術語演進：舊 Task → Task Attempt → 現行 Issue → Workspace(=worktree) → Session(=一次對話嘗試)。這就是 Codex 說的 execution/attempt/session 分層在真實產品裡的樣子。
  • Workspace＝隔離環境（1 worktree，可掛多 repo，各自 target/working branch）；建立時自動建 worktree + 自動命名 working branch（vk/abc123-task）+ 跑 setup script
  • Session＝與 agent 的一次對話；同 workspace 可多 session 並行、共享檔案但不共享 context；多 session 改同檔＝last write wins（無鎖/無合併）
  • 沒有 rerun 按鈕：想重跑/換做法＝開新 session（全新 context window、同一批檔案）
  • 生命週期 Active/Archived（保留 worktree）/Deleted（不可逆，但 branch+commit 留 repo）；啟動時自動清孤兒 worktree
  • Git 操作內建：branch/PR(AI生描述,draft)/rebase/merge/push；agent 過程中自動 commit
  • 後端 Executor 抽象：StandardCodingAgentExecutor trait（spawn/spawn_follow_up/normalize_logs → 統一 NormalizedEntry → WebSocket JSON patch 推前端）+ Approval 系統
  • 支援 10 種 agent：Claude Code / Codex / Copilot CLI / Gemini / Amp / Cursor Agent / OpenCode / Droid / CCR / Qwen（VK 不管訂閱，靠各 CLI 自認證）
  • Agent Profile：plan mode/model/permission/sandbox 層級/approval 門檻（untrusted/on-failure/on-request/never）
  • Repo 三腳本：setup（建立時跑一次）/ dev server（URL 印 stdout 才能偵測）/ cleanup（必須 idempotent）
審查 / 迴圈（Review Loop）
  • Changes 面板：檔案樹 + Unified/Side-by-side diff；「Never blindly trust agent output」
  • Inline comment：hover 留言，不逐條送而是打包（badge 標數量），送出時附文字
  • review-feedback-fix loop：agent 收所有 inline comment 當 context 逐一處理，重複到滿意；「重跑」＝開新 session
  • Chat：使用者/agent/系統/錯誤四類訊息；編輯訊息＝建新分支；@ 檔案 typeahead；agent 執行中可排隊訊息；context gauge
  • Slash commands（依 agent 動態）；VSCode/Cursor/Windsurf 擴充（Logs/Diffs/Processes 三面板，須在 worktree 目錄開）
  • 內建瀏覽器預覽：Desktop/Mobile/Responsive + Inspect Mode（React/Vue/Svelte…）+ Eruda DevTools。無自動化測試
整合（GitHub / MCP / API）
  • GitHub/Azure：靠 gh/az CLI 建 PR（自動預填標題/描述/base）。無 webhook / 無雙向狀態同步
  • VK 自家 MCP Server（30+ 工具）供外部 client 呼叫：Context/Org/Project/Issue/Assignee/Tag/Relationship/Repo/Workspace-Session 全套。關鍵執行入口：start_workspace（建 workspace 並啟動一次 session）、create_session、run_session_prompt、get_execution
  • 連外部 MCP（給 VK 內 agent 用，per-agent 設定，寫入 agent 全域設定檔）
  • REST/WebSocket：/workspaces /sessions（含 CreateFollowUpAttempt）/execution；WS stream_workspaces_ws / stream_workspace_diff_ws。但主要是內部前端用，無公開 REST 文件——官方對外只主打 MCP
對我們的意義：VK 的 MCP 是「board 工具的 API」——繞它自己的 project/task/workspace 資料模型。拿它當後端＝把 task 狀態複製進 VK＝第二 SOT。要當執行後端，CAO（execution-centric）/ 直驅官方 CLI（無狀態）都比它乾淨。
設定 / 部署 & 明確「沒有」的東西
  • 安裝 npx vibe-kanban；本機 SQLite / Cloud PostgreSQL+ElectricSQL；認證 Cloud 只有 GitHub/Google OAuth（無 API key/SSO/帳號互聯）
  • Docker Compose 自架（Caddy+PG+Electric+server）；組織角色只有 Admin/Member 二元（對專案存取權相同，差別只在組織管理）
  • Remote Access 靠 VK Cloud 配對（隨 Cloud 關閉會消失）；另有 SSH「Open in VSCode」deep link
VK 明確沒有（＝ Ploom 的差異化）：細粒度權限（只有 Admin/Member）、跨組織/訪客分享、Wiki/知識庫、custom fields、swimlane、workflow automation、對外 webhook、SSO/API key、帳號互聯、瀏覽器自動化測試、多 session 寫入合併、正式對外 REST 文件。
